# Глава 10. Кандидат: сборка исторической аналогии

> **Кратко.** Кандидат выпускается в момент, когда рынок находится в состоянии
> после перехода, и отвечает на вопрос «что бывало раньше в такой же
> конфигурации». Собирается однопроходным алгоритмом с накопителями, где
> ключевая дисциплина — только прошлое и только созревшие исходы. Глава
> разбирает механику снимков, объясняет, почему размер выборки пришлось считать
> дважды разными способами, и даёт формулу `research_score`.

---

## 10.1. Что такое кандидат

Досье об исторической аналогии:

```
BTCUSDT, 2026-08-21 14:15 UTC
Конфигурация: переход 9→7, блок событий event_block_004417,
              возраст состояния 45 мин, энтропия входа low
Такое встречалось: 1339 раз (612 независимых реализаций)
Из них с созревшим исходом: 1287 (96.1%)
В 74% случаев за следующие 24 часа цена шла вверх
Путь хорошего случая: +1.8% в нашу сторону (p70),
                      −0.4% против (p80), отношение 4.5
Повторяемость: 47 месяцев, максимум 8.2% случаев в одном месяце
research_score: 0.71
```

Три правила, без которых вся эта статистика была бы самообманом, объявлены прямо
в шапке модуля:

1. **Только прошлое.** Выборка для кандидата в момент $t$ собирается из случаев,
   произошедших раньше $t$.
2. **Только созревшие исходы.** Случай попадает в выборку не раньше, чем пройдёт
   горизонт: в момент $t$ исход события, случившегося час назад, ещё неизвестен.
3. **Разные возрасты состояния.** Снимки берутся не только в момент перехода, но
   и спустя 45 / 90 / 180 минут.

Первые два — про честность, третье — про полноту покрытия.

## 10.2. Снимки конфигураций

### Зачем офсеты

Если выпускать кандидата только в момент перехода, все кандидаты в истории имели
бы `age_bucket = age_lt_30` и `context_status = fresh`. Оси контекста в приёмнике
не различались бы вовсе — они получали бы одно и то же значение всегда.

Поэтому снимки берутся с четырёх офсетов:

```python
SNAPSHOT_OFFSETS_MIN = (0, 45, 90, 180)
```

Это в точности покрывает все четыре бакета возраста: `<30`, `30–60`, `60–120`,
`>120`.

### Правило same_state

Снимок берётся, только если состояние к этому времени **не сменилось**:

```python
positions = index.get_indexer(transitions.index) + shift_bars
snap_states = states.loc[index[positions]]
same_state = snap_states["state_seq"].to_numpy() == source["state_seq"].to_numpy()
```

Иначе снимок описывал бы уже другую конфигурацию: рынок ушёл из состояния, а
кандидат утверждал бы, что он в нём сидит третий час.

Сравнение идёт по `state_seq`, а не по `group_id`: рынок мог выйти из состояния 7
и вернуться в него же — это другая реализация.

### Офсеты позиционные, а не календарные

```python
shift_bars = offset // bar_minutes
positions = index.get_indexer(transitions.index) + shift_bars
```

На дыре в барах «45 минут» окажется бо́льшим интервалом реального времени. Это
известное свойство, а не дефект: фильтр `same_state` и логика валидности исходов
отсекают снимки, разъехавшиеся с конфигурацией, поэтому дыра даёт не кривой
снимок, а **отсутствующий**.

### Что в снимке

```
ts, offset_min, state_seq, transition_id,
prev_group_id, current_group_id,
age_minutes, age_bucket, entropy,          ← из bar_states
event_block_id, atom_count, family_count,
intensity, primary_family,                 ← из bar_events
ret_pct, mfe_pct, mae_pct, valid           ← из outcomes
```

Снимок без событий или без разметки исхода в выборку не годится:

```python
snapshots["valid"] = snapshots["valid"].fillna(False).astype(bool)
snapshots = snapshots.dropna(subset=["event_block_id"])
```

`fillna(False)` обязателен: после `reindex` пропуск становится `NaN`, а
`bool(NaN)` — это `True`.

На истории BTC получается около 64 тысяч снимков из 26 тысяч переходов — то есть
в среднем 2.4 снимка на переход (не 4, потому что до старших офсетов доживает не
всякая реализация).

## 10.3. Однопроходный алгоритм с накопителями

Главная вычислительная идея модуля. История проходится один раз в хронологическом
порядке, и одновременно поддерживаются два словаря накопителей:

```python
by_full: dict[tuple[str, str], Accumulator] = {}   # (переход, блок) → выборка
by_transition: dict[str, Accumulator] = {}         # переход → выборка
```

```python
for i, row in enumerate(records):
    ts = row["ts"]

    # Шаг 1: доливаем в накопители всё, чей горизонт уже закрылся
    while pending < total and records[pending]["ts"] + horizon <= ts:
        done = records[pending]
        by_full.setdefault(key(done), Accumulator()).add(...)
        by_transition.setdefault(done["transition_id"], Accumulator()).add(...)
        pending += 1

    # Шаг 2: читаем накопитель для текущей конфигурации
    acc = by_full.get((row["transition_id"], row["event_block_id"]))
    ...
```

Указатель `pending` идёт по той же ленте, но отстаёт ровно на горизонт. Тем
самым автоматически выполняются оба правила честности:

- в накопителе только случаи **раньше** текущего момента;
- и только те, чей исход **уже известен** на текущий момент.

Сложность — $O(n)$ по числу снимков, память — $O(k)$ по числу уникальных ключей.
Никаких повторных проходов по истории и никаких оконных запросов.

Функция объявлена генератором, а не возвращает список: кандидатов на восемь лет
истории — сотни тысяч, держать их все в памяти незачем, вызывающий код пишет их
пачками по 5000.

### Откат на переход

Пара «переход × блок событий» набирается не всегда: блоков тысячи, и на редкую
комбинацию история не даст 30 случаев.

```python
acc = by_full.get((transition_id, event_block_id))
scope = "transition+event_block"
if (acc is None or not _sample_enough(acc, cfg)) and cfg.fallback_to_transition:
    acc = by_transition.get(transition_id)
    scope = "transition"
```

Итоговый scope записывается **в тело кандидата** — это поле `sample_scope`. Оно
важнее, чем кажется: при откате поля блока событий у кандидата заполнены (они
описывают текущий бар), но выборка про блок **не знает ничего**. Приёмник обязан
это учитывать, иначе кандидат утверждает «редкий блок» на статистике, к блоку не
относящейся.

Живое распределение scope: 68–81% кандидатов на BTC/ETH/SOL идут с
`sample_scope = transition`, а у HYPEUSDT — **100%**: на 8.4 тысячи снимков
приходится 4.5 тысячи пар, и до 30 аналогов не добирается ни одна. Это следствие
короткой истории, а не поломки.

### Насколько редок полный ключ на самом деле (замер 2026-08-24)

Доля кандидатов с полным ключом (13–19% на монетах с длинной историей) —
величина, посчитанная по КАНДИДАТАМ, а кандидаты порождаются с откатом, и один
частый ключ даёт их сотнями. Замер задачи F волны A (журнал генератора, раздел
57) посчитал то же по **реализациям перехода**, то есть по самим конфигурациям:

| монета | ключей всего | набрали 30 реализаций |
|---|---|---|
| BTCUSDT | 12 574 | **75** (0.6%) |
| ETHUSDT | 11 657 | **87** (0.7%) |
| SOLUSDT | 10 461 | **23** (0.2%) |
| AAVEUSDT | 8 869 | **42** (0.5%) |
| TAOUSDT | 6 145 | **3** (0.05%) |
| HYPEUSDT | ~4 500 | **0** |

**99.3–99.95% конфигураций рынка в истории не повторяются достаточно часто,
чтобы о них можно было сказать хоть что-нибудь.** Откат на переход — не
запасной путь, а основной; полный ключ работает в долях процента случаев.

Это не повод понижать порог: при 30 наблюдениях доверительный интервал доли
имеет ширину около ±0.18, и снижение порога означало бы выпуск кандидатов по
выборкам, где перекос 74% статистически неотличим от 50%.

## 10.4. Накопитель

```python
@dataclass
class Accumulator:
    total: int = 0
    valid: int = 0
    up: int = 0
    ret_sum: float = 0.0
    mfe_up:   list[float]   # отсортирован, путь роста в хорошем случае
    mae_up:   list[float]   # отсортирован, ≥ 0, просадка в хорошем случае
    fav_down: list[float]   # зеркало для short
    adv_down: list[float]
    days:   set             # уникальные даты
    months: Counter         # счётчик по (год, месяц)
    realizations: set       # уникальные state_seq
```

Списки поддерживаются отсортированными через `bisect.insort` — так перцентиль
берётся без сортировки на каждом кандидате.

### Знаковая ловушка в MAE

Самая поучительная строчка модуля:

```python
if ret > 0:
    self.up += 1
    bisect.insort(self.mfe_up, float(mfe))
    bisect.insort(self.mae_up, max(0.0, -float(mae)))
```

Напомним: `mae_pct` — величина **со знаком** (глава 9). Отрицательная, если цена
ходила ниже входа; положительная, если не ходила вовсе.

До 2026-08-13 здесь стоял `abs(mae)`, и это переворачивало смысл: чем чище был
рост без отката, тем больше записывалась «просадка».

> ⚠️ **Ломалось молча, и прицельно.** Загрязнение било именно по хорошим
> случаям: список наполняется только при `ret > 0`, где `mae_pct > 0` как раз
> вероятнее всего.

Правильная формула: $\max(0, -\text{mae})$ — глубина просадки в положительных
процентах, где ноль означает «цена ни разу не была ниже входа». Это
содержательное значение, а не отсутствующее.

Забавная деталь: после починки замер на 56 193 кандидатах показал, что **ни один
не изменился ни на сотую**. Ошибка была верной по сути и нулевой по эффекту — и
это записано в журнале так же подробно, как успехи.

### Зеркало для short

```python
elif ret < 0:
    bisect.insort(self.fav_down, max(0.0, -float(mae)))   # выгода short
    bisect.insort(self.adv_down, max(0.0,  float(mfe)))   # риск short
```

Для короткой стороны роли меняются местами: выгода — глубина хода вниз, риск —
то, что пришлось пересидеть вверх.

До 2026-08-13 этих двух накопителей не было вовсе, и следствие было тихим:
F/A ratio существовал только для long, приёмник честно ставил short'у `None` и
считал ось directional по двум критериям вместо трёх. Медианный short получал по
этой оси 0.100 против 0.400 у long — **штраф за сторону рынка, а не за качество
конфигурации**.

Разметка горизонта при этом симметрична с самого начала: `outcomes` считает MFE и
MAE каждому бару. Не хватало ровно этих двух списков.

Случай `ret == 0` не попадает ни в одну ветку: нулевой исход не является
«хорошим случаем» ни для одной из сторон. В `short_outcome_count` он при этом
входит, потому что там считается «не вверх», а не «вниз».

## 10.5. Два размера выборки

Здесь самая содержательная правка в истории модуля.

### Проблема

`total` считает **строки снимков**. Одна реализация перехода даёт до четырёх
строк (офсеты 0/45/90/180), и окна их исходов при горизонте 24 часа
перекрываются минимум на 87.5%:

```
офсет 0:    [t+1 … t+96]
офсет 180:  [t+13 … t+108]     ← общих баров 84 из 96
```

То есть четыре «наблюдения» — это одно и то же событие, посмотренное четыре
раза.

Замер 2026-08-13 на четырёх монетах: медиана завышения **2.2** (не 4, потому что
до старших офсетов доживает не всякая реализация — `same_state` отсекает).

Значит «выборка 1000» означала около 450 случаев, и всё, что от размера выборки
зависит — `research_score`, пороги выпуска, ступень statistical в приёмнике —
оперировало завышенным числом.

### Решение

```python
@property
def effective(self) -> int:
    """Число независимых реализаций перехода в выборке."""
    return len(self.realizations)
```

Множество `state_seq`: все снимки одной реализации имеют один `state_seq`
(глава 8), поэтому размер множества и есть число случаев.

**Оба числа уходят наружу.** Ломать `sample_size` нельзя — на нём откалиброваны
профили оценки. Поэтому кандидат несёт и `sample_size` (строки), и
`effective_sample_size` (случаи), а приёмник решает, чем пользоваться.

### Порог выпуска

```python
def _sample_enough(acc, cfg) -> bool:
    return (acc.total >= cfg.min_sample_size            # 30 строк, мягкий
            and acc.effective >= cfg.min_effective_sample_size)  # 30 случаев
```

Значение то же — 30, — но теперь оно означает то, что написано. Прямое следствие:
кандидатов заметно меньше. Отсев при переходе на новый порог: 20.3% у BTC, 15.6%
у ETH, 26.9% у SOL и **74.9%** у HYPEUSDT с её годовой историей.

Это и есть цель: система перестала утверждать больше, чем знает.

## 10.6. Перцентили пути

Две величины, описывающие «типичный хороший случай»:

$$\text{p70\_favorable} = Q_{0.70}\left(\{\text{mfe}_i : \text{ret}_i > 0\}\right)$$

$$\text{p80\_adverse} = Q_{0.80}\left(
\{\max(0, -\text{mae}_i) : \text{ret}_i > 0\}\right)$$

$$\text{F/A ratio} = \frac{\text{p70\_favorable}}{\text{p80\_adverse}}$$

Читается так: «в 70% хороших случаев цена прошла в нашу сторону не менее чем на
X%, а против нас в 80% случаев не более чем на Y%». Отношение — грубая мера
«потенциал к риску».

Перцентили разные (70 и 80) намеренно: к выгоде требование мягче, к риску —
строже. Это калибровочный выбор из исходного ТЗ, параметры
`CAND_FAVORABLE_PCT` / `CAND_ADVERSE_PCT`.

Реализация — линейная интерполяция по уже отсортированному списку:

```python
pos = (len(values) - 1) * q / 100.0
low, high = int(np.floor(pos)), min(int(np.floor(pos)) + 1, len(values) - 1)
weight = pos - low
return values[low] * (1 - weight) + values[high] * weight
```

При нулевом знаменателе (просадок в выборке не было вовсе) ratio равен просто
числителю, а не бесконечности:

```python
ratio = favorable / adverse if adverse > 1e-9 else float(favorable)
```

Short-версия считается **всегда**, а не только short-кандидату: это свойство
конфигурации, а не стороны, и решать, что с ним делать, должен приёмник.
Но `None`, если падений в выборке не было вовсе:

```python
ratio_short = None
if acc.fav_down:
    ...
```

Пустой список дал бы ratio = 0.0, а это не «плохое отношение», это отсутствие
данных. Правило то же, что для всех Optional-полей: **критерий без данных
выбывает, а не начисляет ноль**.

## 10.7. research_score

Синтетическая оценка силы исторической аналогии, $[0, 1]$. Считается генератором
и в приёмник уходит как одно из полей.

```python
skew = abs(2 * acc.long_share - 1)

s_skew   = min(1.0, skew / 0.5)
s_sample = min(1.0, np.log10(acc.effective + 1) / 3.0)
s_repeat = min(1.0, months / 18.0)
s_spread = 1.0 - min(1.0, acc.monthly_concentration / 0.5)
s_valid  = acc.valid / acc.total
s_rare   = (rarity_score(transition) + rarity_score(block)) / 2

score = (0.25 * s_skew + 0.20 * s_sample + 0.15 * s_repeat
       + 0.15 * s_spread + 0.15 * s_valid + 0.10 * s_rare)
```

Шесть компонент, все в $[0, 1]$, веса в сумме 1.0.

| Компонента | Формула | Что мерит | Насыщение |
|---|---|---|---|
| `s_skew` | $\min(1, \|2p_\uparrow - 1\| / 0.5)$ | сила перекоса | при доле 75% или 25% |
| `s_sample` | $\min(1, \log_{10}(n_{\text{эфф}} + 1) / 3)$ | объём | при 1000 случаев |
| `s_repeat` | $\min(1, m / 18)$ | распределённость по месяцам | при 18 месяцах |
| `s_spread` | $1 - \min(1, c / 0.5)$ | равномерность | 0 при концентрации 50% |
| `s_valid` | доля валидных | качество разметки | — |
| `s_rare` | среднее двух категорий | специфичность | — |

Логарифм в `s_sample` — потому что полезность выборки растёт сублинейно: разница
между 30 и 100 случаями огромна, между 900 и 1000 — пренебрежима.

`s_sample` считается по **реализациям**, а не по строкам: до 2026-08-13 здесь
стоял `acc.total`, и «1000 случаев → 1.0» означало около 450.

$$\text{monthly\_concentration} = \frac{\max_m n_m}{\sum_m n_m}$$

Доля случаев, попавших в один месяц. Защита от «все 1000 случаев за одну неделю
мая 2021 года».

### Что research_score не является

Явно проговорено в докстринге:

> Это **не вероятность прибыли** — только то, насколько выборка велика,
> устойчива во времени и однонаправлена.

Приёмник считает свой `quality_score` независимо и использует `research_score`
лишь как один из входов оси rarity.

### Ограничение начисления за редкость блока

```python
e_rarity_scored = e_rarity if scope == "transition+event_block" else "common"
```

Редкость блока описывает бар, на котором выпущен кандидат, и в этом качестве
честна всегда. Но **начислять** за неё баллы можно только когда выборка на блок
обусловлена: при откате на `scope = "transition"` статистика собрана по переходу
целиком, и «редкий блок» к ней отношения не имеет.

То же ограничение стоит в приёмнике (`_score_rarity` по `sample_scope`) — здесь
его двойник для `research_score`.

## 10.8. Сборка полей

### Направление

```python
skew = 2 * long_share - 1
if abs(skew) < cfg.min_abs_skew:      # 0.06
    return None                        # кандидата нет
side = "long" if skew > 0 else "short"
```

Без перекоса кандидата нет: направление не определено. Порог 6% отсекает
конфигурации, где доля роста между 47% и 53%.

Отдельно считается `historical_bias_context` с другим, более строгим порогом:

```python
def _bias_context(long_share, threshold=0.10):
    if long_share > 0.5 + threshold:  return "long_skew"
    if long_share < 0.5 - threshold:  return "short_skew"
    return "neutral"
```

### Почему side входит в ключ семьи

```python
"candidate_family_key": f"{symbol}|{group}|{transition}|{block}|{bias}|{side}"
```

Пороги разные (0.06 против 0.10), и в полосе между ними long-кандидат и
short-кандидат по одной конфигурации получают `bias = "neutral"` **оба**.

До 2026-08-13 они падали в одну семью и вытесняли друг друга в
`select_best_per_family` приёмника — выживал не более сильный по направлению, а
более свежий. Конфликт направлений при этом и так детектируется отдельно
(`candidate_filter.detect_conflicts`), схлопывать их в ключе незачем.

### Свежесть контекста

```python
context_status = "fresh" if row["age_minutes"] <= 30 else "stale"
```

Конфигурация ещё формально та же, но снимок уже не «сейчас».

### Поля размаха

```python
def _range_fields(ts, range_view):
    if range_view is None:
        return dict.fromkeys(RANGE_FIELDS)      # все четыре None
    try:
        row = range_view.loc[ts]
    except KeyError:
        return dict.fromkeys(RANGE_FIELDS)
    return {"expected_range_ratio_p50": ..., "range_lift": ..., ...}
```

Отсутствие строки — **штатный случай**: так выглядит бар до конца обучения
модели размаха, бар без полного набора признаков и любой бар, если модель не
заведена. Пустые поля честно означают «система про размах этого бара ничего не
говорит».

Важно: прогноз приходит сюда **готовым**. Генератор кандидатов ничего не
вычисляет заново — это тот же принцип, по которому приёмник только оценивает.

## 10.8а. Сколько конфигураций значимы после поправки на множественность

Вопрос, который система не задавала себе ни разу: кандидат выпускается при
$|\text{skew}| \ge$ `min_abs_skew`, но **сколько ключей отличаются от базовой
ставки монеты значимо после поправки на множественность?** При 12 тысячах
ключей и $\alpha = 0.05$ без поправки «значимыми» окажутся шестьсот штук из
чистого шума — и именно они, будучи самыми перекошенными, попадут в кандидаты.

Замер (задача F волны A, `make measure-configs`, журнал генератора раздел 57)
устроен так: одна строка = одна **реализация** перехода (не снимок — снимки
дают до четырёх строк на реализацию с перекрытием окон 87.5%), статистика —
отклонение доли от базовой ставки, стандартизованное биномиальной ошибкой,
нулёвка — блочная перестановка принадлежности ключу при неподвижных исходах.

P-value не берётся прямо из реплик, и это арифметика: минимум достижимого —
$1/(1+B) = 0.0005$ при $B = 2000$, а порог BH для сильнейшего из 12 тысяч
ключей при $\alpha = 0.10$ — порядка $10^{-5}$. Из реплик оценивается
**коэффициент раздутия дисперсии** по бинам размера выборки, а $p$ считается по
нормальному приближению. Раздутие вышло 1.00–1.08: на уровне реализаций
зависимость наблюдений почти не раздувает дисперсию (на уровне снимков она
раздувала её втрое — глава 12.1).

**Результат: 7 ключей на пять монет.** BTC — 2, ETH — 2, SOL — 1, AAVE — 1,
TAO — 1, HYPE — 0. Негативный контроль (исходы блочно переставлены) дал ноль
на каждой монете.

Предсказание было записано до прогона в форме «выживут единицы или ноль» и
сбылось. Читать выживших надо ровно так, как записано там же: **это отдельные
находки, разбираемые штучно, а не механизм выпуска сигналов.** Семь ключей на
всю историю пяти монет — и все они привязаны к конкретной модели состояний, то
есть не переживут ближайшего `train`.

## 10.10. Кандидаты train против кандидатов live

Различие, которое надо держать в голове при любом анализе.

**Кандидат `train`-прогона in-sample по определению состояний.** Модель обучалась
на всей истории, включая бар этого кандидата и его будущее. Разметка состояния,
которую он несёт, посчитана моделью, знавшей исход.

**Кандидат `live`-прогона честен.** Модель обучена раньше, бар размечен
загруженной моделью, ничего из будущего в разметку не попало.

Отсюда:

- поля размаха у `train`-кандидатов **пустые всегда** — модель размаха режет
  выдачу по `train_end` (глава 13);
- маркеры на графике разделены по слоям `issued` / `all` (глава 8.8);
- любой замер обязан различать эти два типа.

Отправляются наружу обычно только `live`-кандидаты: недельный `train` идёт с
`--no-emit`. Исторический бэкфилл делается отдельной командой `emit`.

## 10.11. Резюме главы

Кандидат — результат однопроходного алгоритма с двумя уровнями накопителей и
отстающим указателем, который автоматически обеспечивает «только прошлое и

Две поправки, сделавшие выдачу честнее и скромнее: размер выборки по независимым

следующей главы.
