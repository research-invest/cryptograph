# Глава 11. Оценка: четыре оси и профили монет

> **Кратко.** `quality_score` ∈ [0, 1] — взвешенная сумма четырёх осей, каждая
> из которых усредняет несколько критериев, а каждый критерий считается по
> ступенчатой шкале. Ни одного порога нет в коде: все живут в YAML-профиле
> монеты, потому что «выборка больше 1000» — характеристика рынка с
> десятилетней историей, а не универсальная истина. Глава разбирает формулу,
> механику профилей, процедуру калибровки и защиты, которые не дают линейкам
> разъехаться незаметно.

---

## 11.1. Формула целиком

$$Q = w_{\text{stat}} A + w_{\text{dir}} B + w_{\text{ctx}} C + w_{\text{rar}} D$$

Веса базового профиля: $0.30$, $0.35$, $0.20$, $0.15$; сумма проверяется при
загрузке.

Каждая ось — среднее своих критериев:

$$A = \frac{1}{4}\Big(
L_{\text{valid}}(\text{valid\_label\_pct}) +
L_{\text{size}}(n) +
L_{\text{conc}}(\text{monthly\_concentration}) +
L_{\text{rep}}(\text{repeatability\_months})\Big)$$

$$B = \frac{1}{k}\Big(
L_{\text{win}}(\text{win\_rate}) +
L_{\text{skew}}(|\text{skew}|) +
[\,L_{\text{fa}}(\text{F/A})\,]\Big),
\qquad k \in \{2, 3\}$$

$$C = \frac{1}{3}\Big(
M_{\text{ctx}}(\text{context\_status}) +
M_{\text{age}}(\text{age\_bucket}) +
M_{\text{ent}}(\text{trajectory\_entropy})\Big)$$

$$D = \frac{1}{k}\Big(
M_{\text{tr}}(\text{transition\_rarity}) +
L_{\text{rs}}(\text{research\_score}) +
[\,M_{\text{ev}}(\text{event\_rarity\_bucket})\,]\Big),
\qquad k \in \{2, 3\}$$

Здесь $L$ — ступенчатая шкала по числовому признаку, $M$ — карта
«значение enum → балл». Квадратные скобки означают критерий, который **выбывает
при отсутствии данных**, и тогда ось делится на меньшее число.

Рейтинг:

$$\text{rating} = \begin{cases}
\text{STRONG}, & Q \ge \text{strong\_min} \\
\text{MODERATE}, & Q \ge \text{moderate\_min} \\
\text{WEAK}, & \text{иначе}
\end{cases}$$

В базовом профиле границы 0.75 и 0.55.

## 11.2. Ступенчатая шкала

```yaml
sample_size: {mode: higher_better, ladder: [[1000, 1.0], [500, 0.7], [200, 0.4]], floor: 0.1}
```

Читается сверху вниз, сравнение **строгое**:

```python
def apply(self, value):
    if self.mode == "higher_better":
        for threshold, score in self.ladder:
            if value > threshold:
                return score
    else:
        for threshold, score in self.ladder:
            if value < threshold:
                return score
    return self.floor
```

$$L(v) = \begin{cases}
1.0, & v > 1000 \\
0.7, & 500 < v \le 1000 \\
0.4, & 200 < v \le 500 \\
0.1, & v \le 200
\end{cases}$$

Строгое сравнение — не мелочь: `valid_label_pct == 0.85` даёт 0.7, а не 1.0. Это
поведение перенесено из исходного хардкода слово в слово и заморожено тестом.

### Две проверки при загрузке

**Монотонность.** Немонотонная лесенка означает недостижимую ступень: проверка
идёт сверху вниз, и порог, который слабее предыдущего, не сработает никогда.

```python
ordered = all(a > b for a, b in zip(thresholds, thresholds[1:]))  # higher_better
if not ordered:
    raise ValueError(f"пороги должны строго убывать … часть ступеней недостижима")
```

Ровно этот дефект был найден аудитом в хардкоде оси `age_60_120` — и там его
нельзя было увидеть иначе как тестом.

**Достижимость верхней ступени.** Для признаков, значение которых по схеме лежит
в [0, 1], порог 1.0 у `higher_better` не сработает никогда:

```python
_SHARE_FIELDS = {"valid_label_pct", "monthly_concentration",
                 "win_rate", "abs_outcome_skew", "research_score"}

if spec.mode == "higher_better" and top >= 1.0:
    raise ValueError(f"{name}: верхняя ступень {top} недостижима …")
```

Не гипотетика: калибратор предложил такую ступень на реальных данных ETH — p90
доли валидных меток оказался ровно 1.0. Монотонность такое не ловит.

## 11.3. Ось A: статистическая надёжность

Четыре критерия, все про качество выборки.

| Критерий | Направление | Базовые ступени |
|---|---|---|
| `valid_label_pct` | больше лучше | 0.85 / 0.80 / 0.75 → 1.0 / 0.7 / 0.4 |
| `sample_size` | больше лучше | 1000 / 500 / 200 → 1.0 / 0.7 / 0.4 |
| `monthly_concentration` | меньше лучше | 0.10 / 0.15 / 0.30 → 1.0 / 0.7 / 0.3 |
| `repeatability_months` | больше лучше | 15 / 12 / 6 → 1.0 / 0.7 / 0.4 |

### Переход на эффективный размер выборки

Глава 10 объяснила, что `sample_size` завышен примерно вдвое. Но просто
подставить `effective_sample_size` в ту же ступень нельзя: пороги вида 1010
откалиброваны на строках, и применить их к вдвое меньшему числу значит занизить
оценку всем.

Решение — необязательная вторая ступень:

```python
def _sample_size_score(c, spec):
    if spec.effective_sample_size is not None and c.effective_sample_size is not None:
        return _ladder(c.effective_sample_size, spec.effective_sample_size)
    return _ladder(c.sample_size, spec.sample_size)
```

«Обе стороны» — это профиль (у него определена ступень) и кандидат (он несёт
поле, то есть выпущен после 2026-08-13). Если хотя бы одной нет, считаем по
строкам — той самой ступени, на которой кандидат и был выпущен.

> ⚠️ **Смешивать нельзя ни в какую сторону.** Ступень по реализациям примерно
> вдвое ниже ступени по строкам. Применить её к `sample_size` — завысить оценку
> всем старым кандидатам; обратное — занизить всем новым. Ошибка была бы тихой:
> числа остаются правдоподобными.

Живой пример из профиля BTCUSDT@4:

```yaml
sample_size:           ladder: [[1010, 1.0], [585, 0.7], [242, 0.4]]
effective_sample_size: ladder: [[416, 1.0], [248, 0.7], [127, 0.4]]
```

Отношение порогов 2.4 / 2.4 / 1.9 — та самая измеренная кратность.

## 11.4. Ось B: сила перекоса

$$\text{win\_rate} = \begin{cases}
\text{long\_outcome\_share}, & \text{side} = \text{long} \\
1 - \text{long\_outcome\_share}, & \text{side} = \text{short}
\end{cases}$$

Единственное место перевода доли роста в win rate — функция `win_rate_for`. В
профиль она не выносится: это свойство данных, а не калибровки.

$$\text{F/A} = \begin{cases}
\text{long\_favorable\_adverse\_ratio\_p70\_p80}, & \text{side} = \text{long} \\
\text{short\_favorable\_adverse\_ratio\_p70\_p80}, & \text{side} = \text{short}
\end{cases}$$

Может быть `None` — у кандидатов, выпущенных до появления поля, и у
конфигураций, где падений в выборке не было вовсе. Тогда ось считается по двум
критериям.

Историческая справка: до 2026-08-13 short-версии не существовало вовсе, и
короткая сторона получала систематический штраф — медиана оси 0.100 против 0.400
у long (глава 10.4).

Ступени **общие на обе стороны**. Отдельные ступени на сторону были реализованы и
отвергнуты замером: после появления short-версии F/A они не меняют ни медиану
оси, ни её разброс, а на ETHUSDT ухудшали баланс.

## 11.5. Ось C: контекстуальная свежесть

Три карты enum → балл:

```yaml
context_status:     {fresh: 1.0, stale: 0.0}
age_bucket:         {age_lt_30: 1.0, age_30_60: 0.75, age_60_120: 0.5, age_gt_120: 0.0}
trajectory_entropy: {low: 1.0, medium: 0.5, high: 0.0}
```

Логика: чем дольше рынок сидит в состоянии, тем ближе смена фазы; чем
хаотичнее была траектория входа, тем менее определённа конфигурация.

Полнота карт проверяется при загрузке против самих enum'ов:

```python
_validate_enum_map("context.age_bucket", self.age_bucket,
                   {e.value for e in AgeBucket})
```

Проверяются обе стороны: не покрытое значение — ошибка, неизвестный ключ —
тоже. Второе ловит опечатки, которые иначе создали бы мёртвую строку.

## 11.6. Ось D: редкость и специфичность

```yaml
event_rarity_bucket: {rare: 1.0, uncommon: 0.7, common: 0.2}
transition_rarity:   {rare: 1.0, uncommon: 0.7, common: 0.2}
research_score:      {mode: higher_better, ladder: [[0.85, 1.0], [0.70, 0.6]], floor: 0.2}
```

Здесь работает то же ограничение, что в `research_score` генератора:

```python
if c.sample_scope != SampleScope.transition:
    criteria = 3
    score += _map(c.event_rarity_bucket.value, spec.event_rarity_bucket)
```

При `sample_scope == "transition"` генератор откатился на статистику по переходу
целиком; «редкий блок» тогда описывает текущий бар, а не то, из чего собрана
выборка. Начислять за него — то же самое, что начислять long-кандидату за чужую
сторону рынка.

`sample_scope is None` (старые выгрузки) трактуется как «не знаем» — поведение
прежнее, три критерия. Иначе появление поля молча сдвинуло бы оценку всей
накопленной истории.

Эффект правки был крупным: `sample_scope = transition` — это 68–81% выдачи на
основных монетах и 100% у HYPEUSDT.

## 11.7. Профили: зачем и как

### Проблема

Порог «выборка больше 1000 случаев» откалиброван под рынок с десятилетней
историей. Для монеты с двумя годами торгов та же лесенка означает «всё WEAK» — и
это свойство линейки, а не кандидатов.

### Решение

YAML-файл на монету в `config/symbols/`:

```yaml
symbol: BTCUSDT
version: 4
description: 'Калибровка по 7980 свежим кандидатам выгрузки v3 модели #24'
extends: _default

weights: {statistical: 0.3, directional: 0.35, context: 0.2, rarity: 0.15}
statistical:
  sample_size:
    mode: higher_better
    ladder: [[1010, 1.0], [585, 0.7], [242, 0.4]]
    floor: 0.1
  …
```

Почему YAML в каталоге, а не Python-модуль и не таблица в БД:

- правится без пересборки образа (каталог монтируется volume'ом);
- лежит в git рядом с кодом — видно в диффе, кто и когда двигал пороги;
- не требует живого PostgreSQL, чтобы посчитать score.

Реестр профилей заодно работает **whitelist'ом монет**: отдельного списка
символов в приёмнике нет. Неизвестный символ получает `_default` и warning-флаг
`unknown_symbol_profile`, но оценку получает — валидатор по контракту не бросает
исключений.

### Наследование

Только от `_default`, только на один уровень:

```python
if parent != DEFAULT_PROFILE_NAME:
    raise ValueError("наследование поддерживается только от _default")
```

Слияние глубокое, с одним важным различием:

- **словари сливаются по ключам** — можно подвинуть один бакет `age_bucket`, не
  переписывая все четыре; полнота гарантирована родителем;
- **списки заменяются целиком** — `ladder` наследуется только целиком.
  Частично унаследованной лесенки не бывает: её нельзя было бы прочитать глазами
  по одному файлу. При этом `mode` и `floor` рядом с ней наследуются.

Поле `description` **не наследуется** намеренно: унаследованное, оно превращает
реестр в дезинформацию — профиль ETHUSDT показывал бы себя как «базовую
калибровку под BTCUSDT».

### Битый профиль не роняет процесс

```python
except Exception as exc:
    _load_errors[path.stem.upper()] = f"{type(exc).__name__}: {exc}"
    logger.error("Профиль %s не загружен — монета будет считаться по %s", …)
    continue
```

Исключение — сам `_default`: без него считать нечем, и молчать об этом нельзя
(`FileNotFoundError`).

## 11.8. `_default` — не калибровка, а мерка

Файл `_default.yaml` исторически был переносом хардкода слово в слово — той
самой калибровкой под BTCUSDT. С версии BTCUSDT@2 биткоин на неё больше не
опирается: у него, как и у всех, свой профиль.

Роль сменилась и стала важнее:

- по нему считается `quality_score_baseline` у **всех** монет — единственное
  межмонетно сравнимое число;
- по нему оценивается монета, у которой своего профиля ещё нет.

> **Этот файл не калибруют.** Его правка обесценивает все накопленные baseline
> разом и рушит сравнимость задним числом.

Заморожен снапшот-тестом на 200 кандидатах и продублирован копией в
`tests/fixtures/profiles/`. Если правка всё же осознанна: бампнуть `version`,
пересобрать снапшот (`scripts/make_scorer_snapshot.py`), обновить копию в
фикстурах и раздел README.

### Два числа у каждого кандидата

```python
total    = _weighted_total(stat, direc, ctx, rar, profile)   # профильный
baseline = _weighted_total(…, default_profile())             # общая мерка
```

| Число | Сравнимо | Участвует в рейтинге |
|---|---|---|
| `quality_score` | внутри монеты | да |
| `quality_score_baseline` | между монетами и во времени | нет |

Двух рейтингов не заводим: рейтинг считается **только** от профильного.

Оптимизация: если профиль монеты и есть базовый (совпали symbol и version),
второй проход пропускается.

## 11.9. Отпечаток профиля

Каждая сохранённая оценка помечена двумя полями:

```python
scoring_profile:    "BTCUSDT@4"
profile_fingerprint: "a3f9c2e10b47"     # sha256 содержимого, 12 символов
```

Зачем оба. Метка `symbol@version` ловит осознанную перекалибровку. Отпечаток
ловит **правку порога без бампа версии** — иначе записи «до» и «после» лежали бы
под одной меткой и молча смешивались в средних.

Правило чтения данных: сравнение корректно только внутри одного
`scoring_profile` **и** одного отпечатка. Это стоит проговаривать в ответах
пользователю.

### Отпечаток считается один раз на объект

```python
@property
def fingerprint(self) -> str:
    if self._fingerprint is None:
        payload = json.dumps(self.model_dump(mode="json", exclude={"description"}),
                             sort_keys=True, ensure_ascii=False, separators=(",", ":"))
        self._fingerprint = hashlib.sha256(payload.encode()).hexdigest()[:12]
    return self._fingerprint
```

Это не микрооптимизация. Замер на 31 921 кандидате BTC: **3.53 секунды из 3.78
секунд всего скоринга** уходило на пересчёт одной и той же константы —
`model_dump` вложенной модели плюс sha256 на каждого кандидата.

Кэш безопасен ровно потому, что модель `frozen=True`. Перезагрузка каталога
собирает **новые** объекты, а не правит эти. Если модель когда-то перестанет
быть frozen, кэш придётся снимать здесь же — иначе правка порога снова станет
невидимой, тем самым способом, от которого отпечаток и защищает.

## 11.10. Калибровка новой монеты

Скрипт `scripts/calibrate_profile.py` предлагает ступени как перцентили
реального распределения монеты и сразу показывает, что от этого изменилось.

```bash
# 1. выгрузить кандидатов (ORDER BY ts обязателен)
psql -c "\copy (SELECT payload FROM processing.candidates
         WHERE symbol='ETHUSDT' ORDER BY ts) TO 'dumps/eth.jsonl'"

# 2. черновик
python3 scripts/calibrate_profile.py --symbol ETHUSDT --input dumps/eth.jsonl --dry-run

# 3. записать
python3 scripts/calibrate_profile.py --symbol ETHUSDT --input dumps/eth.jsonl \
        --out config/symbols/ETHUSDT.yaml

# 4. проверить схему и положить sanity-якорь
make profiles-check
```

### Правило хвоста

По умолчанию калибровка идёт **по свежему окну выгрузки**, а не по всей истории
(`--tail`, четверть по умолчанию).

Причина: `sample_size` монотонно растёт по мере накопления истории. Кандидат
2018 года видит сотню аналогов, кандидат 2026-го — тысячи. Перцентили по всей
выгрузке ставят планку туда, где сидели бедные ранние годы, а применяется
профиль к сегодняшним кандидатам — и те массово оказываются «выдающимися».

На данных ETH это дало 10% STRONG на калибровочной части против **26%** на свежей
трети.

### Правило `ORDER BY ts`

> ⚠️ **Ломается молча.** В схеме кандидата нет поля времени (`_meta` снимается
> перед отправкой), и скрипт доверяет порядку строк. На нём держатся и `--tail`,
> и `--holdout`. Выгрузка без сортировки превращает «проверку на будущем» в
> проверку на случайной половине, и она перестаёт что-либо ловить.

### Целевая селективность

`--target-strong`, по умолчанию 0.01 — столько STRONG даёт BTC.

Рейтинг сравним только внутри монеты, но сводный список «что сегодня сильного»
общий: монета со щедрой планкой залила бы его.

### Шесть правил калибровки

Из `docs/step_04_multi_symbol.md`, применяются в этом порядке:

1. **Сначала ступени, потом веса** — вес не чинит вырожденную ось.
2. **Ступени от перцентилей выборки**, а не от круглых чисел.
3. **Три диагноза читаются по распределению** — вырожденная ось (σ близко к
   нулю), мёртвая ступень, перекос селективности.
4. **Чем меньше данных, тем больше веса статистической надёжности.**
5. **Два якоря**: регрессия BTC (снапшот-тест) и sanity-кандидат монеты.
6. **Калибровка — событие**: меняешь профиль → бампаешь `version`.

Скрипт выдаёт **черновик**, а не готовый профиль: перцентили не знают, что
`sample_size = 120` статистически несостоятелен независимо от того, что это p90
конкретной монеты.

### Монету нельзя завести без sanity-якоря

`tests/fixtures/sanity_candidates.json` — по одному реальному кандидату на
монету с ожидаемым рейтингом. На это есть отдельный **падающий** тест: профиль,
который нечем проверить, проверить некому.

## 11.11. Живая картина по шести монетам

Из локальной базы на 2026-08-21 (78 381 оценка):

| Монета | Оценок | STRONG | MODERATE | Средний Q |
|---|---|---|---|---|
| BTCUSDT | 31 151 | 315 (1.0%) | 11 752 | 0.517 |
| ETHUSDT | 26 544 | 176 (0.7%) | 9 265 | 0.468 |
| SOLUSDT | 15 554 | 87 (0.6%) | 5 665 | 0.480 |
| AAVEUSDT | 3 983 | 50 (1.3%) | 3 933 | 0.565 |
| TAOUSDT | 685 | 11 (1.6%) | 674 | 0.568 |
| HYPEUSDT | 464 | 16 (3.4%) | 448 | 0.608 |

Доля STRONG держится около целевого 1% у крупных монет и растёт у молодых — там
профилей мало данных, и калибровка грубее.

Насколько разъезжаются сами линейки, видно по действующим профилям:

| Профиль | STRONG ≥ | MODERATE ≥ | Порог батча | Верхняя ступень `sample_size` | То же по реализациям |
|---|---|---|---|---|---|
| BTCUSDT@4 | 0.697 | 0.482 | 0.482 | 1010 | 416 |
| ETHUSDT@3 | 0.714 | 0.485 | 0.485 | 1310 | 595 |
| SOLUSDT@3 | 0.735 | 0.497 | 0.497 | 596 | 274 |
| AAVEUSDT@1 | 0.718 | 0.495 | 0.495 | 764 | 297 |
| TAOUSDT@1 | 0.782 | 0.490 | 0.490 | 271 | 119 |
| HYPEUSDT@3 | 0.793 | 0.498 | 0.498 | 137 | 59 |
| `_default@1` | 0.75 | 0.55 | 0.60 | 1000 | — |

Читается так: **одно и то же число `quality_score` означает у разных монет
разное.** 0.70 — это STRONG у биткоина и MODERATE у HYPEUSDT. Верхняя ступень
объёма выборки различается почти в десять раз (1310 у ETH против 137 у
HYPEUSDT), и это не щедрость к молодой монете, а её фактическое распределение.

Обратите внимание, что **порог батча у всех монет равен нижней границе
MODERATE**. Отсюда и наблюдение выше: WEAK в базе почти не появляется — приёмник
отсекает такие оценки ещё до записи. У `_default` порог выше границы (0.60
против 0.55) — он не калибруется и остаётся с исходными числами ТЗ.

Средний `quality_score` между монетами сравнивать **нельзя** — для этого
существует baseline.

## 11.12. Валидатор и фильтры

### Валидатор только помечает

`validate_candidate` возвращает список `warning_flags` и **никогда не бросает
исключений**. Кандидат по монете без профиля обязан быть оценён — с флагом, но
оценён.

Одиннадцать флагов: `symbol_defaulted`, `unknown_symbol_profile`,
`context_status_stale`, `age_gt_120`, `stale_and_aged_combined`,
`transition_rarity_common`, `low_valid_label_pct`,
`false_confidence_high_score_low_validity`,
`high_monthly_concentration_seasonal_risk`, `very_small_sample_size`,
`low_repeatability_months`.

Тонкость: поле `symbol` имеет значение по умолчанию `"BTCUSDT"`, поэтому payload
без него молча становился биткоином. Проверка идёт по `model_fields_set` —
множеству реально пришедших полей.

### Фильтр батча

Три операции по порядку:

**Порог.** `breakdown.total >= profile.batch.min_quality_score` — у каждой монеты
свой. Явное число в вызове перекрывает профили для всего батча; это режим разовых
экспериментов, а не регулярной работы.

**Лучший в семье.**

```python
def _family_rank(candidate, quality_score, profiles):
    bonus = fresh_bonus if candidate.context_status == fresh else 0.0
    return quality_score + bonus
```

Надбавка за свежесть (0.05) — **не абсолютный приоритет**: заметно более сильный
`stale` не должен проигрывать слабому `fresh`.

Ключ группировки — пара `(symbol, candidate_family_key)`.

> ⚠️ **Ломается молча.** Без символа в ключе «семья 1.0|42->1|…» у BTC и ETH одна
> и та же, и одна монета гасит другую.

**Конфликты.** Четыре типа:

| Тип | Условие |
|---|---|
| `contradictory_direction` | один переход одной монеты, разные стороны |
| `stale_and_old_context` | `stale` и возраст > 120 мин одновременно |
| `false_confidence` | высокий `research_score` при низкой доле валидных меток |
| `seasonal_concentration` | `monthly_concentration` выше порога профиля |

Группировка по `(symbol, transition_id)` обязательна: «42→1» в графе BTC и в
графе ETH — разные переходы, и разное направление по ним не противоречие.

## 11.13. Объяснение

Два взаимозаменяемых пути, дающих одинаковые числа и разные тексты.

**Детерминированный** (`agent/deterministic.py`) — набор if-правил, собирающих
`strengths` и `risks`. Пороги формулировок берутся **из ступеней профиля**, а не
из литералов:

```python
if candidate.research_score > research_ladder.step(0):
    strengths.append(f"Очень высокий research_score ({candidate.research_score:.3f})")
elif candidate.research_score > research_ladder.step(-1):
    strengths.append(f"Хороший research_score ({candidate.research_score:.3f})")
```

`step(i)` возвращает порог ступени по индексу с зажимом в границы: «очень
высокий» — это верхняя ступень **той монеты**, о которой идёт речь, а не литерал
0.85. Иначе текст про альткоин описывал бы линейку биткоина.

**LLM** (`agent/llm_node.py`) — Claude получает готовые числа и пишет
`strengths` / `risks` / `summary` в JSON. Системный промпт параметризован
монетой и подсказкой из её профиля (`llm.market_hint`):

> «Ты аналитик кандидатов BTC» на кандидате по ETH — не мелочь: модель начинает
> рассуждать о ликвидности и глубине истории не того рынка.

В промпте явно проговорены три вещи, которые модель иначе переврала бы:
`research_score` — не вероятность прибыли; кандидат — идея, а не сигнал;
`quality_score` посчитан профилем такой-то монеты и межмонетно несравним.

Плюс два условных предупреждения: про `sample_scope = transition` (иначе LLM
запишет «редкий блок событий» в сильные стороны) и про неприменимость F/A ratio
к short без short-версии.

При сбое API — fallback на детерминированный путь. Ключевой инвариант: **LLM
ничего не решает**.

## 11.14. Резюме главы

Оценка — детерминированная взвешенная сумма четырёх осей, полностью вынесенная в
конфигурацию. Код описывает форму формулы, YAML — все числа.

Три защиты от тихого разъезда линеек: `_default` заморожен снапшот-тестом,
каждая запись помечена версией и отпечатком профиля, монета не заводится без
sanity-якоря.

Две поправки последнего времени сделали оценку строже: эффективный размер
выборки вместо строк снимков и запрет начислять за редкость блока при откате
выборки. Обе уменьшили `quality_score` — потому что до них система считала себя
увереннее, чем имела право.

Следующая глава — про то, как система проверяет саму себя, и почему эта проверка
дала отрицательный ответ.
