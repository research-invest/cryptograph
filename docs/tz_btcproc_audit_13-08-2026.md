> «конфигурация предсказывает направление», пока оно не подтверждено новым

### A1. 🔴 `abs(mae)` превращает отсутствие просадки в просадку

> **✅ Сделано 13.08.** Правка внесена и верна — но замер показал, что её
> эффект на выдаче **строго нулевой** (ни один из 56 193 long-кандидатов не
> изменился). Предсказанные ниже последствия не материализовались; разбор
> причины — proc 29.1. Читать этот пункт как «дефект был, цена оказалась
> нулевой при нынешних перцентилях и горизонте».

**Файл:** `btcproc/candidates/builder.py`, строка 68.

```python
if ret > 0:
    self.up += 1
    bisect.insort(self.mfe_up, float(mfe))
    bisect.insort(self.mae_up, abs(float(mae)))   # ← здесь
```

`mae_pct` считается в `btcproc/candidates/outcomes.py` как

```python
mae[:last] = (low_windows[1:last + 1].min(axis=1) / entry - 1.0) * 100.0
```

то есть это **минимум low за горизонт относительно цены входа**. Если за 24
часа цена ни разу не сходила ниже цены входа, `mae_pct` получается
**положительным**.

Проверка арифметики: `entry = 100`, минимальный low за окно = `101` →
`mae_pct = +1.0` → `abs(+1.0) = 1.0` → в список неблагоприятных экскурсий
записывается **1.0% просадки, которой не было**.

Последствия, по нарастанию:

1. Значение искажается не случайно, а **инвертированно**: чем сильнее и чище
   был рост без отката, тем больше записанная «просадка».
2. Список `mae_up` наполняется только по случаям `ret > 0` — то есть ровно по
   тем, где вероятность `mae_pct > 0` максимальна. Загрязнение бьёт в самую
   плотную часть выборки.
3. `p80_long_adverse_pct` = `_percentile_sorted(acc.mae_up, 80)` завышается.
4. `long_favorable_adverse_ratio_p70_p80 = favorable / adverse` занижается.
5. Поле уходит в agent и попадает в ось B скоринга:
   `agent/src/scorer/candidate_scorer.py::_score_directional` → `_ladder(ratio, spec.fa_ratio)`,
   одна из трёх составляющих оси directional для long-кандидатов, вес оси —
   из профиля монеты.

**Исправление:**

```python
bisect.insort(self.mae_up, max(0.0, -float(mae)))
```

Семантика после правки: «просадка 0%» означает «цена ни разу не была ниже
входа» — это корректное и информативное значение, а не отсутствующее.

**Что замерить до и после (обязательно):** долю случаев `ret > 0 and mae_pct > 0`
по всей истории каждой монеты, и сдвиг `p80_long_adverse_pct` и
`long_favorable_adverse_ratio_p70_p80` в медиане и в квартилях. Без замера
масштаб эффекта неизвестен — я его оценить не могу, данных на руках нет.

**Регрессия:** `tests/test_candidates.py` — синтетическая серия, где цена
монотонно растёт весь горизонт; ожидание `p80_long_adverse_pct == 0.0`.
Сейчас этот тест провалится на текущем коде — это и есть подтверждение бага.

### A2. 🔴 `sample_size` завышен до 4× и уходит наружу как есть

> **✅ Сделано 13.08.** Заведено `effective_sample_size`, порог применяется к
> нему, ступень оси A в профилях переведена на него отдельной необязательной
> лесенкой. Уточнение по факту: завышение **2.2× по медиане, а не 4×**
> (proc 29.2, agent 5.2 и 6.2).

**Файлы:** `btcproc/candidates/builder.py` (`SNAPSHOT_OFFSETS_MIN`, `generate`),
`agent/src/scorer/candidate_scorer.py::_score_statistical`.

`SNAPSHOT_OFFSETS_MIN = (0, 45, 90, 180)` даёт до **четырёх строк снимка на одну
реализацию перехода**. В `generate()` каждая такая строка кладётся в
аккумулятор:

```python
by_full.setdefault(key, Accumulator()).add(...)
by_transition.setdefault(done["transition_id"], Accumulator()).add(...)
```

Значит `acc.total` — это число **строк**, а не число независимых событий.

Хуже того, эти четыре строки почти не несут новой информации: горизонт 24h =
1440 минут, максимальный офсет 180 минут, то есть окна исходов снимков одной
реализации перекрываются минимум на **87.5%**.

Зависимость наблюдений **уже осознана и починена в измерителях** — раздел 21.1
лога, блочный бутстрап в `analysis/lift.py` и `analysis/holdout.py`. Но
**в самом поле кандидата она не починена**, а поле — это внешний контракт:

* `agent/src/scorer/candidate_scorer.py::_score_statistical` строит по
  `sample_size` ступенчатую шкалу (одна из четырёх составляющих оси A);
* `btcproc/candidates/builder.py::research_score` берёт
  `s_sample = min(1.0, log10(acc.total + 1) / 3.0)` — то есть «1000 случаев → 1.0»
  на деле означает «250 реализаций → 1.0»;
* `CAND_MIN_SAMPLE_SIZE = 30` фактически означает порог в **~8 реализаций**.

**Исправление — два поля, а не одно.** Ломать `sample_size` нельзя: на нём
откалиброваны профили `agent/config/symbols/*.yaml`. Поэтому:

1. Добавить в `Accumulator` счётчик уникальных реализаций. Ключ реализации —
   `state_seq` снимка (он уже есть в `states`, надо протащить в `snapshots`):

   ```python
   realizations: set = field(default_factory=set)
   # в add(): self.realizations.add(state_seq)
   ```

2. Новое поле кандидата `effective_sample_size = len(acc.realizations)`.
3. `research_score`: `s_sample` считать по `effective_sample_size`.
4. `CAND_MIN_SAMPLE_SIZE` применять к `effective_sample_size`, а старое
   значение оставить как отдельный, более мягкий порог по `sample_size`.
5. В agent: добавить поле в `src/models/candidate.py` (Optional, дефолт None —
   чтобы старые выгрузки не ломали валидатор), и перевести ступень
   `statistical.sample_size` на него после перекалибровки профилей.

**Важно:** это **не** сделает систему предсказательной. Это уберёт из неё
конкретное завышение, из-за которого «выборка в тысячу случаев» на самом деле
означала «две с половиной сотни».

### A3. 🟠 Fallback-кандидат несёт признаки блока, которого нет в его статистике

> **✅ Сделано 13.08.** `sample_scope` уехал в тело кандидата, ось rarity при
> откате считается по двум критериям. Масштаб по замеру — 72–100% выдачи
> (proc 29.3, agent 5.1). Альтернатива «выключить `CAND_FALLBACK_TRANSITION`»
> не принята: числа для решения есть (выдача усохнет в 4–8 раз, у HYPEUSDT
> обнулится), но само решение про цель системы и ждёт шага 7.

**Файл:** `btcproc/candidates/builder.py::generate` и `_assemble`.

Когда по паре `(переход, блок событий)` не набралось `min_sample_size`,
происходит откат:

```python
acc = by_transition.get(row["transition_id"])
scope = "transition"
```

Но в `_assemble` дальше **безусловно** проставляются:

```python
"event_block_id":         row["event_block_id"],
"event_rarity_bucket":    e_rarity,          # из block_meta по этому блоку
"event_block_total_rows": int(block.get("total_rows", acc.total)),
"event_block_row_share":  float(block.get("row_share", 0.0)),
"primary_event_family":   ...,
"signature_atom_count":   ...,
```

и `research_score` получает `e_rarity` весом 0.10.

То есть кандидат утверждает «редкий блок событий», хотя его историческая
статистика на блок **не обусловлена вообще**. В agent
`_score_rarity` читает `event_rarity_bucket` как одну из трёх составляющих оси D.

Масштаб: по README доля `transition+event_block` — 29.3% (BTC), 32.1% (ETH),
19.0% (SOL). То есть **у 68–81% кандидатов** признаки блока и статистика
относятся к разным вещам. Для HYPEUSDT в разделе 27.5 лога зафиксирован
случай `transition+event_block = 0` — там это 100%.

`_meta.scope` эту разницу фиксирует, но `strip_meta()` вырезает `_meta` перед
отправкой, и agent о ней не знает.

**Исправление:**

1. Вынести `scope` из `_meta` в тело кандидата (поле `sample_scope`,
   enum `transition+event_block` | `transition`).
2. В `agent/src/models/candidate.py` добавить поле (Optional).
3. В `agent/src/scorer/candidate_scorer.py::_score_rarity` при
   `sample_scope == "transition"` **не начислять** баллы за
   `event_rarity_bucket` (делить на 2 составляющие, как уже сделано для
   short в `_score_directional`).
4. В `research_score` при откате использовать `e_rarity = "common"`.

**Альтернатива, которую стоит рассмотреть отдельно:** вообще отключить
`CAND_FALLBACK_TRANSITION`. Он был введён, чтобы кандидаты не иссякали, но
после раздела 26 «чтобы кандидаты были» перестало быть целью. Замерить долю
выдачи и посмотреть, что останется.

### A4. 🟠 Порог перекоса не согласован с порогом bias, а тот входит в family_key

> **✅ Сделано 13.08.** Выбран первый вариант — сторона добавлена в ключ

min_abs_skew:        0.06   # ниже — кандидата нет

Для кандидатов с `|skew| ∈ [0.06, 0.10)`:

* `research_side` = `long` или `short` (определяется знаком),
* `historical_bias_context` = `neutral`,
* `candidate_family_key` = `{symbol}|{group}|{transition}|{block}|neutral`.

То есть long-кандидат и short-кандидат по одной конфигурации попадают в **одну
семью** и конкурируют в `select_best_per_family` agent'а, где выживает один.
Направление при этом выбирается не по силе, а по свежести/качеству.

Полоса `[0.06, 0.10)` — не маргинальная: по разделу 26.5 медиана `sample_size`
173, и `CAND_MIN_ABS_SKEW = 0.06` при такой выборке — это 0.79 SE.

**Исправление:** либо включить `research_side` в `candidate_family_key`, либо
свести оба порога к одной величине. Первое предпочтительнее — конфликт
направлений и так детектируется отдельно в
`agent/src/filters/candidate_filter.py`.

### A5. 🟡 Сглаживание состояний переписывает прошлое — в live это лаг, а не look-ahead

> **⬜ Не начато.** Задача 9 порядка работ, после решения владельца (шаг 7).

**Файл:** `btcproc/states/assign.py::smooth_labels`.

```python
if i - pending_start + 1 >= min_run:
    current = value
    out[pending_start:i] = value   # ← задним числом
```

Метка бара `t` определяется барами `t … t + min_run − 1`. При
`STATES_SMOOTHING_BARS = 2` это один лишний бар = 15 минут.

**Это не ошибка расчёта** — история размечается одинаково и в train, и в live,
статистика внутренне согласована. Но семантика поля `_meta.ts` вводит в
заблуждение: кандидат помечен временем `t`, а физически он мог быть выпущен
не раньше закрытия бара `t + 1`. Исход же меряется от `close[t]`.

Для описательного инструмента это неважно. Для любого утверждения о
достижимости — важно. Поэтому:

**Исправление:** добавить в кандидата поле `decision_ts` = время, начиная с
которого конфигурация была фактически известна
(`ts + (smoothing_bars − 1) × base_minutes`), и использовать **его** во всех
замерах достижимости. `_meta.ts` оставить как есть — это время конфигурации.

### A6. 🟡 `rarity_by_quantiles` на дискретных счётчиках даёт не треть

> **⬜ Не начато.** Задача 9. Делать в один заход с пересборкой контура:
> правка меняет `transition_rarity`, то есть требует новой выгрузки и
> перепроверки селективности профилей.

**Файл:** `btcproc/states/graph.py::rarity_by_quantiles`.

```python
q_rare = counts.quantile(0.33)
np.select([counts <= q_rare, counts <= q_uncommon], ["rare", "uncommon"], "common")
```

Распределение `count` по переходам сильно скошено, и одиночных переходов
(`count == 1`) обычно много. Если `q_rare == 1`, то условие `counts <= 1`
захватывает **все** одиночные переходы — их может быть сильно больше трети.
Обещание докстринга («треть самых редких») не выполняется.

Не ломает ничего, но делает `transition_rarity` менее информативным, чем
заявлено. **Исправление:** использовать `counts.rank(pct=True, method="average")`
вместо сравнения со значением квантиля — ранг корректно делит связки.
Регрессия: синтетический вход, где 60% переходов имеют `count == 1`; проверить,
что доля `rare` близка к 0.33, а не к 0.60.

## 2. Что в коде сделано хорошо (не трогать)

Это не комплименты, это список инвариантов, которые легко сломать по неведению:

1. **`_separation` через d-prime**, а не через радиус группы (`clustering.py`).
   Радиус растёт как √d; замена схлопнет граф в 3–4 узла. Обосновано в README 3.2.
2. **`_split_gain` — полный gap statistic с порогом в сигмах референса**
   (`clustering.py`). Абсолютный порог зависит от размерности, из-за чего
   двенадцать признаков **любой природы, включая чистый шум**, обрушивали граф
   43 → 22. Регрессия: `test_split_gain_is_independent_of_dimensionality`.
3. **Разделение `SIGNATURE_ATOMS` / `CONTEXT_ATOMS`** (`events.py`). Без него
   16 000 блоков на 76 000 баров, выборка по полному ключу не набирается никогда.
4. **`shift(1)` для старших ТФ** (`features/builder.py::_context_features`).
   Регрессия: `test_features_do_not_look_ahead`.
5. **Созревание исходов в `generate()`** — накопитель пополняется только тем,
   чей горизонт закрылся до `ts` текущего снимка. Регрессия:
   `test_candidate_sample_uses_only_matured_past`.
6. **Символ в `configuration_hash`, `candidate_family_key`, `candidate_id`.**
   Без него дедуп agent'а вернёт ETH готовую оценку BTC, и по данным это не
   диагностируется. Регрессия: `tests/test_multi_symbol.py`.
7. **Блочный бутстрап как единственный способ считать значимость**
   (`analysis/lift.py`, `analysis/holdout.py`). Наивный биномиальный интервал
   занижен примерно втрое. Раздел 21.1 и 26.1 лога.
8. **`pgvector` / `neo4j` проверяются до отправки** (`tests/test_sink_deps.py`).
   Иначе «сохранён частично» молча теряет оценки.
9. **`train` не запускается «для обновления»** — `group_id` перенумеровываются.
10. **`SINK_MIN_QUALITY = None` по умолчанию** — профильные пороги монет
    применяются, а не глушатся нулём.

## 3. Блок C: смена предмета предсказания

конкретизация первого, с обоснованием, почему именно он.

### C0. Почему направление не предсказывалось, а размах может

Направление доходности на горизонте 24h — величина с автокорреляцией, близкой
к нулю по построению рынка. Волатильность — нет: кластеризация волатильности
(периоды высокой волатильности следуют за периодами высокой волатильности) —
одно из самых устойчивых эмпирических свойств финансовых рядов, на нём
построено всё семейство ARCH/GARCH-моделей.

Практический смысл: предсказание размаха и асимметрии MFE/MAE, даже при нулевом
направленном преимуществе, напрямую применимо — размер позиции, размещение
стопа, выбор между покупкой и продажей опциональности. Утверждение «в этом
режиме 24-часовой размах обычно 3.1%, а не привычные 1.8%» проверяемо и
полезно, тогда как «в этом режиме 62% вверх» — не воспроизвелось.

**Важно:** тезис «волатильность прогнозируема лучше знака» — общее свойство
рынков, а не измерение на этих данных. Он объясняет, почему стоит попробовать,
но **не** предсказывает результат для конкретно этого графа состояний. Замер
обязателен.

### C1. Задача: `outcomes.py` — новые целевые величины

Добавить к `ret_pct / mfe_pct / mae_pct` на том же горизонте:

| Величина | Определение | Зачем |
|---|---|---|
| `range_pct` | `(max(high) − min(low)) / entry × 100` | размах |
| `rv_fwd` | realized vol по 96 барам вперёд | режим волатильности |
| `mfe_mae_asym` | `(mfe + mae) / (mfe − mae)` | асимметрия пути, знаковая, но не про знак ret |
| `range_ratio` | `range_pct / ATR-based ожидание на входе` | размах **относительно текущего** — стационарная величина |

`range_ratio` — ключевая. Абсолютный размах нестационарен (2018 и 2024 не
сравнимы), а отношение к текущему уровню волатильности — сравнимо.

### C2. Задача: `candidates/builder.py` — второй тип кандидата

Не ломая существующий: `Accumulator` копит распределение `range_ratio`
(перцентили p25/p50/p75/p90). Новый набор полей:

```
expected_range_ratio_p50
expected_range_ratio_p90
range_regime          # "compressed" | "normal" | "expanded"
range_lift            # p50 конфигурации / p50 базовой частоты за тот же период
```

`range_lift` — обязательно относительная величина, ровно по уроку раздела 26.4:
абсолютное число неотличимо от дрейфа, разница с бенчмарком — отличима.

### C3. Задача: holdout для нового предмета

Переиспользовать `analysis/holdout.py`, заменив бинарную метрику:

* вместо directional accuracy — **Spearman-корреляция** предсказанного
  `expected_range_ratio_p50` с фактическим `range_ratio` на holdout;
* бенчмарк — не «всегда long», а **безусловная скользящая оценка волатильности**
  (простейшая: `rv` последних 96 баров). Ровно та же логика парного сравнения;
* значимость — блочный бутстрап, `block_length_rows`, общий код с `lift.py`
  (инвариант 11, не копировать!);
* калибровка — предсказанный перцентиль против фактического, ECE.

**Критерий заявляется ДО запуска** (как было сделано для Ш0, и это правильно):

> Spearman-корреляция значимо выше нуля по блочному бутстрапу **И**
> парное сравнение с бенчмарком «скользящая rv» значимо положительно,
> на двух монетах из трёх и на двух разных зёрнах кластеризации.

Если критерий не пройден — фиксировать это в логе так же прямо, как раздел 26,

## 8. Что явно НЕ делать

* Не подбирать пороги (`split_gain_sigma`, `merge_separation`,
  `CAND_MIN_ABS_SKEW`) под красивое число состояний или под красивую accuracy.
  Раздел 21.17 показал, что критерий калибровки сам мерил шум.
* Не включать `SMC_FEATURES_ENABLED` без перекалибровки порогов дробления.
