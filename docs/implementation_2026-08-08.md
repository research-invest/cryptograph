# Мультимонетность: отчёт о реализации

**Дата:** 2026-08-08. **Проекты:** btc-graph (приёмник) и btc-graph-processing (генератор).

Реализованы две задачи целиком:

* [`btc-graph/docs/step_04_multi_symbol.md`](../btc-graph/docs/step_04_multi_symbol.md) —
  профили оценки на символ, изоляция данных;
* [`btc-graph-processing/docs/task_multi_symbol.md`](../btc-graph-processing/docs/task_multi_symbol.md) —
  реестр монет, помонетные прогоны, админка.

В работе три монеты: **BTCUSDT, ETHUSDT, SOLUSDT**, у каждой свой откалиброванный
профиль оценки. Тесты: 282 (btc-graph) и 76 (btcproc, в обоих интерпретаторах).
Миграции прогнаны на живом стеке.

## 2. Три вещи, которые стоит знать про результат

### 2.1. Базовая линейка оказалась слишком МЯГКОЙ — и для альткоинов, и для BTC

Обе задачи строились на гипотезе «альткоину тесно в биткоиновой линейке:
выборки мелкие, всё уедет в WEAK». Вышло наоборот, причём у всех трёх монет.

Ось `statistical` насыщалась везде: BTC 0.822 (σ 0.143), ETH 0.827 (σ 0.121),
SOL 0.736 (σ 0.137) — почти все кандидаты у потолка, ось перестала различать.
Причина в накоплении: ступень `sample_size > 1000` ставилась под эталонный
кандидат ТЗ с выборкой 1339, а за девять лет истории типичная выборка выросла
кратно. Калибровка вернула оси разрешающую способность у всех: ~0.496 при
разбросе ~0.22.

**Следствие: `_default` сменил роль.** Он больше не «калибровка под BTC» —
у биткоина теперь свой профиль, как у остальных. `_default` стал неподвижной
общей меркой: по нему считается `quality_score_baseline`, и по нему же
оцениваются монеты без профиля. Его не калибруют, иначе обесценятся все
накопленные baseline разом.

**Правило для будущих монет: направление, в которое нужно двигать ступени,
заранее неизвестно. Проверять фактом, а не ожиданием.**

### 2.2. Имена состояний нельзя задавать руками

`train` перенумеровывает состояния с нуля при каждом прогоне. Рукописное
«состояние 7 = тихий боковик» протухло бы при первом переобучении — причём
молча: номер остался бы, а рынок под ним стал бы другим.

Поэтому имя выводится из отклонений признаков самого состояния и хранится
per `(run_id, group_id)`. Проверка: один и тот же `group_id` в прогонах #4 и
#12 (обе BTCUSDT) имеет разные имена. При выкладке на другой контур мигрировать
нечего — туда едет только словарь «признак → формулировка».

### 2.3. Профильный `quality_score` между монетами не сравним

Это свойство конструкции, а не недоделка. Рядом всегда считается
`quality_score_baseline` — тот же кандидат по базовой калибровке, и только он
сравним между монетами. Границы рейтинга при этом выровнены по селективности
эталона (~1% STRONG у всех монет), чтобы сводный список «что сегодня сильного»
не заливала монета с самой низкой планкой.

## 3. Что сделано в btc-graph

### Профили калибровки

Пороги ушли из кода в `config/symbols/*.yaml`. `candidate_scorer.py` описывает
только форму формулы — какие признаки в какую ось и как оси складываются.

* `src/config/profiles.py` — Pydantic-схема, ленивая загрузка, слияние с
  `_default`, fingerprint, кэш, `reload_profiles()`.
* Валидация схемы ловит: сумму весов ≠ 1, немонотонную лесенку, **недостижимую
  верхнюю ступень доли**, непокрытые значения enum, `strong_min ≤ moderate_min`.
* `WEIGHTS`, `RATING_STRONG_MIN`, `_AGE_SCORE`, `FRESH_BONUS` остались
  deprecated read-only проекциями `_default` через модульный `__getattr__`.
* Профиль резолвится один раз на кандидата в начале pipeline и прокидывается
  во все узлы: иначе `POST /config/reload` посреди батча дал бы оценку, где
  score посчитан одной калибровкой, а rating и тексты — другой.

### Изоляция данных по монетам

Ошибки здесь не падают, а молча портят данные, поэтому проверялись отдельно.

| Хранилище | Ключ | Что было бы без изоляции |
|---|---|---|
| Neo4j | `MarketGroup {symbol, group_id}` + constraint | «Группа 1.0» BTC и ETH схлопнулись бы в один узел, `avg_quality_score` усреднился по разным рынкам |
| Redis dedup | `{symbol}:candidate:hash:*` | ETH получил бы готовую оценку BTC при совпадении хэша |
| PostgreSQL | PK `(symbol, candidate_id)` | Upsert перезаписал бы строку чужой монеты |
| Continuous aggregates | `symbol` + `scoring_profile` в `GROUP BY` | Средние по всем монетам и калибровкам сразу |
| Фильтры | `(symbol, family_key)`, `(symbol, transition_id)` | Одна монета гасила бы кандидатов другой; ложные конфликты направлений |

Не изолирован намеренно только вектор pgvector — он symbol-agnostic, чтобы
можно было спросить «а у BTC такая конфигурация была?» (`?cross_symbol=`).

### API

`?symbol=` обязателен там, где выдача привязана к графу монеты
(`/candidates/strong`, `/graph/*`), опционален в `/stats/*`. Добавлены
`/config/symbols`, `/config/symbols/{symbol}`, `POST /config/reload`
(за `ENABLE_CONFIG_RELOAD`, по умолчанию выключен), `/graph/symbols`,
`/stats/symbols`.

### Инструменты

* `scripts/make_scorer_snapshot.py` + `tests/test_scorer_snapshot.py` —
  200 кандидатов, снятых **до** рефакторинга. Сторожит базовую линейку
  `_default`, по которой считается `quality_score_baseline` у всех монет.
* `tests/fixtures/profiles/` — замороженные профили для тестов механики.
  Без этой развязки любая перекалибровка роняет десятки тестов, не имеющих
  к калибровке отношения: калибровка BTCUSDT@2 уронила 66 случаев.
* `scripts/calibrate_profile.py` — черновик профиля по выгрузке, отчёт
  с диагнозами, holdout, `--tail`, `--target-strong`.
* `scripts/migrate_graph_symbol.cypher` — перевод накопленного графа.
* `alembic/versions/004_multi_symbol.py` — составные PK, новые колонки,
  пересоздание CAGG.

## 4. Что сделано в btc-graph-processing

* `btcproc/symbols.py` — реестр монет: дата листинга, `states_overrides`,
  `enabled`. Список в коде, а не в окружении: это знание о рынке, оно должно
  версионироваться и ревьюиться в диффе.
* **Символ в `configuration_hash` и `candidate_family_key`** — самая тихая
  из возможных поломок, разобрана в разделе 5.
* Относительный порог дробления `min_group_share`.
* `runs.symbol` + помонетные выборки; `live` берёт модель своей монеты.
* CLI `--symbol` / `--all`, пакетный режим с продолжением после ошибки
  и ненулевым exit code.
* Админка: селектор монеты сквозь все страницы, лимит одновременных прогонов
  вместо глухой блокировки, 422 при рассогласовании монеты и прогона.
* Имена состояний (`states/naming.py`) — сверх задачи.

## 5. Дефекты, найденные по ходу

Ни один не был бы найден на синтетике: восемь вылезли на реальных данных,
три — при работе с живым интерфейсом и при первой же перекалибровке.

| # | Дефект | Почему опасен | Где разобран |
|---|---|---|---|
| 1 | Калибратор предлагал ступень с порогом `1.0` для доли | Сравнение строгое, доля больше единицы не бывает — верхний балл не взял бы никто, потолок критерия молча упал бы до 0.4. Монотонность это не ловит | `btc-graph/docs/audit_findings.md`, №21 |
| 2 | `--holdout` проверял не то, что обещал | Делит по порядку строк, а выгрузка шла без `ORDER BY ts`. В схеме кандидата нет поля времени, отсортировать вход скрипт не может — требование было частью контракта и не было записано | там же, №22 |
| 3 | Профиль калибровался по всей истории | `sample_size` растёт со временем; планка вставала туда, где сидели бедные ранние годы. 10% STRONG на калибровке против 26% на свежих данных | там же, №23 |
| 4 | Целевая селективность ни к чему не привязана | 10% STRONG против биткоиновых 1.0% — ETH залил бы сводный список | там же, №24 |
| 5 | `BTC_GRAPH_PATH` указывал в несуществующий каталог | `SINK_MODE=direct` падал, а тест контракта схемы между проектами **молча скипался** | `btc-graph-processing/docs/development_log.md`, 11.6 |
| 6 | Метки узлов Neo4j после бэкфилла остались в старом формате | В одном графе оказались бы `group_1` и `BTCUSDT:group_1` — там, где монету и надо различать | `btc-graph/docs/audit_findings.md`, прогон шага 4 |
| 7 | Профиль наследовал `description` от `_default` | `ETHUSDT@1` показывал себя как «базовую калибровку под BTCUSDT» — реестр дезинформировал | там же |
| 8 | `emit` не печатал прогресс | На очереди в 34 тысячи это час тишины, неотличимый от зависшей команды | `task_multi_symbol.md`, раздел 19 |
| 9 | Тесты механики зависели от боевой калибровки | Калибровка BTCUSDT@2 уронила 66 случаев, из которых к калибровке относились два. Калибровка — штатное повторяющееся событие; сюита, падающая на каждой, перестаёт быть сигналом | `btc-graph/docs/audit_findings.md`, №25 |
| 10 | Подпись имени на графе была невидима на светлой теме | Красилась в `--node-label` (белый — он для текста поверх заливки узла), контраст 1.08:1 | `development_log.md`, 12.3 |
| 11 | Порог подписей на графике считался из неверной посылки | «Всего баров / целевое число» верно только при равных отрезках; выходило 5 подписей вместо 40 | там же, 12.2 |

## 9. Дополнено: переобучение BTC и его калибровка (2026-08-08, вечер)

BTC переобучен на полной истории (прогон #17) и получил собственный профиль
`BTCUSDT@2`. До этого его «последним train» числился короткий прогон #12
(с 2025-08, 35 тыс. баров, 20 состояний при 0.6% полного scope), а профиль был
пустым наследованием от `_default`.

**Результат переобучения воспроизвёл прежнюю модель:** 43 состояния, 602 ребра,
27.9% полного scope против 43 / 631 / 29.3% у прогона #4. Значит, переход на
относительный порог дробления эталонный граф не сдвинул.

**Калибровка вскрыла то же, что у альткоинов:** ось `statistical` у BTC была
насыщена базовой линейкой (0.822 при разбросе 0.143). Поднятые ступени
`sample_size` (2342/904/201 против 1000/500/200) вернули ей различающую
способность: 0.496 при разбросе 0.224. Распределение рейтингов почти не
поехало: 0.8% STRONG было, 1.0% стало.

### Что из этого следует для чтения документации

Эталонный кандидат из ТЗ по профилю BTCUSDT@2 получает **MODERATE (0.6133)**
вместо прежнего STRONG (0.7783). По базовой линейке он по-прежнему 0.7783 —
это и есть его `quality_score_baseline`, и снапшот-тест этого не отпустит.

Причина не в том, что кандидат «испортился», а в том, что он перестал быть
представителем: его выборка (1339) и сезонная концентрация (10.0%) были
выдающимися для калибровки шага 1, а на девятилетней истории p50 концентрации
равен 6.3%. Раздел 8 README обновлён и объясняет расхождение двух чисел.

### Побочный эффект, который стоило поймать раньше

Калибровка BTC уронила **66 тестовых случаев** — куда больше, чем я
предупреждал («снапшот и якорь»). Причина структурная: почти вся сюита звала
скорер без явного профиля, а он резолвится по символу кандидата. Пока боевой
BTCUSDT был пустым наследованием, тесты ступеней `_default` проходили
по совпадению.

Починено не подгонкой ожиданий, а развязкой: тесты механики считают по
замороженным профилям из `tests/fixtures/profiles`, боевые отдаёт фикстура
`shipped_profiles` тем немногим тестам, которым нужна поставляемая правда
(снапшот, sanity-якоря, реестр). Калибровка по правилу 6 — штатное
повторяющееся событие, и сюита обязана его переживать.

## 10. Дополнено: читаемость интерфейса (2026-08-08, вечер)

Не было ни в одной из задач; сделано по ходу, когда стало видно, что цветом
десятки состояний не различить.

* **Имена состояний** — выводятся из отклонений признаков, хранятся
  в `market_groups.name`. Подробности и отвергнутая альтернатива —
  `btc-graph-processing/docs/development_log.md`, раздел 12.
* **Подсказка на графике** — одна строка фиксированной высоты: цвет, номер,
  имя, переход. Многострочная дёргалась под курсором, потому что строка
  перехода есть не у каждого бара.
* **Номера состояний на графике** — на первом баре отрезка, порог длины
  берётся из фактического распределения (около 40 подписей на любом масштабе).
  Первая версия считала порог как «всего баров / целевое число подписей»
  и давала 5 подписей вместо 40: отрезки сильно разной длины.
* **Контраст подписей на графе** — внешняя подпись красилась в `--node-label`
  (белый, он для текста поверх заливки узла) и на светлой теме давала
  контраст **1.08:1**, то есть надписи не было видно. Стало 16.17:1.
  Номер внутри узла на сером фоне был 2.93:1 при норме 4.5 — добавлена
  тёмная обводка глифа.
* **Страница `/help`** — шпаргалка для оператора в самой админке: принципы,
  словарь, рейтинги, ежедневный чек-лист, чего делать нельзя. Не заменяет
  `operator_guide.md`, а избавляет от похода в репозиторий за мелочью.
