## 2. P0-1: замер лифта считает зависимые наблюдения независимыми

### 2.1. Что не так

`btcproc/analysis/lift.py::two_proportion_z` — стандартный двухвыборочный z-тест:

```
SE = √( p_pool · (1 − p_pool) · (1/n₁ + 1/n₂) )
```

Эта формула верна **только для независимых наблюдений**. У нас они зависимы дважды:

**Перекрытие горизонтов.** `HORIZON = 24h`, `BASE_TF = 15m` → горизонт равен **96 барам**. Два кандидата, отстоящие друг от друга меньше чем на 96 баров, имеют почти один и тот же `is_up`: их окна исходов перекрываются.

**Снимки офсетов.** `SNAPSHOT_OFFSETS_MIN = (0, 45, 90, 180)` — одна реализация перехода даёт до 4 кандидатов в пределах 12 баров. Их исходы перекрываются на 87–100%.

### 2.2. Насколько велика ошибка

По фактическим числам BTC:

```
баров:                          314 141
кандидатов одной модели:         28 818
доля баров с кандидатом:  28818/314141 = 9.2%
средний интервал:         314141/28818 = 10.9 бара
горизонт:                                96 баров
──────────────────────────────────────────────────
кандидатов на одно независимое окно:  96/10.9 ≈ 8.8
```

Design effect для кластеризованных наблюдений: `DEFF = 1 + (m̄ − 1)·ρ`, где `m̄` — средний размер кластера, `ρ` — внутрикластерная корреляция. У нас `ρ` близка к 1 (соседние бары в пределах горизонта дают почти одинаковый исход), значит `DEFF ≈ m̄ ≈ 8.8`.

Стандартная ошибка входит под корнем:

```
SE_истинная / SE_наивная = √8.8 ≈ 2.97
z_истинный ≈ z_наивный / 2.97
```

Оценка снизу: офсеты концентрируют кандидатов вокруг переходов, поэтому реальный `m̄` больше равномерного. `DEFF = 8.8` — оптимистичная граница.

**Следствие для уже полученных выводов.** Порог BH при 25 тестах требует примерно `|z| ≥ 2.5…2.9`. Чтобы пережить деление на 2.97, наивный `z` должен был быть в районе 8–9. Такие значения при лифтах 2–5 п.п. недостижимы.

Прикидка детектируемости при честной независимости. `n_эфф = 314141/96 ≈ 3272`, разбиение 20/80, `p ≈ 0.5`:

```
n₁ = 654,  n₂ = 2618
SE = √( 0.25 × (1/654 + 1/2618) ) = √0.000478 = 0.0219
```

| Лифт | z | Проходит BH при 25 тестах |
|---|---|---|
| +0.030 | 1.37 | нет |
| +0.040 | 1.83 | нет |
| +0.054 | 2.47 | на грани |
| +0.080 | 3.65 | да |

То есть наблюдённые эффекты 2–5 п.п. лежат ровно на границе разрешающей способности. `bos_down` (+0.054 на BTC) — единственный, доходящий до неё.

### 2.3. Что важно: это не отменяет отрицательный результат

Асимметрия, которую надо понимать и не переусердствовать с починкой.

Завышенный `n` делает тест **анти-консервативным**: он находит эффекты, которых нет. Значит:

- вывод «зонная половина SMC (FVG, ордер-блоки, брейкеры, снятия) эффекта не дала» — **надёжен и после починки станет только надёжнее**. Если даже с завышенным втрое `z` они не прошли, они точно не пройдут;
- вывод «четыре структурных атома прошли» — **под вопросом** и требует перепроверки.

Починка не обесценивает работу. Она отделяет надёжную половину результата от ненадёжной.

### 2.4. Как чинить

Три варианта по возрастанию строгости. Делать **первый и второй**, третий — опционально.

**Вариант A: прореживание (sanity check, ~20 строк).**

Берём кандидатов через каждые `H` баров, где `H` — горизонт в барах. Получаем непересекающиеся окна. Повторяем для всех `H` фаз смещения и берём медиану `z`.

```python
def thinned_z(frame, atom, horizon_bars, bar_minutes):
    """Медиана z по всем фазам прореживания непересекающимися окнами."""
    step = pd.Timedelta(minutes=horizon_bars * bar_minutes)
    zs = []
    for phase in range(horizon_bars):
        start = frame["ts"].iloc[0] + pd.Timedelta(minutes=phase * bar_minutes)
        picked = _pick_one_per_window(frame, start, step)
        result = _measure_one(picked, atom, "atoms", "metric")
        if result:
            zs.append(result.z)
    return float(np.median(zs)) if zs else 0.0
```

Медиана, а не среднее: отдельные фазы могут попасть на вырожденные выборки.

Плюс: понятно и невозможно ошибиться. Минус: выбрасывает 99% данных, теряет мощность.

**Вариант B: stationary block bootstrap (основной, ~40 строк).**

Politis–Romano: блоки геометрической длины со средним `H`, склеиваются циклически до длины исходной выборки. Сохраняет всю выборку и корректно учитывает автокорреляцию.

```python
def block_bootstrap_p(frame, atom, horizon_bars, n_boot=2000, rng=None):
    """
    P-value через stationary block bootstrap.

    Средняя длина блока = горизонт: наблюдения внутри блока сохраняют
    свою зависимость, между блоками считаются независимыми.
    """
    rng = rng or np.random.default_rng(42)
    observed = _measure_one(frame, atom, "atoms", "metric")
    if observed is None:
        return 1.0

    n = len(frame)
    p_block = 1.0 / horizon_bars      # вероятность начать новый блок
    null_lifts = []
    for _ in range(n_boot):
        idx = _stationary_blocks(n, p_block, rng)
        resampled = frame.iloc[idx].reset_index(drop=True)
        # Нулевая гипотеза: перемешиваем метку атома блоками,
        # метрику оставляем на месте — рушим связь, сохраняя автокорреляцию.
        resampled["atoms"] = frame["atoms"].to_numpy()[idx[::-1]]
        result = _measure_one(resampled, atom, "atoms", "metric")
        if result:
            null_lifts.append(result.lift)

    null_lifts = np.array(null_lifts)
    return float((np.abs(null_lifts) >= abs(observed.lift)).mean())
```

Ключевая деталь: **перемешивать надо признак, а не метрику**, и перемешивать блоками. Обычный `shuffle` разрушит автокорреляцию и вернёт нас к наивному тесту.

`horizon_bars` брать из конфига: `config.data.horizon_minutes // config.data.base_minutes`, не хардкодить 96.

**Вариант C: кластерная SE по `(transition_id, event_block_id)`.**

Дополняет B, а не заменяет: B ловит временну́ю зависимость, C — зависимость через общий аккумулятор. Если делать только одно — делать B.

## 3. P0-2: `_split_gain` зависит от размерности и от одного случайного draw

### 3.1. Что не так

`btcproc/states/clustering.py`:

```python
real = silhouette_score(sample, labels)
low, high = sample.min(axis=0), sample.max(axis=0)
reference = rng.uniform(low, high, size=sample.shape)   # ОДИН draw
ref_labels = KMeans(...).fit_predict(reference)
ref = silhouette_score(reference, ref_labels)
return float(real - ref)                                # порог STATES_SPLIT_GAIN = 0.02
```

Это gap statistic Тибширани, реализованный наполовину: есть идея «сравнить с однородным облаком в том же боксе», но нет ни усреднения по референсам, ни нормировки порога на их разброс.

**Дефект 1: B = 1.** Силуэт случайного облака — случайная величина со своей дисперсией. Сравнение с одним draw при абсолютном пороге 0.02 означает, что решения о дроблении вблизи границы определяются шумом этого draw. `rng` засеян (`default_rng(42)`), поэтому на идентичных данных всё воспроизводимо — но лишняя неделя баров меняет подвыборку, меняет draw, и решения переворачиваются.

Это объясняет наблюдённую нестабильность:

| Источник | BTC | ETH | SOL |
|---|---|---|---|
| README | 43 | 29 | 32 |
| Продакшен | 36 | 26 | 34 |
| Локальный прогон | 43 | 42 | 32 |

ETH: 29 → 26 → 42. Разброс ±60% в числе состояний — это не «относительный порог двигается от длины истории», это детерминированный хаос вокруг границы решения.

**Дефект 2: порог абсолютный, разность силуэтов от размерности зависит.** В 44 измерениях концентрация расстояний сжимает и `real`, и `ref`, но неодинаково. Порог 0.02, откалиброванный на 32 измерениях, в 44 означает другую строгость.

Это подтверждено собственным замером с контролем:

| Монета | База, 32 | SMC, 44 | Контроль (шум), 44 |
|---|---|---|---|
| BTCUSDT | 43 | 31 | 22 |
| ETHUSDT | 42 | 24 | 12 |
| SOLUSDT | 32 | 24 | 20 |

Двенадцать признаков **любой природы** обрушивают граф. Это свойство калибровки, а не SMC — и оно повторится при ончейне, при индексах, при деривативах, при каждом источнике.

`_separation` (d-prime) в отличие от `_split_gain` уже нормирован по размерности намеренно — в его докстринге это прямо объяснено. То есть половина механизма спроектирована правильно, вторая половина нет.

### 3.2. Как чинить

Полная форма gap statistic:

```python
def _split_gain(x, rng, cfg) -> float:
    """
    Насколько разбиение надвое лучше, чем то же разбиение случайного облака.

    Референсов несколько, а порог выражен в их собственных сигмах, а не в
    абсолютных долях силуэта. Абсолютный порог зависит от размерности:
    в 44 измерениях концентрация расстояний сжимает силуэт, и константа,
    подобранная на 32, означает совсем другую строгость. Порог в сигмах
    самонормируется — ради этого свойства gap statistic и придуман.
    """
    sample = _subsample(x, cfg.silhouette_sample, rng)
    if len(sample) < 50:
        return -1.0

    labels = KMeans(n_clusters=2, n_init=3,
                    random_state=cfg.random_state).fit_predict(sample)
    if len(np.unique(labels)) < 2:
        return -1.0
    real = silhouette_score(sample, labels)

    low, high = sample.min(axis=0), sample.max(axis=0)
    refs = []
    for i in range(cfg.split_reference_draws):
        reference = rng.uniform(low, high, size=sample.shape)
        # n_init=1: референс однороден, множественные старты ему не нужны,
        # а B прогонов по 3 старта утроили бы стоимость дробления.
        ref_labels = KMeans(n_clusters=2, n_init=1,
                            random_state=cfg.random_state + i).fit_predict(reference)
        refs.append(silhouette_score(reference, ref_labels))

    refs = np.asarray(refs)
    # Поправка √(1 + 1/B) — стандартная у Тибширани: référence-сигма сама
    # оценена по B наблюдениям, и её неопределённость входит в порог.
    sigma = float(refs.std(ddof=1)) * math.sqrt(1.0 + 1.0 / len(refs))
    return float(real - refs.mean() - cfg.split_gain_sigma * sigma)
```

Решение о дроблении: `gain > 0` (порог уже внутри).

Новые параметры в `StatesConfig`:

| Переменная | Дефолт | Смысл |
|---|---|---|
| `STATES_SPLIT_REFERENCE_DRAWS` | `10` | Число референсов `B` |
| `STATES_SPLIT_GAIN_SIGMA` | `1.0` | Порог в сигмах референса. Подлежит калибровке |

`STATES_SPLIT_GAIN` (абсолютный) удаляется. Это ломающее изменение калибровки — обязательно бампнуть версию модели состояний и записать в `development_log.md`.

### 3.3. Стоимость

`B = 10` референсов вместо одного, но `n_init=1` вместо 3 для референсов: чистое удорожание ≈ 3.3×, не 10×. Затрагивает только `train`, у которого расчётная часть ~8 минут. Ожидаемое удорожание дробления — минуты, не часы. Замерить фактически и записать.

### 3.4. Калибровка `split_gain_sigma`

Критерий калибровки — **не** «столько же состояний, сколько было». Критерий — **стабильность**:

1. Прогнать `train --no-emit` на трёх монетах с окнами разной длины: полная история, минус месяц, минус два месяца.
2. Для каждого значения `split_gain_sigma` из {0.5, 0.75, 1.0, 1.5, 2.0} посчитать разброс числа состояний между окнами.
3. Выбрать значение, при котором разброс минимален **и** число состояний в разумном диапазоне (порядка 25–50 для BTC).

Сейчас разброс ETH составляет 29→26→42. Целевой — не более ±15%.

Отдельно повторить сравнение 32 против 44 признаков с перемешанным контролем. Если после починки контроль (шум) перестаёт обрушивать граф, а SMC-признаки держат состояния на уровне базы — калибровка сделана правильно, и вопрос о включении признаков можно ставить заново.

### 3.5. Критерий приёмки P0-2

- `_split_gain` усредняет по `B ≥ 10` референсам, порог выражен в сигмах;
- `STATES_SPLIT_GAIN` удалён, новые параметры в конфиге и в `to_dict()` модели;
- калибровка проведена по 3.4, таблица разбросов в `development_log.md`;
- повтор эксперимента с перемешанным контролем при новой калибровке;
- тест: на синтетике из двух явно разделимых облаков gain положителен, на однородном облаке — отрицателен, в 32 и в 64 измерениях **одинаково**.

## 4. P1-1: реестр источников и версия из состава

### 4.1. Что не так

`btcproc/features/builder.py:38-45`:

```python
def feature_version() -> str:
    return SMC_FEATURE_VERSION if config.smc.features_on else BASE_FEATURE_VERSION
```

Схема двоичная. Второй источник по тому же рецепту даёт:

```python
if config.smc.features_on:     return "v2"
if config.onchain.features_on: return "v3"
return "v1"
```

и набор «база + SMC + ончейн» (56 признаков) вернёт `"v2"` — ту же метку, что «база + SMC» (44). Дальше `save_feature_set` перезапишет `feature_sets.names` по PK, старые строки `features` останутся массивами на 44 значения, а `load_features` построит DataFrame из 56 имён на 44 числа.

Источник зашит по имени ещё в двух местах: `if config.smc.features_on` в `build_features:158`, `_attach_smc` в `detect_atoms:237`, плюс отдельный `SMCConfig`. Для одного источника терпимо, для трёх — цепочка условий.

### 4.2. Решение: версия композируется из состава

```python
def feature_version() -> str:
    """
    Метка набора признаков, собранная из имён включённых источников.

    Композиция вместо нумерации: "v1", "v1+smc", "v1+onchain",
    "v1+onchain+smc". Читается глазами, не требует ручного согласования
    номеров, и главное — база без источников остаётся "v1", то есть все
    накопленные строки features сохраняют идентичность и миграция не нужна.

    Имена сортируются, чтобы порядок объявления источников не влиял на метку.
    """
    active = sorted(s.name for s in registry.enabled_feature_sources())
    return BASE_FEATURE_VERSION + "".join(f"+{name}" for name in active)
```

Обратная совместимость полная: при выключенных источниках метка `"v1"`, как сейчас.

### 4.3. Реестр источников

Новый модуль `btcproc/features/registry.py`:

```python
@dataclass(frozen=True)
class FeatureSource:
    name: str                        # "smc", "onchain", "indices"
    features_enabled: Callable[[], bool]
    atoms_enabled: Callable[[], bool]
    feature_columns: tuple[str, ...]  # имена колонок, которые даёт источник
    atom_columns: tuple[str, ...]     # булевы колонки-атомы
    compute: Callable[[pd.DataFrame], pd.DataFrame]
```

`build_features` и `detect_atoms` итерируются по реестру вместо цепочки `if`. Тест полноты: каждая колонка каждого источника обязана иметь подпись в `naming.ATOM_LABELS` / `naming.AXES` — сюита падает, если источник приехал наполовину описанным.

### 4.4. Критическое ограничение: реестр не владеет порядком атомов

Порядок ключей в `ATOM_FAMILY` задаёт номера битов в маске, то есть **идентичность всех исторических `event_block_id`**. Если реестр начнёт собирать `ATOM_FAMILY` динамически, порядок станет зависеть от порядка регистрации источников и от того, какие включены, — и биты поедут при каждом изменении конфигурации.

**`ATOM_FAMILY` обязан остаться единственным упорядоченным источником правды, с добавлением только в конец.** Источники поставляют детекторы (функции расчёта), а не позиции в словаре.

Тест, закрепляющий это: зафиксировать хэш от `tuple(ATOM_BIT.items())` в файле и сверять — любое изменение порядка ломает сюиту с явным сообщением «меняются исторические event_block_id».

### 4.5. Критерий приёмки P1-1

- `feature_version()` собирается из состава, при выключенных источниках возвращает `"v1"`;
- SMC переведён на реестр без изменения поведения (метка становится `"v1+smc"` вместо `"v2"` — миграции не требует, поскольку признаки в продакшене выключены);
- тест полноты подписей;
- тест неизменности порядка битов;
- `docs/extending_features.md` обновлён — п. 2.4 сейчас предписывает ровно тот механизм, который воспроизводит проблему.

## 5. P1-2: узлы Neo4j без измерения модели

### 5.1. Что не так

`btc-market-candidate-agent/src/db/graph_repo.py:81,98`:

```cypher
MERGE (g:MarketGroup {symbol: $symbol, group_id: $group_id})
MERGE (src)-[t:TRANSITION {symbol: $symbol, transition_id: $tid}]->(dst)
ON MATCH SET t.count = t.count + 1, ...
```

Ключ — `(symbol, group_id)`. Измерения модели нет. Каждый `train` перенумеровывает `group_id`, и накопленные `count`, `avg_quality_score`, `avg_horizon_return` продолжают инкрементироваться поверх узлов предыдущего поколения.

В логе это подано как решённое: «раз в неделю, а не чаще — чаще переобучать значит чаще смешивать нумерации». Это не решение, а замедление. Еженедельный `train` — еженедельное смешивание; через квартал в графе тринадцать поколений нумерации в одних узлах.

**Это тот же класс ошибки, что `run_id ≠ model_id`**, найденный и починенный в замере лифта и в админке. Собственная формулировка урока применима дословно: «записи разных моделей внешне неотличимы: у них те же колонки, те же диапазоны значений и правдоподобные `group_id`».

### 5.2. Варианты

**A. Добавить `model_id` в ключ узла и ребра.** Поколения сосуществуют, история сохраняется, запросы фильтруют по модели. Требует, чтобы `model_id` доехал из processing в btc-graph.

**B. Чистить граф монеты при `train`.** Дёшево, теряет накопленное.

**Рекомендуется B** — по рамке §0.1 терять нечего, а вариант проще и не требует протаскивать `model_id` через контракт между проектами. Одна строка в начале `train`: `MATCH (g:MarketGroup {symbol: $symbol}) DETACH DELETE g`.

Вариант A остаётся правильным решением **для фазы эксплуатации** и его стоит держать в виду: как только накопленная статистика рёбер станет ценной сама по себе, B перестанет годиться. Заводить A сейчас — преждевременно; записать причину в `development_log.md`, чтобы через полгода не пришлось выяснять заново.

Что обязательно сделать **при любом варианте**: закрыть возможность молчаливого смешивания. Сейчас узел предыдущего поколения и узел нового неотличимы, и это надо сделать невозможным, а не маловероятным. Минимум при варианте B — падать с явной ошибкой, если `train` завершился, а очистка не выполнилась.

### 5.3. Как доставить `model_id`, не ломая схему кандидата

Схема закреплена тестом `test_generated_candidates_match_btc_graph_schema` — 37 полей. Есть два пути:

**B1. Параметр батча, а не поле кандидата.** `run_batch_pipeline` уже принимает список кандидатов и параметры; добавить необязательный `state_model_id: int | None`. Sink передаёт `run_id` модели из `runs.model_run_scope()`. Схема кандидата не меняется вовсе.

**B2. 38-е поле `state_model_id: Optional[int] = None`.** Опциональность даёт обратную совместимость со старыми кандидатами. Требует обновления теста схемы, парсера `_FIELD_MAP` и документации.

Начинать с B1 — он дешевле и не трогает контракт. B2 понадобится, только если кандидаты будут приходить из нескольких источников с разными моделями в одном батче.

При `state_model_id = None` — legacy-режим: ключ как сейчас, чтобы старые данные не осиротели.

### 5.4. Критерий приёмки P1-2

- Ключ узла и ребра включает модель, при `None` работает как раньше;
- запрос «все переходы монеты в текущей модели» возвращает только текущее поколение;
- миграция: существующие узлы получают `model_id` последнего `train` монеты либо помечаются `legacy`;
- документация: в README btc-graph раздел про Neo4j объясняет, что `group_id` осмыслен только в паре с моделью.

## 7. Второй заход по зонной SMC — ордер-блоки и FVG

### 7.1. Постановка и статус разногласия

**Позиция владельца проекта:** ордер-блоки и FVG работают, и система обязана уметь их учитывать.

**Что показал первый замер:** зонная половина SMC — FVG, ордер-блоки, брейкеры, снятия ликвидности — эффекта не дала ни на одной из трёх монет. Прошла только структурная половина.

Эти два утверждения не примиряются голосованием, и в ТЗ не записывается ни одно из них как факт. Записывается третье: **первый замер был слабым тестом зонной гипотезы, и она заслуживает второго, устроенного лучше.** Ниже — как именно, и что будет считаться закрытием вопроса в обе стороны.

Отдельно и заранее: если второй заход тоже не даст эффекта, вопрос закрывается отрицательно и переоткрывается только под новые данные или новую операционализацию с обоснованием. Три захода подряд по одной гипотезе на одних данных — это уже не проверка, а подбор.

### 7.2. Почему первый замер был слабым тестом — четыре конкретные причины

Ни одна из них не является «надо поверить сильнее». Это дефекты операционализации, и они чинятся.

**1. Бинарный флаг вместо градации.** `in_unfilled_fvg` — булево «цена внутри незакрытого FVG». Это самая бедная из возможных формулировок. В практике SMC ценность зоны зависит от: свежести, размера относительно ATR, первого касания против пятого, доли уже закрытого гэпа, согласованности со старшим таймфреймом. Всё это схлопнуто в один бит. Признаки `near_*` и `fvg_fill_pct` эту градацию несут — но они в канале **признаков**, а признаки выключены (`SMC_FEATURES_ENABLED=false`), и в замере лифта не участвовали вовсе.

Это, вероятно, главная причина. **Замерялась худшая треть того, что было реализовано.**

**2. Базовый таймфрейм 15m.** Зоны в практике SMC строят на H1/H4/D1. FVG на 15-минутке — по большей части микроструктурный шум. `SMC_SWING_LEFT/RIGHT = 3` при 15m означает подтверждение свинга за 45 минут; зона, построенная на таком свинге, к H4-ордер-блоку отношения не имеет. Открытый вопрос из первоначального ТЗ (раздел 13, пункт 1) так и не был закрыт замером.

**3. Параметры детекторов ни разу не калибровались.** `SMC_FVG_MIN_ATR = 0.5`, `SMC_EQ_TOLERANCE_ATR = 0.15`, `SMC_RECLAIM_BARS = 4` — все взяты из первоначального ТЗ как правдоподобные догадки, с явной пометкой «подобрать в фазе 2». Фаза 2 измерила частоты, но подбор порогов под них не проводился. При неудачном пороге детектор либо срабатывает постоянно (и тонет в шуме), либо почти никогда (и не набирает выборку).

**4. Замерялся маргинальный эффект, а практика условная.** Это самый содержательный пункт. Практик SMC не утверждает «цена в ордер-блоке → вверх». Он утверждает нечто вроде: «цена вернулась в свежий бычий ордер-блок, находясь в дисконте, при согласованной структуре старшего таймфрейма, после снятия ликвидности снизу». Это конъюнкция четырёх условий.

Маргинальный тест `P(up | in_bullish_ob)` усредняет по всем случаям, включая те, где условия не выполнены — и если эффект существует только в конъюнкции, он в среднем размывается до нуля. **Первый замер физически не мог обнаружить условный эффект.**

### 7.3. Что делать — три рабочих потока

**Поток A: включить градацию (дёшево, делать первым).**

Замерить лифт не по бинарным атомам, а по непрерывным SMC-признакам, разбитым на квантили. `near_fvg_bull`, `fvg_fill_pct`, `near_ob`, `ob_age_norm`, `premium_discount` — по терцилям или квартилям, тест на монотонность тренда (Cochran–Armitage), а не на разницу двух групп.

Признаки для этого включать в модель **не нужно** — достаточно посчитать их на барах кандидатов и приджойнить. То есть `SMC_FEATURES_ENABLED` остаётся выключенным, а замер идёт по вычисленным значениям. Это важно: поток A не зависит от §3 и запускается сразу.

Монотонность — более сильное свидетельство, чем разница долей. «Чем свежее зона, тем выше доля роста» гораздо труднее объяснить случайностью, чем один порог, попавший удачно.

**Поток B: старший таймфрейм (средне, зависит от §3).**

Построить зонные детекторы на H1 и H4 с подмешиванием в базовый ТФ через `shift(1)` + `ffill` — механизм уже есть в `_context_features`. Сравнить лифт зон 15m против H1 против H4.

Гипотеза, которую это проверяет: «зоны работают, но не на 15-минутке». Если лифт растёт с таймфреймом — гипотеза подтверждается, и это самостоятельный результат.

**Поток C: условный тест (дорого, делать последним и осторожно).**

Проверить конъюнкции вида «зона + дисконт + структура + снятие». Здесь два серьёзных подвоха, и без их учёта поток C не имеет смысла:

*Взрыв гипотез.* Четыре условия из десятка кандидатов дают сотни комбинаций. Тестировать все — гарантированно найти «работающие» из чистого шума. Поэтому: **не более пяти конъюнкций, зафиксированных письменно до замера**, с обоснованием каждой из практики, а не из перебора. Список пишется владельцем проекта, а не подбирается скриптом.

*Обвал выборки.* Каждое условие режет выборку. Конъюнкция из четырёх условий, каждое с частотой 20%, даёт 0.16% баров — при 314 141 баре это ~500 наблюдений, а с учётом перекрытия горизонтов ~5 независимых. Ничего не докажешь. Поэтому перед замером — расчёт ожидаемой выборки; конъюнкции с ожидаемым эффективным n < 100 не тестируются вовсе, а сокращаются до двух-трёх условий.

### 7.4. Что считать закрытием вопроса

Порядок и критерии фиксируются заранее, чтобы результат нельзя было переинтерпретировать задним числом.

| Исход | Что означает | Что делать дальше |
|---|---|---|
| Поток A даёт монотонный тренд по градации, переживающий блочный бутстрап и holdout | Зоны работают, первый замер потерял эффект из-за бинаризации | Включать соответствующие признаки, калибровать пороги, рассматривать сильнейший детектор в signature |
| Поток A ничего, поток B даёт лифт на H4 | Зоны работают, но не на базовом ТФ | Строить зонные детекторы на старшем ТФ, базовые убрать |
| Потоки A и B ничего, поток C даёт эффект на предзаявленной конъюнкции | Эффект условный, как и утверждает практика | Заводить конъюнкцию как один составной атом, не как набор |
| Все три потока ничего | Зонная SMC на этих данных и этих горизонтах эффекта не даёт | Закрыть вопрос отрицательно, записать подробно, **атомы оставить включёнными** — они дёшевы и пригодятся для разметки и разбора |

Последняя строка важна: «не даёт лифта» и «удалить из системы» — разные решения. Контекстные атомы не дробят блоки, не требуют переобучения и стоят ~50 секунд на монету за прогон. Они уже интегрированы, бэкфилл на полной истории сделан, `live` их пишет. **Требование «система должна уметь учитывать SMC» выполнено на уровне инфраструктуры независимо от исхода замеров.** Спор идёт не о том, интегрировать ли, а о том, давать ли им влиять на `quality_score` и на определение состояний.

### 7.5. Чего в этом разделе делать нельзя

| Соблазн | Почему нельзя |
|---|---|
| Записать «ордер-блоки и FVG работают» в ТЗ как обоснование | ТЗ станет самоподтверждающимся. Вся система построена ради проверки таких утверждений, а не ради их обхода |
| Начислять зонным атомам баллы в `quality_score` без прошедшего замера | Пятая ось обсуждалась и была отвергнута в первоначальном ТЗ, раздел 12. Основание не изменилось |
| Подбирать пороги детекторов по результату лифта | Это подгонка. Пороги калибруются по частоте срабатывания (цель — попасть в разумный диапазон), лифт замеряется после и на других данных |
| Перебирать конъюнкции скриптом | См. 7.3, поток C. Гипотезы фиксируются письменно до замера, иначе результат ничего не стоит |
| Считать «прошло на 2 из 3 монет» после просмотра всех результатов | Критерий формулируется до, а не после. См. §2.8 про коррелированность монет |

## 8. Порядок работ

По рамке §0.1 всё ломающее собирается в один пакет и пересобирается одним прогоном.

```
0. P0-1  блочный бутстрап в lift.py        ← не ломает ничего, не требует
   0.1  реализация + тесты на синтетике       переобучения, чинит измеритель
   0.2  перемер трёх зафиксированных гипотез
   0.3  запись результата с обоими p-value

1. §7 поток A — градация зонной SMC        ← дёшево, признаки включать не надо,
   1.1  квантильный лифт по near_* / fill_pct   идёт параллельно пункту 2
   1.2  тест на монотонность (Cochran–Armitage)

2. ЛОМАЮЩИЙ ПАКЕТ — одним заходом
   2.1  P0-2  split_gain → gap statistic
   2.2  P2    round_level_touch в доли от цены
   2.3  P2    EVENT_VERSION задействовать
   2.4  P1-1  реестр источников + версия из состава
   2.5  P1-2  очистка графа монеты при train
   ──── затем один `train --all` и пересборка ────
   2.6  калибровка split_gain_sigma по стабильности
   2.7  повтор контроля 32 vs 44 с новой калибровкой

3. §7 поток B — зоны на H1/H4              ← зависит от 2, требует прогонов
4. §7 поток C — условный тест              ← только после A и B, гипотезы
                                              зафиксированы письменно до замера
5. P2    docs/extending_features.md закоммитить
```

**Почему P0-1 переехал в начало.** Он единственный, кто ничего не ломает и не требует переобучения, а чинит инструмент, которым будут оцениваться все последующие результаты. Мерить потоки A/B/C сломанным измерителем — значит получать числа, которые придётся выбросить.

**Почему P0-2 остаётся раньше потоков B и C.** `split_gain` отвечает на вопрос «можно ли вообще включать признаки нового источника». Пока порог зависит от размерности, ответ всегда «нет» независимо от качества источника — и зонная SMC, и ончейн упрутся в одну стену. Поток A обходит это ограничение (замер по вычисленным значениям без включения в модель), поэтому идёт параллельно.

**Почему ломающий пакет одним заходом.** Каждый полный `train --all` — это 1.5–3 часа на три монеты. Пять отдельных изменений с пересборкой после каждого стоят день; один пакет — одну пересборку.

## 9. Ожидаемый результат

Прогноз, который стоит записать заранее, чтобы потом было с чем сверять:

1. **После блочного бутстрапа большинство или все четыре атома перестанут проходить.** Это не провал: отрицательная половина результата (зонная SMC не работает) станет только надёжнее, а положительная получит честную оценку. `bos_down` имеет наибольшие шансы устоять.
2. **После починки `split_gain` число состояний стабилизируется**, и разница между 32 и 44 признаками сократится. Тогда вопрос о включении SMC-признаков можно будет поставить заново — сейчас он поставлен на сломанной калибровке.
3. **Реестр источников и версия из состава ничего не улучшат сами по себе**, но без них второй источник сломает `feature_sets` молча, и обнаружится это через недели.
4. **По зонной SMC (§7) наиболее вероятен поток A.** Если эффект есть, он с наибольшей вероятностью проявится как монотонность по свежести и размеру зоны, а не как разница двух групп — просто потому, что бинаризация была самым слабым местом первого замера. Поток B — вторая по вероятности версия. Поток C выглядит убедительнее всего содержательно, но именно он хуже всего защищён от подгонки, и выборки на него может физически не хватить.

Прогнозы записаны **до** проведения замеров. Если результат разойдётся с прогнозом — это интересно и подлежит разбору; если совпадёт — тоже. Чего делать нельзя: править прогноз после того, как числа получены.
