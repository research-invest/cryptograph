# Аудит crypto-graph — 2026-08-15

Полный проход по обоим подпроектам (btcproc-генератор и btc-graph-приёмник) с упором на
незакоммиченные изменения (деривативные метрики) и алгоритмическое ядро. Все утверждения
ниже либо воспроизведены запуском (тесты, микрозамеры), либо привязаны к конкретным строкам кода.

**Повторная проверка (тот же день, второй проход по логике/математике):** из пунктов
первого прохода **не исправлено ничего** — B1–B5, O1, O3, O5 воспроизводятся в текущем
коде без изменений. Второй проход дал одну крупную новую находку (**B7** — train и live
размечают историю двумя разными правилами, расхождение 21–28% баров, замерено на боевых
моделях всех четырёх монет) и одну малую (**B8** — бары с нулевым диапазоном молча
выпадают из признаков уже сегодня). Обе — в разделе 1.

**Метод.** Прочитаны: конвейер btcproc целиком (ingest → features → events → states →
candidates → sink → notify), аналитические модули (lift, gradation, range_lift, novelty,
holdout-обвязка), db-слой, конфиг, реестр монет; на стороне btc-graph — pipeline, фильтр,
дедуп Redis. Прогнаны тесты обоих проектов в двух режимах (флаги источников выключены /
включены). Два подозрения по производительности проверены микробенчмарками на синтетике
той же размерности, что боевые данные BTC (300 тыс. баров × 32 признака).

**Итог одной строкой:** система в отличном состоянии — дисциплина «только прошлое»,
блочный бутстрап, инварианты и регрессии на каждый исторический баг выдерживают придирчивый
разбор; найдено 5 подтверждённых ошибок (крупнейшая — **B7: две несовпадающие разметки

и 30× снижение пика памяти в `StateModel.predict`** — вероятно, закрывает большую часть
мотивации выноса в Go.

## 1. Ошибки

### B1. Тесты не нейтрализуют третий источник — упадут при включении `DERIV_ENABLED` на бою

**Статус: воспроизведено.** `FGI_ENABLED=true SMC_ENABLED=true DERIV_ENABLED=true pytest`
даёт два падения:

```
FAILED tests/test_registry.py::test_feature_version_reflects_the_flags
       AssertionError: assert 'v1+deriv' == 'v1'
FAILED tests/test_fear_greed.py::test_event_version_includes_fgi_when_atoms_only
       AssertionError: assert 'v1+deriv+fgi' == 'v1+fgi'
```

Оба теста гасят `config.smc` и `config.fgi` явным `monkeypatch`, а `config.deriv` — нет
(`tests/test_registry.py:74-83`, `tests/test_fear_greed.py:283-289`). Это в точности
ловушка из журнала 34.10, о которой предупреждает собственный комментарий первого теста
(«Заводя третий источник, добавь его сюда») — деривативы туда не добавлены.

Сейчас на VPS `DERIV_ENABLED=false` (`deploy/02_configure.sh:458`), поэтому пока всё
зелёное. Но решение фазы 2 (журнал, раздел 36) — «четыре контекстных атома-квадранта
остаются как бесплатная разметка», то есть флаг предстоит включить, и в этот момент
тесты на бою покраснеют, а локально останутся зелёными — ровно тот разъезд, который
проект дважды ловил с FGI.

**Починка** (10 минут): в оба теста добавить
`monkeypatch.setattr(config, "deriv", config.DerivConfig(enabled=False, features_enabled=False))`.
Заодно стоит пройтись `grep -l "monkeypatch.setattr(config, \"smc\"" tests/` и проверить,
нет ли других тестов, нейтрализующих два источника из трёх.

### B2. Гонка в кэшах источников: параллельные прогоны админки могут молча подмешать монете чужие данные

`build_smc_cached`, `build_fear_greed_cached`, `build_deriv_cached` пишут кэш двумя
отдельными присваиваниями:

```python
_CACHE["key"], _CACHE["value"] = key, value   # smc.py:437, fear_greed.py:231, deriv.py:233
```

Админка запускает до `ADMIN_MAX_CONCURRENT_RUNS=2` прогонов одновременно через
`BackgroundTasks` — то есть в РАЗНЫХ ПОТОКАХ одного процесса (`admin/app.py:572,598`).
GIL не делает пару присваиваний атомарной: перемежение «A пишет key_A → B пишет key_B →
B пишет value_B → A пишет value_A» оставляет в кэше **key_B с value_A**. Следующее
обращение с key_B (второй вызов `compute` того же прогона — атомы после признаков)
получает DataFrame другой монеты.

Хуже всего то, что это не упадёт: бары всех монет живут на одной 15-минутной сетке,
индексы совпадают, и `a[name] = values[name]` в `_attach_sources` (events.py:361) молча
выровняет чужие значения по совпавшим timestamp — монета B получит SMC-структуру или
ОИ-квадранты монеты A. Это тот самый класс «тихо неверных данных», против которого в
проекте выстроены инварианты 6 и 13. Окно гонки узкое, но прогоны идут каждые полчаса
годами.

**Починка** (30 минут): атомарная запись одним присваиванием —
`_CACHE["entry"] = (key, value)` и чтение `entry = _CACHE.get("entry")` (запись одного
значения в dict атомарна под GIL), либо `threading.Lock` вокруг обоих обращений.
В CLI-прогонах (отдельный процесс на запуск) проблемы нет — только в админке.

### B3. Автообновление графика умирает после первой же неудачной загрузки

Свежий код автообновления (`admin/templates/chart.html:777-820`):

```js
function scheduleAutoReload() {
  autoReloadTimer = setTimeout(async () => {
    await autoReload();          // если load() бросил — reject
    scheduleAutoReload();        // ← до этой строки дело не дойдёт
  }, msUntilNextTick());
}
```

`autoReload` пробрасывает исключение из `load()` наружу (`try/finally` без `catch`), и
`scheduleAutoReload()` после `await` не вызывается. Один транзиентный сбой — перезапуск
админки, обрыв сети, 502 от nginx — и вкладка молча перестаёт обновляться до ручного
рефреша, что для страницы «смотрим рынок раз в полчаса» и есть основной сценарий.
Восстановление `savedRange` при ошибке тоже пропускается.

**Починка** (15 минут): обернуть `await autoReload()` в `try/catch` (лог в консоль),
`scheduleAutoReload()` перенести в `finally`. Заодно поправить комментарий: в нём
«до СЛЕДУЮЩЕЙ пятиминутки», а код считает получасовки.

### B4. Латентная ловушка: включение `DERIV_FEATURES_ENABLED` молча срежет историю признаков до 2020-09

`build_features` завершает сборку общим `dropna()` по всем колонкам
(`features/builder.py:181`). Деривативные признаки — NaN везде, где метрик нет:

* до `metrics_start` монеты (BTC — 2020-09-01 при барах с 2017-08: **минус три года
  истории**, ETH/SOL — до 2021-12-01);
* в дырах по колонкам у поставщика (§0.9 ТЗ: у 2022-01 живой ОИ при пустых
  ratio-колонках → `ls_retail_z`/`top_vs_retail` NaN → бары выпадают **из середины**
  истории, дырами, которые дальше ломают `valid`-логику соседних окон).

Сейчас флаг выключен и по результатам гейтов включать его не планируется — но флаг
существует, ничего не предупреждает, и «включил ради эксперимента → модель молча
обучилась на трети истории» — это ровно сценарий тихой деградации. У FGI-признаков та же
механика мягче (история с 2018-02, дыр четыре дня).

**Починка** (на выбор, полчаса): при `features_on` любого источника логировать/падать,
если dropna отрезал больше N% строк относительно baseline-набора; либо для источников с
известной границей заполнять «нет данных» нейтральным значением с явным решением в ТЗ
фазы 3. Минимум — абзац в `extending_features.md`, что фаза 3 деривативов обязана решить
вопрос «что делать с 2017–2020».

### B5. `oi_rank` считается по сырому `oi` с нулями-глитчами

В `build_deriv` нули фида (116 баров BTC, задокументированы в комментарии) вычищены в
`oi_safe` для логарифмов, но `oi_rank` берёт сырой ряд:
`out["oi_rank"] = ind.rolling_rank(oi, w["1m"])` (`features/deriv.py:163`). Глитч-ноль
получает ранг ~0.0 («экстремально низкий ОИ») и тащит за собой ранги соседей в месячном
окне. Признаки выключены, так что это влияет только на замеры (гейты R/G уже считались с
этим), но правка однострочная: `rolling_rank(oi_safe, ...)`. Стоит пересверить вывод по
`oi_rank` в разделе 36 после правки — он «прошёл частично», и 116 выбросов могли внести
вклад.

### B7. Train и live размечают историю двумя разными правилами — расходятся на 21–28% баров

**Статус: замерено на боевых моделях всех четырёх монет (второй проход, докер).**

Каналов разметки два, и они не совпадают:

* `train` сохраняет в `bar_states` **членство в группах кластеризации** — сырые метки из
  `fit_states` (`pipeline/train.py:205-212`): к какой группе бар был отнесён рекурсивным
  дроблением (и слиянием);
* `live` размечает ту же историю через `model.predict` — **ближайший центроид**
  (`pipeline/live.py:192`).

Эти правила эквивалентны только для вороного разбиения, а разбиение здесь не вороное:
иерархическое 2-means-дробление режет пространство последовательными локальными
границами, и итоговая ячейка группы не совпадает с ячейкой её центроида (слияния в
`_merge_close` усугубляют, но не обязательны — эффект есть и без них). Модель хранит
только центроиды, то есть **сохранённая модель в принципе не способна воспроизвести
разбиение, статистику которого записал train**.

Замер (сглаживание `assign_states` применено к обоим каналам — ровно боевой путь):

| монета | train run | баров | mismatch | переходов train | переходов predict |
|---|---|---|---|---|---|
| BTCUSDT | 24 | 312 758 | **25.7%** | 28 806 | 31 744 |
| ETHUSDT | 25 | 312 591 | **21.4%** | 29 025 | 28 828 |
| SOLUSDT | 26 | 208 556 | **28.3%** | 19 507 | 22 670 (+16%) |
| HYPEUSDT | 34 | 36 741 | **28.3%** | 3 528 | 3 725 |

Крупнейшие группы теряют при predict-разметке 30–50% своих баров (BTC группа 1 — 38.9%,
HYPE группа 1 — 52.1%). Расхождение равномерно по годам (24–30% в каждый год 2017–2026),
то есть это не ревизия баров после train, а структурное свойство; в модели BTC при этом
**ноль слияний** — чистый эффект «дробление ≠ вороное». Контроль на синтетике: хорошо
разделённые облака дают 0.0% (правила совпадают тривиально), перекрывающийся рыночный
континуум из conftest — 7.7%.

Что из этого следует (всё — про внутреннюю согласованность, а не про look-ahead;
look-ahead здесь не возникает):

* **`bar_states` в БД — лоскут из двух разметок:** train пишет всю историю членством,
  каждый live переписывает окно от cutoff предиктом. Любой замер, читающий `bar_states`
  поперёк шва, смешивает два правила.
* **`market_groups` (статистика, имена состояний, `top_features`) описывают разбиение,
  которое боевой предиктор не воспроизводит на четверти баров.** Подпись узла «низкая
  волатильность, цена у верха» посчитана по одному множеству баров, а live относит к
  этому узлу заметно другое множество.
* **Кандидаты train и live построены на разных исторических выборках.** `live` собирает
  снимки и аккумуляторы из predict-разметки полной истории (внутри одного live это
  самосогласованно), train — из членства; `transition_id` вида «42→1» в двух каналах
  означает разные наборы случаев, а у SOL predict находит на 16% больше переходов.
* **Граф Neo4j копит рёбра поверх двух разметок** — train закладывает узлы/статистику
  одним правилом, последующие live доливают переходы другим.

**Починка** (полчаса + недельный train применит): после сборки модели в `fit_states`
вернуть метки предиктом, а не членством — `labels = model.predict(x)`; сортировку групп
по размеру и `group_ids` считать по predict-наполнению. Тогда единственным определением
состояния становится «ближайший центроид» — то, что модель и так единственно умеет
воспроизводить, — и оба канала совпадают тождественно. Регрессия: на обучающей матрице
`fit_states(...)[1] == model.predict(x)` поэлементно. Цена: числа `group_stats`
слегка сдвинутся (группы обменяются ~уже сегодня спорными барами), сопоставимость с
прошлыми прогонами и так рвётся каждым train.

Важно для чтения прошлых замеров: валидация holdout (раздел 26 журнала) и контрольная
модель (раздел 31) вердикт не меняют — сигнала нет в обоих правилах разметки. Но любой
замер, сравнивавший статистику train-канала с кандидатами live-канала, нёс этот шум.

### B8. Бары с нулевым диапазоном молча выпадают из признаков уже сегодня

Механика B4 (глобальный `dropna` в `build_features`) срабатывает не только «при включении
деривативов когда-нибудь», а прямо сейчас: `range_exp = log((high−low)/mean(...))` на баре
с `high == low` даёт `log(0) → −inf → NaN → dropna` — **вся строка признаков исчезает**.
По боевой базе таких баров: BTC — 147, ETH — 329, SOL — 14, HYPE — 0 (плюс 60/154/13
баров с нулевым объёмом — те же кандидаты в дыры через `vol_ratio` при вырожденных окнах).

Доля мала (~0.05–0.1%), но дыра тихая и точечная: пропавший бар сдвигает позиционные
офсеты снимков (см. B6), рвёт непрерывность `age`/энтропии в `assign` и выкидывает бар
из разметки состояний, хотя в `ohlcv` и `outcomes` он есть. Починка — считать
`range_exp` по `replace(0, np.nan)` от **числителя до деления** и заполнять
нейтральным значением (нулевой диапазон — это «сжатие», а не «нет данных»), либо
`fillna` по колонке перед общим dropna. Заодно закрыть смежный краевой случай
`indicators.rsi`: на полностью плоском окне (avg_gain = avg_loss = 0) RSI получает 100
(«только рост»), что на тех же нулевых барах кормит и признак `rsi`, и атом
`rsi_overbought`; честнее 50 или NaN.

## 2. Оптимизации

### O1. `StateModel.predict`: 22× быстрее, 30× меньше памяти — замерено

Текущая реализация (`states/clustering.py:52-56`) материализует массив (n, k, d):

```python
distances = np.linalg.norm(x[:, None, :] - self.centroids[None, :, :], axis=2)
```

Замер на боевой размерности (300 000 × 32, 45 центроидов, эта машина):

| вариант | время | пик памяти |
|---|---|---|
| текущий (broadcast + norm) | 5.30 с | **7.13 ГБ** |
| разложение ‖x−c‖² = ‖x‖² − 2xcᵀ + ‖c‖² | 0.24 с | ~0.2 ГБ |

Метки совпадают 1.0000 (argmin инвариантен к монотонному преобразованию, корень не нужен).
Вызывается на ПОЛНОЙ истории в каждом `live` (раз в полчаса × 4 монеты), в `train`,
`replay`, `holdout`. Семь гигабайт пика на VPS — это ещё и риск свопа/OOM рядом с
PostgreSQL и Neo4j, то есть правка не только про скорость.

```python
def predict(self, x: np.ndarray) -> np.ndarray:
    c = self.centroids
    d2 = (x * x).sum(axis=1)[:, None] - 2.0 * (x @ c.T) + (c * c).sum(axis=1)[None, :]
    return self.group_ids[d2.argmin(axis=1)]
```

Один тест на эквивалентность старой формуле — и готово. Это самое дешёвое из крупных
ускорений в проекте.

### O2. `live` пересчитывает всю историю каждые полчаса — главный структурный резерв

`run_live` на каждый запуск: грузит все бары, строит все признаки, все события, все
исходы, размечает всю историю, строит ВСЕ снимки и прогоняет `cand.generate` по всем
снимкам с 2017 года — чтобы в конце оставить кандидатов за последние полчаса
(`pipeline/live.py:177-232`). Это честно по построению (аккумуляторам кандидатов нужна
вся предыстория, replay/train переиспользуют тот же код), но крон платит полную цену
двенадцать раз в сутки на монету.

Направления, по убыванию отдачи к сложности:

1. **Кэш аккумуляторов на модель.** Состояние `generate` — это `by_full`/`by_transition`
   аккумуляторы плюс водяной знак «созревшие снимки до ts». Оно детерминировано парой
   (model_run_id, последний созревший снимок) и сериализуемо (все поля — счётчики,
   отсортированные списки, множества). Прогон: загрузить состояние, долить новые
   созревшие снимки, выпустить кандидатов хвоста, сохранить состояние. Инвалидация
   тривиальна — по `model_run_id` (train создаёт новый). Осторожность: `states` для
   хвоста всё равно нужен на полной истории из-за сглаживания/энтропии — но это дёшево
   после O1.
2. **Признаки хвостом.** Все окна конечны (максимум месяц = 2688 баров плюс прогрев EMA);
   признаки можно считать только за последние ~2×2688 баров и брать историю из уже
   посчитанного. Осложнение: SMC-реестры принципиально несут состояние с начала истории —
   но SMC-признаки выключены, а атомы уже закэшированы в рамках процесса.
3. Если п.1–2 делать не хочется — хотя бы дисковый кэш `build_smc` (сейчас кэш только
   в памяти процесса и в кроне бесполезен: каждый запуск — новый процесс).

С учётом O1 и п.1 типичный live должен уложиться в десятки секунд вместо минут — что,
по-видимому, и была цель эксперимента с Go, только без второго рантайма и без риска
разъезда двух реализаций логики (главный аргумент против выноса: вся ценность проекта —
в инвариантах, а их пришлось бы поддерживать в двух языках).

### O3. `ingest-metrics` ежедневно перемалывает весь архив с 2020 года

`sync_metrics` без `--start` стартует от `metrics_start_date()` монеты
(`ingest/metrics.py:262-264`), а крон (`deploy/02_configure.sh:923`) и `make
ingest-metrics` зовут его без `--start`. Итог: каждый день на VPS — ~2170 zip-архивов
BTC (плюс остальные монеты) читаются с диска, парсятся, агрегируются и upsert-ятся
(~208 тыс. строк на монету) ради одного нового дня. Сеть не страдает (кэш), но это
минуты CPU и бессмысленная нагрузка на таблицу ежесуточно.

**Починка** (30 минут): дефолтная точка старта — `max(ts)` из `deriv_metrics` монеты
минус страховочные 3–5 дней (архив дозаполняется задним числом на границах листинга);
`--start` остаётся для бэкфилла. Симметрично тому, как `sync_recent` баров продолжает от
`last_ts`.

### O4. `_merge_close` пересчитывает все пары после каждого слияния

`states/clustering.py:240-273`: на каждой итерации while заново считаются separation всех
пар — а `_separation` каждый раз заново усредняет исходные точки групп. Замер: один полный
проход пар при 50 группах на 300k×32 — ~2.9 с; при M слияниях это M полных проходов.
Кэшировать на группу центроид (и пересчитывать только пары с участием свежесмёрдженной
группы) — O(k) пересчётов на итерацию вместо O(k²). Экономия — десятки секунд на train;
некритично (train недельный), но правка локальная.

### O5. `repo.save_*` собирают строки через `iterrows`

`save_bar_states`, `save_events`, `save_outcomes`, `save_groups`, `save_transitions`
(`db/repo.py:80-231`) идут по DataFrame через `iterrows()`/`for ts, r in ...` — на 300 тыс.
строк train это заметно медленнее `itertuples()` (обычно в 5–10 раз на конверсии; сама
вставка потом доминирует, но конверсия — секунды лишнего CPU на каждую таблицу). Правка
механическая; если когда-нибудь упрётесь во вставку как таковую — следующий шаг
`COPY` (psycopg2 `copy_expert`) вместо `execute_values`, но сейчас это не нужно.

### O6. Мелкое

* `ingest/binance._sync_daily_tail` кэширует дневные zip навсегда; после закрытия месяца
  они дублируются месячным дампом. Чистка `data/binance/*/15m/YYYY-MM-DD.zip` старше
  месяца — одна строка в `scripts/maintenance.py`.
* `block_statistics` (events.py:481-487) использует Python-лямбды с `mode()` в agg —
  на числе уникальных блоков это копейки; трогать не стоит, фиксирую, что смотрел.

## 3. Что проверено и оказалось в порядке (чтобы не перепроверять)

* **Look-ahead.** Прошёл руками все стыки: сдвиг старших ТФ (`builder._context_features`),
  сдвиг свингов SMC, суточный сдвиг FGI (включая выравнивание календаря под дыры),
  отсутствие сдвига у deriv-метрик (доказательство в докстринге `metrics.aggregate`
  корректно: окно [T, T+15m) при 5m-гранулярности безопасно при обеих конвенциях
  `create_time`), `forward_range_ratio` (окно (t, t+H] собрано без заглядывания),
  созревание выборки в `cand.generate` (`ts + horizon <= t`). Дефектов нет.
* **Статистика.** Блочный бутстрап (стационарный, Полица–Романо, векторизован),
  знаменатель только по пригодным репликам, обобщённый Cochran–Armitage (σ² фактическая,
  на бинарной метрике совпадает с классикой), `partial_r2_gain` с пересчётом r_bp на
  реплике, `block_length_rows` прямым счётом плотности окна — всё корректно и
  задокументировано лучше, чем в среднем по индустрии.
* **Изоляция монет.** symbol в `configuration_hash`/`candidate_family_key`/ключах Redis,
  проброс `symbol` через `FeatureSource.compute` — на месте, регрессии есть.
* **Notify.** Три предохранителя на месте, `_claim` атомарен, счётчики под локом,
  переполнение очереди — честный drop с журналом.
* **Тесты.** btcproc: все зелёные без флагов; btc-graph: все зелёные (1 skip). Единственный
  красный режим — B1 выше.
* **db/session.** Пул с семафором, возврат битых соединений с `close=True`, сброс
  autocommit — аккуратно.
* **Второй проход по математике (2026-08-15, вечер).** Перепроверены с карандашом:
  `outcomes.compute_outcomes` (окна sliding_window_view выровнены точно: (t, t+H],
  созревание в `generate` сходится с концом бара — look-ahead нет и на границе);
  `candidates/builder` (веса `research_score` в сумме 1.0, `_percentile_sorted`,
  `effective` по реализациям, зеркальная short-тройка); `graph.transition_stats` /
  `group_stats` / `_describe_groups`; `lift.stationary_block_indices` (корректная
  реализация Полица–Романо через cumsum/maximum.accumulate), `block_length_rows`
  (прямой счёт плотности окна, поправка на обрезанные окна у края), `thinned_z`,
  `benjamini_hochberg`; `gradation.cochran_armitage` (обобщение на непрерывную метрику
  точно совпадает с классикой на бинарной), `trend_bootstrap_p` (фиксированные μ и σ²
  корректны — метрика не пересобирается); `range_lift.partial_r2_gain` (r_yb справедливо
  фиксирован — b и y не пересобираются, r_bp пересчитывается); `novelty_r2` (fit только
  на train-части); `forward_range_ratio`; атомы `events.detect_atoms` (экстремумы со
  shift(1)); `_context_features` (shift на бар старшего ТФ + ffill). Новых дефектов в
  этих местах нет. Единственная методологическая мелочь: в `gradation` бины holdout
  строятся по квантилям самого holdout, а не по границам train — при дрейфе
  распределения «направление удержалось» проверяется на слегка другом разбиении;
  на вердикты замеров не влияло (все гейты провалены с запасом).

B7 поставлен первым не из-за размера правки, а из-за накопления: каждый train пишет
статистику одним правилом, каждый из ~340 live в неделю доливает данные другим, и чем
дольше это живёт, тем меньше смысла в накопленном графе. Правка при этом — строка плюс
перенумерация.

Про Go: после O1 (и тем более O2.1) горячие точки Python-контура закрываются NumPy/BLAS и
устранением повторной работы; выигрыш второго рантайма останется в границах «ещё в разы»,
а цена — двойная реализация инвариантов, на которых держится весь проект. По этому аудиту —
жить на Python оправданно.
