Кандидатов у BTC стало 37 497 против 28 818 — плюс 30%. Состояний больше, переходов больше, каждый реже, значит распределение `sample_size` съехало вниз. Аналогично поехали `monthly_concentration` и `research_score`.

## 4. Три дефекта измерителя

Все в `btcproc/analysis/lift.py`. Ни один не отменяет полученных выводов, но каждый смещает их в известную сторону.

### 4.1. Разрешения бутстрапа не хватает под Бонферрони

`DEFAULT_N_BOOT = 2000`, p-value с поправкой на единицу `(1 + k) / (1 + B)`, минимум `1/2001 ≈ 0.0005`.

Порог Бонферрони при 25 тестах: `0.05 / 25 = 0.002`. Пройти могут только `1 + k ≤ 4.002`, то есть **не более трёх реплик из двух тысяч**.

Насколько это шумно. При истинной хвостовой вероятности `p = 0.001` ожидаемое `k` равно 2:

```
P(K ≤ 3 | λ = 2) = e⁻² × (1 + 2 + 2 + 8/6) = 0.1353 × 6.333 = 0.857
```

**14% шанс потерять настоящий эффект чисто на шуме Монте-Карло**, независимо от данных.

Починка: `n_boot ≥ 10 · m / α` при Бонферрони, то есть от 5000, надёжнее 20000. Плюс предупреждение в `format_table`, если `1/(1 + n_boot) > α/m × 0.25`.

### 4.2. Длина блока считается от среднего шага

```python
step_minutes = span_minutes / (n - 1)
```

Средний интервал по всей выборке. Но плотность кандидатов по истории неоднородна: ранняя реже, поздняя плотнее, а снимки офсетов `(0, 45, 90, 180)` дают четыре кандидата в пределах 12 баров и затем разрыв.

Зависимость сильнее всего там, где плотность выше. Среднее завышает интервал в плотных участках, значит блок короче нужного, значит тест анти-консервативен ровно там, где должен быть строже.

```python
gaps = ordered.diff().dropna().dt.total_seconds() / 60.0
step_minutes = float(gaps.quantile(0.10))   # плотные участки
```

Даст более длинный блок и более консервативный тест — направление правильное.

Проверка: `thinned_z` от этой ошибки свободен (окна режутся по времени, а не по строкам). Расхождение бутстрапа и прореживания на боевых данных — прямой индикатор.

### 4.3. Непригодные реплики смещают p вниз

```python
usable = (counts > 0) & (counts < n)
extreme += int((usable & (lifts >= observed)).sum())
done += size          # ← все реплики, включая непригодные
```

Непригодная реплика попадает в знаменатель, но никогда в числитель. Смещение — в сторону значимости.

Для частого атома доля непригодных пренебрежима. Для самого редкого, проходящего `min_group = 30` при `n ≈ 30 000`, доля True около 0.1%, блоков с True около 3.2, доля реплик без единого True порядка `e⁻³·² ≈ 4%`. До 4 п.п. относительного смещения **у самых редких атомов, которые и без того наиболее подозрительны**.

Починка: `done += int(usable.sum())`, добирать реплики до нужного числа пригодных.

### 4.4. Критерий приёмки §4

- Тест: на синтетике с известной автокорреляцией и заданной частотой атома бутстрапный p при `n_boot = 2000` и при `n_boot = 20000` различается не более чем на разрешение;
- тест: длина блока на выборке с неоднородной плотностью больше, чем при расчёте по среднему;
- тест: при доле непригодных реплик 10% p не смещается.

## 5. Голосование вместо одного draw

### 5.1. Ингредиент уже измерен

Замер 2026-08-11: на крупных группах BTC `gain` по восьми подвыборкам силуэта даёт `+0.032 ± 0.007` (решение «дробить» 8 из 8) и `−0.019 ± 0.010` (1 из 8). Вывод сформулирован верно: критерий воспроизводим вдали от границы и переворачивается у неё, а рекурсия усиливает единственный перевёрнутый выбор во всё поддерево.

Но решение по-прежнему принимается по одному draw. **Голоса посчитаны — надо на них решать.**

### 5.2. Реализация

```python
def _split_vote(x, rng, cfg) -> bool:
    """
    Дробим, если за это голосует большинство подвыборок силуэта.

    Одна подвыборка у границы решения переворачивается, а рекурсия
    усиливает единственный перевёрнутый выбор во всё поддерево.
    Голосование убирает именно этот механизм: устойчивое решение проходит
    единогласно (замер 2026-08-11: 8/8 при gain +0.032), пограничное
    отсеивается (1/8 при −0.019).
    """
    votes = sum(
        _split_gain(x, np.random.default_rng(cfg.random_state + k), cfg) > 0
        for k in range(cfg.split_vote_draws)
    )
    return votes >= cfg.split_vote_threshold * cfg.split_vote_draws
```

| Параметр | Дефолт |
|---|---|
| `STATES_SPLIT_VOTE_DRAWS` | `5` |
| `STATES_SPLIT_VOTE_THRESHOLD` | `0.6` (три из пяти) |

### 5.3. Стоимость

Пять подвыборок вместо одной, но число референсов снижается с 10 до 4 — голосование уже усредняет, и точность отдельной сигмы менее важна. Чистое удорожание ≈ 2×, то есть около 5 минут на монету при нынешних 2.3.

### 5.4. Ожидаемый эффект и как проверять

Разброс числа состояний должен упасть у всех монет, **включая SOL**, потому что убирается именно тот механизм, который его порождает.

Порядок: реализовать → прогнать калибровочный свип заново (он автоматизирован) → сравнить с текущими 10.3% / 13.9% / 50.4%.

**Если голосование лечит SOL — задача §7 снимается.** Поэтому §5 идёт раньше §7.

## 6. PCA-выровненный референс

### 6.1. Диагноз

Эффект размерности сократился вдвое, но не исчез: BTC −24%, ETH −40%, SOL −20%. Причина установлена верно — референс равномерен в bounding box, а это плохой ноль для концентрированных данных в высокой размерности. Реальное облако признаков занимает малую долю объёма своего гиперкуба, и чем выше размерность, тем сильнее расходятся два множества.

Синтетический критерий приёмки при этом выполняется (знак не зависит от размерности в 8/32/64), но **величина** зависит — а именно она решает, где остановится дробление на реальных данных.

### 6.2. Починка

Второй вариант референса у Тибширани: равномерное облако генерируется в боксе, выровненном по главным компонентам данных, и затем поворачивается обратно.

```
1. центрировать выборку
2. SVD → главные компоненты
3. спроецировать на них
4. равномерный референс в bounding box проекции
5. повернуть обратно в исходные координаты
```

Референс получает ту же ковариационную структуру, что и данные, и остаётся «бесструктурным» только в смысле отсутствия кластеров — а не в смысле отсутствия корреляций между признаками.

### 6.3. Критерий приёмки

Повторить контроль «32 против 44 с перемешанным шумом». Целевое: **эффект размерности на шуме не превышает 10%** на всех трёх монетах. Сейчас 24 / 40 / 20%.

Если после §5 и §6 шум перестаёт менять число состояний, вопрос о включении признаков нового источника можно ставить чисто: изменение графа будет означать, что источник несёт информацию, а не что он добавил измерений.

## 7. `states_overrides` для SOL

### 7.1. Что известно

SOL нестабилен при любом `sigma` (41–50% разброса) и после пересборки дал 55 состояний против прежних 32 — рост на 72% против +19% и +21% у остальных. При этом кандидатов у него меньше всех: 20 905.

Диагностика исполнителя:
- **не нормировка** — отрезание двух месяцев сдвигает медианы признаков на 0.01 IQR, IQR на 1.4%, геометрия та же;
- **дело в дроблении, не в слиянии** — полное окно 48 дроблений и 0 слияний, укороченное 27 и 0, при одинаковом `keep = 12`. Различие набирается на ветках, доходящих до `max_depth`.

### 7.2. Порядок

**Делать только после §5.** Голосование может вылечить причину, и тогда подбор параметров окажется подгонкой под симптом.

Если после голосования разброс SOL остаётся выше 20%:

1. Снизить `max_depth` в `states_overrides` монеты — ветки перестанут упираться в предел;
2. либо поднять `min_group_share` — крупные группы перестанут дробиться до вырождения;
3. критерий выбора — **стабильность между окнами**, не «столько же состояний, сколько у BTC».

Категорически нельзя: подбирать параметры так, чтобы получилось нужное число состояний, или чтобы прошёл какой-то замер.

## 9. Поток C — условный тест

При горизонте 4h конъюнкция частотой 5% требует 0.041 вместо 0.100 — уже в области наблюдаемого.

### 9.2. Что требуется от владельца проекта

Инструмент готов. Нужен **письменный список до пяти конъюнкций, записанный до замера**, с обоснованием каждой из практики. Например: «цена вернулась в свежий бычий ордер-блок, находясь в дисконте, при согласованной структуре старшего ТФ».

Подбирать конъюнкции скриптом нельзя — при сотнях комбинаций «работающие» найдутся из чистого шума гарантированно.

### 9.3. Протокол

1. §8 выполнен, горизонт для замера выбран;
2. список конъюнкций записан в `development_log.md` с датой;
3. для каждой посчитана ожидаемая частота и минимальный обнаружимый лифт — конъюнкции с ожидаемым `n_эфф < 100` **не тестируются вовсе**, а сокращаются до двух-трёх условий;

| 1h | −0.065 |
| 4h | −0.084 |

Не засчитан: профиль по бинам не строго монотонен, одна инверсия. Корреляция с `pos_1d` = 0.44 — дубликатом существующего признака не является.

### 10.2. Почему это нельзя засчитать сейчас

Предзаявленный критерий проверял монотонность **по бинам признака**. Данные показывают монотонность **по таймфрейму** — то есть зависимость «доза — отклик», которую предсказывает гипотеза «зоны работают, но не на 15-минутке».

Это независимое свидетельство, и в критерий оно не входило. Промотировать его сейчас — в точности сад расходящихся тропок: гипотеза породилась данными и должна проверяться на данных, которые её не порождали.

### 10.3. Протокол

Записать в `development_log.md` **до прогона**, с датой:

> Если эффект растёт с таймфреймом, то на D1 лифт `premium_discount` будет отрицательным и по модулю больше 0.084 на BTC, со знаком, сохранённым на ETH и SOL.

Затем прогнать `measure_zone_timeframe.py` с D1 по трём монетам.

Засчитывается только при полном выполнении. «На D1 меньше, но всё равно значимо» — не та гипотеза, и засчитывать её нельзя.

Дополнительно: посмотреть `n` по бинам. Если инверсия приходится на крайний бин с малой выборкой — это артефакт, а не нарушение монотонности, и критерий стоит переформулировать (тоже заранее).

## 11. Диагностика слияний

Полчаса, но может вскрыть неработающую половину алгоритма.

В диагностике SOL зафиксировано **0 слияний** в обоих окнах при 48 и 27 дроблениях. Проверить, срабатывает ли `merge_separation` вообще где-нибудь:

```sql
SELECT symbol,
       params->>'merge_separation' AS threshold,
       jsonb_array_length(params->'trace') AS steps
FROM processing.state_models
ORDER BY symbol;
```

и посчитать в `trace` долю шагов с `action = "merge"` по всем монетам и прогонам.

Если слияния не срабатывают нигде и никогда — это не настройка порога, а неработающая часть алгоритма. И она объясняет, почему число состояний определяется исключительно дроблением и потому нестабильно: корректирующего механизма просто нет.

Результат записать в журнал независимо от того, что найдётся.
