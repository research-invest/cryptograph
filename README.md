# crypto-graph

Исследовательский контур, который размечает историю крипторынка графом
состояний и выпускает **кандидатов** — досье вида «такая конфигурация уже была
1339 раз, в 74% случаев за следующие 24 часа цена шла вверх».

Система состоит из двух частей: одна такие досье **строит**, другая — **оценивает,
объясняет и фильтрует**. Обе лежат в этом репозитории.

> **Прочитать до всего остального.**
> На отложенной части истории утверждение «после такой конфигурации чаще бывало
> вверх» **не подтвердилось**: directional accuracy 0.497–0.516 с доверительными
> интервалами, накрывающими 0.5, наклон калибровки 0.02–0.07 при идеале 1.0,
> STRONG не отличается от WEAK. Контрольная модель без графа на тех же признаках
> критерий тоже не прошла — значит потолок лежит в признаках, а не в структуре
> графа. Подробности — [«Что установлено замером»](#что-установлено-замером).
>
> Отсюда следствие, которое действует на весь проект: **кандидат — это
> исследовательская идея, а не торговый сигнал.** Слова «вероятность»,
> «предсказание», «сигнал» в текстах системы неуместны.

## Как они связаны

```
Binance / Bybit → btcproc (признаки → события → состояния → граф → кандидаты)
                                                          │  40 полей схемы
                                                          ▼
                                      btc-graph (validator → scorer → LLM → фильтр)
                                                          │
                                              PostgreSQL / Neo4j / Redis
```

Разделение ролей жёсткое: **btcproc считает статистику и не решает, что хорошо;
btc-graph оценивает и фильтрует, но ничего не вычисляет заново.** Внутри
btc-graph действует тот же принцип этажом ниже — LLM только формулирует, все
числа считает детерминированный скорер.

Инфраструктура общая и принадлежит btc-graph: PostgreSQL (TimescaleDB +
pgvector), Redis и Neo4j поднимаются его `docker-compose.yml`. У btcproc своей
базы нет — он ходит в ту же базу `btc_graph`, но в схему `processing`, и в
другую Redis-БД (`/1` против `/0`).

Третий выход, помимо btc-graph, — **уведомления**: `btcproc/notify/` шлёт POST
с JSON, когда появляется кандидат под фильтр (монета, рейтинг, сторона, тип
события). Формат тела — внешний контракт,
[`docs/notifications.md`](btc-graph-processing/docs/notifications.md).

## В работе четыре монеты

BTCUSDT, ETHUSDT, SOLUSDT (спот Binance) и HYPEUSDT (спот **Bybit** — на споте
Binance этой пары нет). Площадка — свойство монеты, а не системы.

**Модель состояний своя на каждую монету**, поэтому `group_id` осмыслен только
в паре `(symbol, run_id)`: состояние 7 у BTC и состояние 7 у ETH — разные рынки,
и между прогонами одной монеты нумерация тоже не сохраняется.

Порядок заведения новой монеты важен именно такой: `SymbolSpec` → `ingest` →
`train --no-emit` → сверить граф → **завести профиль оценки в btc-graph** →
`emit`. Пошаговая процедура с гейтами — скилл
[`.claude/skills/add-symbol/`](.claude/skills/add-symbol/SKILL.md).

## Порядок запуска

```bash
cd btc-graph && make up && sleep 15 && make migrate   # postgres, redis, neo4j, api:8000, celery, flower:5555
cd ../btc-graph-processing && make init-db            # схема processing в той же базе
make status                                           # покрытие истории, отставание, доступность btc-graph
make train                                            # первый полный прогон (30–60 мин)
make live                                             # дальше — только это, регулярно
```

Тесты инфраструктуры не требуют:

```bash
cd btc-graph              && make test-local
cd btc-graph-processing   && make test
```

## Что установлено замером

Два результата, полученных на отложенной части истории, и оба отрицательные.

**2026-08-12, walk-forward валидация** (`make validate-holdout` в btcproc).
Шесть замеров из шести (три монеты × две модели состояний, обучение на 70%
истории): система статистически неотличима от «всегда long» на горизонтах 24h,
8h, 4h и 1h; Brier хуже константного прогноза; STRONG не отличается от WEAK ни
разу.

**2026-08-13, контрольная модель** (`make control-model`). Градиентный бустинг
на тех же 32 признаках, без графа состояний, с той же целевой и на том же
разбиении, с purged walk-forward CV — критерий не прошёл ни на одной из четырёх
монет: AUC 0.504–0.536. Отсюда вывод: доводить структуру графа как способ найти
сигнал бессмысленно, менять надо источники данных или предмет предсказания.

Практические следствия: профили оценки не калибруются, план работ
[`docs/plan_priority_2026-08-12.md`](docs/plan_priority_2026-08-12.md) не
выполняется дальше Ш0, а граф состояний остаётся рабочим **описательным**
инструментом — разметка истории, имена состояний, переходы, контекст событий.

Разборы с числами: [`btc-graph-processing/docs/development_log.md`](btc-graph-processing/docs/development_log.md),
разделы 26 и 31.

## Репозиторий и история

До 13 августа 2026 подпроекты жили в отдельных репозиториях. Сейчас это
**монорепо**, а их история **втянута сюда целиком**, с переписанными путями —
поэтому работает нативно:

```bash
git log --oneline -- btc-graph-processing/btcproc/symbols.py
git blame btc-graph/src/scorer/candidate_scorer.py
```

Старые репозитории (`trading-developer/btc-market-candidate-agent` и
`…-processing`) остаются read-only архивом; писать в них больше не нужно.
