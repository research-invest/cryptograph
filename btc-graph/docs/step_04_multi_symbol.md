## Зачем

Сейчас система умеет ровно одну монету. Дело не в том, что где-то написано `BTCUSDT`
(это как раз мелочь), а в двух более глубоких вещах:

1. **Все пороги оценки — абсолютные и откалиброваны под BTC.** `sample_size > 1000`,
   `repeatability_months > 15`, `monthly_concentration < 0.10`, `win_rate > 0.70` — это
   характеристики рынка с 10-летней историей и высокой ликвидностью. Монета с двумя
   годами истории и в 50 раз меньшим объёмом никогда не наберёт эти ступени: **все её
   кандидаты уедут в `WEAK`, и система для неё просто замолчит** — не потому, что
   кандидатов нет, а потому что линейка чужая.
2. **Данные разных монет столкнутся в хранилищах.** `group_id`, `transition_id`,
   `configuration_hash`, `candidate_family_key` — идентификаторы **внутри** графа одной
   монеты. Генератор выдаёт `42->1` и для BTC, и для ETH. Сейчас они схлопнутся в один
   узел Neo4j, один ключ дедупликации Redis и одну «семью» в фильтре.

Шаг 4 закрывает обе: выносит всю калибровку в **профиль на символ** и разводит данные
монет по всем четырём хранилищам.

## Дизайн: профиль оценки на символ

### Форма конфига

Профиль — YAML-файл на монету в `config/symbols/`, с наследованием от `_default.yaml`.
Не Python-модуль и не таблица в БД — по трём причинам: конфиг правится без `make build`
(монтируется volume'ом), лежит в git рядом с кодом (видно, кто и когда двигал пороги),
и не требует живого Postgres, чтобы посчитать score.

```
config/
└── symbols/
    ├── _default.yaml      ← базовый профиль = текущий хардкод, слово в слово
    ├── BTCUSDT.yaml       ← extends: _default, пустые переопределения
    ├── ETHUSDT.yaml
    └── SOLUSDT.yaml
```

```yaml
# config/symbols/_default.yaml — эквивалент текущего candidate_scorer.py
symbol: _default
version: 1
description: Базовая калибровка под BTCUSDT (перенос хардкода шага 1)

statistical:
  valid_label_pct:       {mode: higher_better, ladder: [[0.85, 1.0], [0.80, 0.7], [0.75, 0.4]], floor: 0.0}
  sample_size:           {mode: higher_better, ladder: [[1000, 1.0], [500, 0.7], [200, 0.4]], floor: 0.1}
  monthly_concentration: {mode: lower_better,  ladder: [[0.10, 1.0], [0.15, 0.7], [0.30, 0.3]], floor: 0.0}
  repeatability_months:  {mode: higher_better, ladder: [[15, 1.0], [12, 0.7], [6, 0.4]], floor: 0.1}

directional:
  win_rate:         {mode: higher_better, ladder: [[0.70, 1.0], [0.65, 0.7], [0.60, 0.4]], floor: 0.1}
  abs_outcome_skew: {mode: higher_better, ladder: [[0.40, 1.0], [0.30, 0.7], [0.20, 0.4]], floor: 0.1}
  fa_ratio:         {mode: higher_better, ladder: [[4.0, 1.0], [3.0, 0.7], [2.0, 0.4]], floor: 0.1}

context:
  context_status:     {fresh: 1.0, stale: 0.0}
  age_bucket:         {age_lt_30: 1.0, age_30_60: 0.75, age_60_120: 0.5, age_gt_120: 0.0}
  trajectory_entropy: {low: 1.0, medium: 0.5, high: 0.0}

rarity:
  event_rarity_bucket: {rare: 1.0, uncommon: 0.7, common: 0.2}
  transition_rarity:   {rare: 1.0, uncommon: 0.7, common: 0.2}
  research_score:      {mode: higher_better, ladder: [[0.85, 1.0], [0.70, 0.6]], floor: 0.2}

weights: {statistical: 0.30, directional: 0.35, context: 0.20, rarity: 0.15}
rating:  {strong_min: 0.75, moderate_min: 0.55}
batch:   {min_quality_score: 0.60, fresh_bonus: 0.05}

validator:
  low_valid_label_pct: 0.70
  very_small_sample_size: 100
  high_monthly_concentration: 0.30
  low_repeatability_months: 3
  false_confidence_research_score: 0.85

llm:
  market_hint: "BTC — самый ликвидный крипторынок, история глубокая"
```

**Семантика `ladder`.** Список `[порог, балл]`, проверяется сверху вниз, сравнение
**строгое**: `higher_better` → `value > порог`, `lower_better` → `value < порог`. Ни одна
ступень не сработала → `floor`. Это ровно текущее поведение — существующие
граничные тесты (`0.85 → 0.7`, а не `1.0`) должны пройти без правок.

**Схема валидируется при загрузке (Pydantic):**
- сумма `weights` = 1.0 ± 1e-6;
- пороги в `ladder` строго монотонны в нужную сторону — иначе ступень недостижима.
  Это машинная защита от повторения audit #1 (мёртвая ветка `age_60_120`);
- все ключи enum-карт покрыты (`age_bucket` содержит все четыре значения `AgeBucket`);
- `strong_min > moderate_min`, все баллы в `[0, 1]`.

### Загрузчик

Новый модуль `src/config/profiles.py`:

```python
def get_profile(symbol: str) -> ScoringProfile      # с кэшем, регистронезависимо
def list_profiles() -> list[str]
def reload_profiles() -> None                        # для тестов и /config/reload
def profile_fingerprint(p: ScoringProfile) -> str    # sha256 нормализованного дампа, 12 симв.
```

- Каталог из `PROFILES_DIR` (default `config/symbols`).
- Загрузка **ленивая, при первом обращении**, а не на импорте — модуль не должен ронять
  API из-за опечатки в YAML одной монеты (порченый профиль → лог + `_default`).
- Неизвестный символ → `_default` + warning-флаг `unknown_symbol_profile` (валидатор
  по контракту не бросает исключений, только помечает).
- **Реестр профилей = whitelist известных монет.** Отдельного списка монет не заводим.

### Версионирование: почему это обязательно

В CLAUDE.md уже зафиксировано: «любая правка порогов делает старые сохранённые
`quality_score` несравнимыми с новыми». С профилями на монету правки станут частыми, и
эта проблема из редкой превращается в постоянную. Поэтому каждая запись помечается
профилем, которым посчитана:

- новые колонки `scoring_profile` (`"ETHUSDT@3"`) и `profile_fingerprint` (`"a1b2c3d4e5f6"`)
  в `candidates` и `candidate_events`;
- `fingerprint` считается от содержимого — правка порога без бампа `version` всё равно
  видна;
- в `/stats/*` и в CAGG `scoring_profile` попадает в `GROUP BY`, чтобы средние не
  склеивали до- и после-калибровочные оценки.

### Кросс-монетная сопоставимость: `quality_score_baseline`

Профильный `quality_score` ранжирует кандидатов **внутри** монеты и по построению не
сравним между монетами (у ETH ступень `sample_size` вдвое ниже). Чтобы не потерять
вопрос «какая монета сегодня интереснее», считаем **два** числа:

- `quality_score` — по профилю монеты, идёт в rating, фильтры, отчёты, pub/sub;
- `quality_score_baseline` — тем же скорером, но профилем `_default`; только пишется
  в БД и отдаётся в API.

Стоит один лишний вызов чистой функции. `rating` считается **только** от профильного —
двух рейтингов не заводим.

## Что меняется в коде

### `src/scorer/candidate_scorer.py` — из хардкода в data-driven

```python
def _ladder(value: float, spec: LadderSpec) -> float: ...
def _map(key: str, spec: dict[str, float]) -> float: ...

def score_candidate(candidate: Candidate, profile: ScoringProfile | None = None) -> ScoreBreakdown
def get_rating(quality_score: float, profile: ScoringProfile | None = None) -> str
```

- `profile=None` → `get_profile(candidate.symbol)`; у `get_rating` → `_default`.
  Все существующие вызовы остаются рабочими.
- `WEIGHTS`, `RATING_STRONG_MIN`, `RATING_MODERATE_MIN`, `_AGE_SCORE` остаются как
  read-only алиасы на `_default` (их импортируют тесты), помечены как deprecated.
- `win_rate_for()` и `fa_ratio_for()` **не трогаем**: `None` для short — это свойство
  данных, а не калибровки, и в профиль не выносится. Инвариант «для short ось
  `directional` считается по двум критериям» сохраняется.
- `ScoreBreakdown` получает поля `profile: str` и `fingerprint: str`.

### Изоляция данных

**Neo4j (обязательно, иначе граф испортится молча).**

```cypher
MERGE (g:MarketGroup {symbol: $symbol, group_id: $group_id})
```

- constraint `CREATE CONSTRAINT market_group_key IF NOT EXISTS FOR (g:MarketGroup) REQUIRE (g.symbol, g.group_id) IS UNIQUE;`
- `symbol` кладётся и на ребро `TRANSITION` (для запросов без обхода узлов);
- миграционный скрипт `scripts/migrate_graph_symbol.cypher`: проставить
  `symbol = 'BTCUSDT'` всем существующим узлам и рёбрам **до** создания constraint;
- `find_transitions_to_group` и `get_group_info` получают обязательный `symbol`.

**Redis.** Все ключи и канал уходят под префикс символа:

| Было | Стало |
|---|---|
| `candidate:hash:{hash}` | `{symbol}:candidate:hash:{hash}` |
| `evaluation:{id}` | `{symbol}:evaluation:{id}` |
| `btc:strong_candidates` | `candidates:strong:{symbol}` + дублирование в общий `candidates:strong:all` |

Стрим приёма остаётся **один** (`candidates:stream`, группа `candidates:workers`) — символ
уже лежит в payload, плодить consumer-группы незачем. Старые ключи `btc:*` не мигрируем:
TTL 30 минут, протухнут сами; для стрима — переименование при пустой очереди
(проверить `XLEN` перед деплоем).

**PostgreSQL — миграция `004_multi_symbol.py`:**
- PK `candidates` → `(symbol, candidate_id)`; `candidate_events` → `(event_time, symbol, candidate_id)`;
- `symbol` теряет `server_default='BTCUSDT'`, становится `nullable=False`;
- составные индексы: `(symbol, quality_score DESC)`, `(symbol, rating, direction)`,
  `(symbol, configuration_hash)`, `(symbol, family_key)`;
- новые колонки `scoring_profile`, `profile_fingerprint`, `quality_score_baseline`;
- **пересоздание обоих continuous aggregates** с `symbol` и `scoring_profile` в `GROUP BY`
  (CAGG нельзя `ALTER` — только `DROP` + `CREATE` + refresh);
- бэкфилл существующих строк: `symbol='BTCUSDT'`, `scoring_profile='legacy@0'`.

⚠️ Пересоздание CAGG пересобирает агрегаты из `candidate_events`, а у него retention
90 дней — **агрегаты старше 90 дней будут потеряны безвозвратно**. Если история важна,
до миграции снять дамп `hourly_candidate_stats` / `daily_group_stats` в отдельные таблицы.

## Как подбирать веса и ступени для новой монеты

Это главная содержательная часть шага — «поиграться с весами» должно быть
воспроизводимой процедурой, а не подкруткой на глаз.

### Правило 1: сначала ступени, потом веса

Веса перераспределяют вклад осей, но **ничего не чинят, если ось вырождена**. Если у
монеты медианный `sample_size` = 180, ось `statistical` у всех кандидатов даст ~0.25
независимо от веса. Сначала ступени, веса — вторым проходом.

### Правило 2: ступени — от перцентилей выборки монеты, не от круглых чисел

Скрипт `scripts/calibrate_profile.py`:

```bash
python scripts/calibrate_profile.py --symbol ETHUSDT \
    --input dumps/eth_candidates.jsonl \
    --out config/symbols/ETHUSDT.yaml --dry-run
```

Что делает:
1. читает JSONL кандидатов монеты (выгрузка из btc-graph-processing), парсит `Candidate`;
2. по каждому сырому признаку строит распределение и предлагает ступени как перцентили:
   `higher_better` → p90/p75/p50 → 1.0/0.7/0.4; `lower_better` → p10/p25/p50;
3. считает выборку **дважды** — профилем `_default` и предложенным — и печатает отчёт:
   - распределение `STRONG/MODERATE/WEAK` до и после,
   - медиану и IQR `quality_score`,
   - **вклад каждой оси в итог** (`weight × среднее оси`) и дисперсию оси,
   - топ-10 кандидатов с разбивкой по осям;
4. с `--out` пишет YAML-черновик (`--dry-run` — только отчёт).

Автоматика даёт **черновик**, не финальный профиль: перцентили не знают, что
`sample_size = 120` статистически несостоятелен независимо от того, что это p90 монеты.

**Ступеней объёма выборки с 2026-08-13 две.** `effective_sample_size` считает
независимые реализации перехода, `sample_size` — строки снимков (их 1.5…2.8 на
реализацию). Работает первая, если она есть в профиле И поле есть у кандидата;
иначе вторая. Обе калибруются по своему распределению, каждая по своему —
смешивать нельзя: ступень по реализациям примерно вдвое ниже, и перепутанные
местами они дадут правдоподобные, но неверные оценки. В `_default` ступени по
реализациям нет намеренно: baseline обязан мерить всех одной линейкой.

**Перекалибровка существующей монеты — не то же самое, что заведение новой.**
`calibrate_profile.py` сравнивает черновик с `_default`; при перекалибровке
нужен вопрос «что на новой выгрузке делает профиль, который сейчас работает», и
его задаёт `scripts/profile_shift.py`. Опыт 2026-08-13: профили успели отстать
не только из-за правок расчёта, но и из-за переобучения модели состояний — у
двух монет из четырёх доля STRONG упала практически до нуля (журнал btc-graph,
раздел 6.3). Полное переобучение обязано тянуть за собой эту проверку.

### Правило 3: три диагноза, которые читаются по распределению

| Симптом | Диагноз | Что двигать |
|---|---|---|
| >90% кандидатов `WEAK`, медиана ~0.35 | ступени взяты с BTC, монете недостижимы | ступени вниз (перцентили), веса не трогать |
| >40% `STRONG` | ступени слишком мягкие — score перестал различать | ступени вверх и/или `strong_min` вверх |
| Дисперсия оси < 0.05 | ось константна, её вес просто сдвигает всем score на константу | перераспределить её вес на различающие оси |

### Правило 4: веса отражают, чему на этой монете можно верить

Отправная точка (не догма — проверять отчётом):

| Тип монеты | statistical | directional | context | rarity | Почему |
|---|---|---|---|---|---|
| BTC (эталон) | 0.30 | 0.35 | 0.20 | 0.15 | текущая калибровка |
| Крупный альт (ETH, SOL) | 0.35 | 0.30 | 0.20 | 0.15 | выборки короче → надёжность важнее перекоса |
| Низколиквидная монета | 0.40 | 0.25 | 0.20 | 0.15 | directional шумит: перекос на 200 случаях чаще артефакт, чем сигнал |
| Монета с историей < 1 года | 0.40 | 0.25 | 0.25 | 0.10 | rarity недостоверна — «редкость» на коротком окне не редкость |

Логика: **чем меньше данных, тем больше веса статистической надёжности и меньше —
directional и rarity**, потому что именно они на малых выборках дают ложную уверенность.

### Правило 5: два обязательных якоря

1. **Регрессия BTC.** `BTCUSDT.yaml` — пустое наследование от `_default`; эталонный
   кандидат из ТЗ обязан давать тот же `quality_score` до знака после запятой. Любая
   правка `_default` ломает этот тест намеренно и требует обновления README (раздел
   «Как читать результат оценки») — правило из CLAUDE.md остаётся в силе.
2. **Sanity-кандидат монеты.** Для каждой новой монеты в `tests/fixtures/` кладётся один
   реальный кандидат с зафиксированным ожидаемым рейтингом. Профиль, который переводит
   его через границу рейтинга, — сломанный профиль.

### Правило 6: калибровка — событие, а не правка

Меняешь профиль → бампаешь `version` → старые записи остаются со старым
`scoring_profile`, новые пишутся с новым. Не пересчитываем и не мигрируем: сравнение
идёт внутри одного `scoring_profile`. Это и есть причина, по которой fingerprint пишется
в БД.

## Открытые вопросы (решить до 4.3) — ✅ все закрыты

Ответы получены чтением кода btc-graph-processing и проверены на живом стеке.

| # | Вопрос | Ответ | Что из этого следует |
|---|---|---|---|
| 1 | Глобально ли уникален `candidate_id`? | **Да.** `candidate_id = hash(symbol, ts, transition_id, event_block_id, offset)`, `candidates/builder.py:323` | Составной PK нужен для локальности индексов и как страховка от смены схемы id, а не от коллизий |
| 2 | Включает ли `configuration_hash` символ? | **Нет** (было). Исправлено на стороне генератора | Префикс символа в ключе Redis всё равно нужен — как защита от старого генератора и от возврата к прежней схеме хэша |
| 3 | Отдаёт ли генератор `symbol` в payload? | **Да, всегда** | Маппинг на приёме не обязателен; `?symbol=` у `/queue/enqueue` оставлен для источников, которые поле не шлют |
| 4 | Общий ли словарь `group_id`? | **Нет, свой на монету** | Кросс-монетные связи в графе не заводим; ключ узла — `(symbol, group_id)` |
| 5 | Нужна ли per-symbol модель LLM? | **Отложено**, как и предлагалось | `llm.market_hint` в профиле есть, `llm.model` — нет |

### Исходный текст вопросов

1. **Гарантирует ли генератор глобальную уникальность `candidate_id` между монетами?**
   Если да — составной PK нужен только для локальности индексов; если нет — он
   обязателен, иначе ETH перезапишет BTC. Уточнить в btc-graph-processing.
2. **`configuration_hash` считается по данным монеты или включает символ?** От этого
   зависит, нужен ли префикс символа в ключе дедупликации (по умолчанию — считаем, что
   не включает, и префикс нужен).
3. **Отдаёт ли генератор `symbol` в payload уже сейчас?** Если нет — нужен маппинг на
   стороне приёма (`/queue/enqueue?symbol=`) до того, как поле станет обязательным.
4. **Общий ли `group_id`-словарь у монет** (кластеризация обучена на всех сразу) или
   свой на монету? Если общий — `group_id` семантически сопоставим между монетами, и
   в графе имеет смысл дополнительно завести кросс-монетные связи. По умолчанию
   считаем, что свой на монету.
5. **Нужна ли per-symbol модель LLM?** Дешёвая haiku для потоковых монет и sonnet для
   BTC — одна строка в профиле (`llm.model`), но добавляет ещё один источник
   несопоставимости текстов. Предлагаю отложить.

## Отступления от плана (заполнено по факту реализации, 2026-08-08)

План выдержан целиком; ниже — четыре места, где реальные данные заставили
сделать не то, что было написано. Каждое обнаружено на живой выгрузке, а не
придумано заранее, поэтому и записано здесь, а не в исходном тексте.

### 1. Калибратор считает по свежему окну, а не по всей истории (`--tail`)

**Было в плане:** «читает JSONL кандидатов монеты… по каждому сырому признаку
строит распределение и предлагает ступени как перцентили».

**Проблема:** `sample_size` кандидата — число накопленных аналогов на момент
выпуска, оно монотонно растёт по истории. Кандидат 2018 года видит сотню
случаев, кандидат 2026-го — тысячи. Перцентили по всей выгрузке ставят планку
туда, где сидели бедные ранние годы, а профиль применяется к сегодняшним
кандидатам.

**Измерено на ETH:** профиль по всей истории даёт 10% STRONG на калибровочной
части и **26% на свежей трети**. То есть на живом потоке рейтинг оказался бы
вчетверо щедрее задуманного.

**Решение:** `--tail` (по умолчанию последняя четверть выгрузки). Остаточный
дрейф структурный и никуда не девается: ETH 1.0% → 1.9%, SOL 1.2% → 2.9%.
Порог вмешательства записан в самих профилях.

### 2. Границы рейтинга целятся в селективность эталона (`--target-strong`)

**Было в плане:** про целевую долю STRONG ничего не сказано; первая реализация
взяла 10% как «STRONG должен быть редким».

**Проблема:** BTC на своих данных даёт 1.0% STRONG. При цели 10% ETH выдавал бы
STRONG вдесятеро щедрее, и сводный список «что сегодня сильного» заливала бы
монета с самой низкой планкой. Рейтинг сравним только внутри монеты — но
смотрит-то человек общий список.

**Решение:** цель по умолчанию `--target-strong 0.01` / `--target-moderate 0.39`
— ровно селективность эталона.

### 3. Схема профиля проверяет достижимость верхней ступени

**Было в плане:** «пороги в `ladder` строго монотонны в нужную сторону».

**Проблема:** монотонности мало. На выгрузке ETH калибратор предложил
`valid_label_pct: [[1.0, 1.0], [0.9936, 0.4]]` — p90 признака равен единице,
потому что у девяти кандидатов из десяти метки валидны все до одной. Сравнение
строгое, доля больше единицы не бывает: верхнюю ступень не взял бы никто, а
потолок критерия молча упал бы до 0.4. Монотонность соблюдена (`1.0 > 0.9936`),
проверка проходит.

Это тот же класс дефекта, что audit #1, но причина другая: не порядок ступеней,
а область значений признака.

**Решение:** `_validate_reachable` для полей из `_SHARE_FIELDS` (доли,
ограниченные единицей) — в схеме профиля; плюс калибратор такие пороги
выбрасывает сам.

### 4. `description` не наследуется от `_default`

Мелочь, но заметная: свежий `ETHUSDT@1` показывал себя в `/config/symbols` как
«базовую калибровку под BTCUSDT», унаследовав чужое описание. Реестр
дезинформировал. Поле вынесено в список ненаследуемых.

### Содержательный вывод, которого в плане не было

План строился на гипотезе «альткоину тесно в биткоиновой линейке». **На ETH
вышло ровно наоборот.** У него граф состояний грубее (29 узлов против 43),
поэтому на конфигурацию приходится больше исторических случаев, и ось
`statistical` насыщалась: среднее 0.827 при разбросе 0.121 — почти все
кандидаты у потолка, ось перестала различать. Калибровка подняла ступени
`sample_size` (1497/717/242 против 1000/500/200) и вернула ей разрешающую
способность: 0.495 при разбросе 0.222. То же у SOL.

Направление, в которое нужно двигать ступени новой монеты, заранее неизвестно.
Правило для будущих монет: **проверять фактом, а не ожиданием.**
