# Crypto Graph — API кандидатов, версия 1

Описание для сервиса-потребителя. Самодостаточно: этот файл можно отдать
интегратору или положить целиком в промпт чужому агенту — ничего, кроме
адреса и ключа, для работы с API знать не нужно.

| | |
|---|---|
| Базовый URL | `https://crypto-graph.selll.ru` (боевой контур), `http://localhost:8000` (локально) |
| Префикс | `/api/v1` |
| Формат | JSON, UTF-8 |
| Аутентификация | ключ в заголовке, см. §2 |
| Версия контракта | `1.0.0` |

---

## 1. Что отдаёт этот API и как это читать

Система размечает историю рынка на состояния и выпускает **кандидатов** —
досье вида «такая конфигурация рынка уже встречалась 1339 раз, в 74% случаев
цена дальше шла вверх», с оценкой качества этого досье (`quality_score`) и
рейтингом (`STRONG` / `MODERATE` / `WEAK`).

Четыре свойства данных, без которых интеграция получится неверной. Это не
дисклеймер, а описание того, что означают числа.

**1.1. Кандидат — исследовательская идея, а не торговый сигнал.** В нём нет
точки входа, стопа, тейка и размера позиции, и они не появятся. Утверждение
«после такой конфигурации чаще бывало вверх» проверялось на отложенной части
истории и **не подтвердилось**: точность по направлению 0.497–0.516 при
доверительных интервалах, накрывающих 0.5. Строить на этих полях
автоматическое исполнение сделок нельзя; они годятся для отбора ситуаций,
которые смотрит человек.

**1.2. `quality_score` сравним только внутри одной монеты.** Пороги оценки
калибруются на каждую монету отдельно (у монеты с годовой историей и у BTC
разные линейки), поэтому 0.72 у ETH и 0.72 у BTC — разные вещи. Для сравнения
между монетами есть `quality_score_baseline` — тот же кандидат по единой
неподвижной мерке. Сортировка «что сегодня интереснее по всем монетам» строится
по нему.

**1.3. Оценки сравнимы только внутри одной метки калибровки.** Пара
`(scoring_profile, profile_fingerprint)` едет рядом с каждым числом.
Перекалибровка профиля монеты меняет линейку, а сохранённые ранее оценки не
пересчитываются — поэтому агрегаты («средний score за месяц», «доля STRONG»)
корректны только внутри одной такой пары. Смена метки — штатное событие, а не
инцидент.

**1.4. `rating` считается от `quality_score`, а не от baseline**, и второго
рейтинга не существует. Если нужен единый порог по всем монетам — это порог по
`quality_score_baseline`, но тогда он ваш, а не системный.

## 2. Аутентификация

Ключ выдаётся владельцем контура. Передаётся одним из двух способов:

```http
X-API-Key: <ключ>
```
```http
Authorization: Bearer <ключ>
```

Оба равнозначны; второй существует для клиентов, которым произвольный
заголовок прописать негде.

| Код | Когда | Что делать |
|---|---|---|
| `200` | всё хорошо | — |
| `401` | ключа нет либо он неизвестен | проверить заголовок; ретраить бессмысленно |
| `404` | кандидат не найден | — |
| `422` | параметр запроса не проходит валидацию | смотреть `detail`, это ошибка клиента |
| `500` | сбой на стороне сервиса | повторить с экспоненциальной задержкой |
| `503` | API не настроено (ключи не заданы на сервере) | не ретраить, сообщить владельцу контура |

Ключ ротируется добавлением: у сервиса может быть несколько действующих
ключей одновременно, поэтому переход делается «выдали новый → перевели
клиента → отозвали старый» без окна недоступности.

Проверка связи — `GET /api/v1/ping`: ручка не ходит в базу и отвечает даже
при недоступном хранилище, поэтому годится и как health-check интеграции, и
как первый шаг разбора «у нас всё сломалось».

## 3. Ручки

### 3.1. `GET /api/v1/ping`

Проверка ключа.

```json
{"status": "ok", "key": "bot"}
```

`key` — метка вашего ключа на стороне сервиса (нужна для разбора логов).

---

### 3.2. `GET /api/v1/symbols`

Монеты, по которым есть сохранённые оценки.

```json
{
  "symbols": [
    {"symbol": "BTCUSDT", "has_profile": true,  "scoring_profile": "BTCUSDT@2"},
    {"symbol": "PUMPUSDT", "has_profile": true, "scoring_profile": "PUMPUSDT@1"}
  ]
}
```

`has_profile: false` означает, что монету считали общей линейкой, а не её
собственной; у таких кандидатов в `warning_flags` есть `unknown_symbol_profile`.
Список меняется редко — кэшируйте.

---

### 3.3. `GET /api/v1/candidates` — основная ручка

Кандидаты монеты с оценками, новые сверху.

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `symbol` | string | **обязателен** | Тикер (`BTCUSDT`), регистр не важен. `all` — смешанная выдача по всем монетам |
| `rating` | string | все | `STRONG`, `MODERATE`, `WEAK`; несколько — через запятую |
| `direction` | string | оба | `long` или `short` |
| `min_score` | float `0..1` | — | Нижняя граница `quality_score` |
| `hours` | int ≥ 1 | вся история | Только оценённые за последние N часов |
| `order` | string | `recent` | `recent` — по времени оценки вниз; `score` — по качеству вниз |
| `limit` | int `1..200` | `50` | Размер страницы |
| `offset` | int ≥ 0 | `0` | Смещение |

`symbol` обязателен намеренно: выдача без монеты перемешивает рынки, а
профильные `quality_score` между монетами не сравнимы (§1.2). Смешанная
выдача возможна, но пишется явно — `symbol=all`; при ней `order=score`
сортирует по `quality_score_baseline`, иначе «топ» означал бы «монета с самой
щедрой калибровкой».

**Ответ**

```json
{
  "symbol": "BTCUSDT",
  "total": 128,
  "limit": 50,
  "offset": 0,
  "count": 50,
  "order": "recent",
  "items": [ /* см. §4 */ ],
  "notes": ["…"]
}
```

`total` — сколько строк подходит под фильтр целиком, а не на странице: по нему
строится пагинация (`offset + count < total` — есть ещё). `notes` — короткие
оговорки о смысле чисел; их стоит показывать пользователю, если ваш сервис
отображает оценки человеку.

---

### 3.4. `GET /api/v1/candidates/{symbol}/{candidate_id}`

Один кандидат. Параметр `include_raw=true` добавит `raw_payload` — исходное
досье генератора целиком (около 40 полей: счётчики исходов, перцентили
движения, параметры блока событий). В остальном ответ совпадает с элементом
списка. Нет такого кандидата — `404`.

`raw_payload` не является частью контракта версии 1: состав полей внутри него
задаёт генератор и может меняться. Опирайтесь на поля верхнего уровня.

## 4. Поля кандидата

```json
{
  "candidate_id": "245be5fb0908d59f6e89",
  "symbol": "BTCUSDT",
  "evaluated_at": "2026-09-01T12:00:00+00:00",

  "quality_score": 0.81,
  "quality_score_baseline": 0.79,
  "rating": "STRONG",
  "direction": "long",
  "scoring_profile": "BTCUSDT@2",
  "profile_fingerprint": "9c1f…",

  "win_rate": 0.7446,
  "favorable_adverse_ratio": 4.33,

  "horizon": "24h",
  "sample_size": 1339,
  "valid_label_pct": 0.8596,
  "repeatability_months": 19,
  "monthly_concentration": 0.0999,
  "long_outcome_share": 0.7446,
  "outcome_skew": 0.4891,

  "context_status": "stale",
  "transition_id": "42->1",
  "transition_rarity": "common",
  "current_group_id": 1.0,
  "previous_group_id": 42.0,
  "event_block_id": "event_block_098200",
  "family_key": "1.0|42->1|event_block_098200|long_skew",
  "configuration_hash": "0f8928cb2fc1547b",

  "warning_flags": ["stale_context"],
  "range": {"lift": 1.31, "regime": "wide", "expected_ratio_p50": 1.2, "expected_ratio_p90": 2.4}
}
```

### Идентификация

| Поле | Тип | Смысл |
|---|---|---|
| `candidate_id` | string | Идентификатор кандидата. Уникален глобально, но **ключом считайте пару `(symbol, candidate_id)`** — все ручки адресуют кандидата так |
| `symbol` | string | Тикер |
| `evaluated_at` | datetime, UTC | Когда кандидат оценён. По нему идёт сортировка `recent` и работает фильтр `hours` |
| `configuration_hash` | string | Хэш конфигурации рынка. Один и тот же хэш у разных `candidate_id` — норма |
| `family_key` | string | Семейство близких кандидатов; система уже оставила из семейства лучшего |

### Оценка

| Поле | Тип | Смысл |
|---|---|---|
| `quality_score` | float `0..1` | Качество досье по линейке ЭТОЙ монеты. Сравнивать только внутри монеты и метки калибровки |
| `quality_score_baseline` | float `0..1` | То же по единой мерке — **единственное межмонетно сравнимое число** |
| `rating` | enum | `STRONG` / `MODERATE` / `WEAK`, считается от `quality_score` |
| `direction` | enum | `long` / `short` — сторона, к которой относится статистика |
| `scoring_profile` | string | Метка калибровки, например `BTCUSDT@2` |
| `profile_fingerprint` | string | Отпечаток содержимого профиля: ловит правку порогов без смены версии |
| `warning_flags` | string[] | Замечания валидатора (например `stale_context`, `very_small_sample`, `unknown_symbol_profile`). Пустой список — норма |

### Статистика конфигурации

| Поле | Тип | Смысл |
|---|---|---|
| `win_rate` | float `0..1` \| null | Доля исторических исходов в сторону `direction` |
| `favorable_adverse_ratio` | float \| null | Отношение благоприятного хода к неблагоприятному (перцентили p70/p80). **У `short` всегда `null`** — симметричных полей в исходных данных нет; это не пропуск и не ошибка |
| `horizon` | string | Горизонт исходов, например `24h` |
| `sample_size` | int | Сколько исторических случаев в выборке |
| `valid_label_pct` | float `0..1` | Какая доля случаев дала пригодную метку исхода |
| `repeatability_months` | int | В скольких разных месяцах встречалась конфигурация — грубая проверка «не одна эпоха» |
| `monthly_concentration` | float `0..1` | Доля самого «урожайного» месяца. Высокое значение при большом `sample_size` означает, что вся статистика набрана в один период |
| `long_outcome_share` | float `0..1` | Доля исходов вверх (всегда про long, независимо от `direction`) |
| `outcome_skew` | float `-1..1` | Перекос исходов, `2 × long_outcome_share − 1` |

### Разметка графа состояний

| Поле | Тип | Смысл |
|---|---|---|
| `current_group_id` / `previous_group_id` | float | Номера состояний рынка |
| `transition_id` | string | Переход между ними, `"42->1"` |
| `transition_rarity` | enum | `rare` / `uncommon` / `common` |
| `event_block_id` | string | Идентификатор набора рыночных событий на баре |
| `context_status` | enum | `fresh` / `stale` — свежесть контекста |

**Номера состояний осмысленны только внутри одной монеты и одного обучения
модели.** Модель переобучается еженедельно и перенумеровывает состояния:
«состояние 7» до и после — разные рынки. Не храните их как справочник и не
сравнивайте между монетами; для устойчивой группировки берите
`family_key` или `configuration_hash`.

### Блок `range` — прогноз размаха

| Поле | Тип | Смысл |
|---|---|---|
| `lift` | float \| null | Во сколько раз ожидаемый размах шире тривиального прогноза. **Это то, что стоит показывать** |
| `regime` | string \| null | `wide` / `normal` / `narrow` |
| `expected_ratio_p50` / `expected_ratio_p90` | float \| null | Квантили размаха за горизонт, нормированного на текущую волатильность |

Три оговорки:

* **`null` — штатное значение, а не ошибка.** Полей нет у кандидатов,
  выпущенных до появления модели размаха, и у монет, чья модель не прошла
  калибровку (коротким историям система числа не даёт). `null` означает
  «система про размах здесь ничего не говорит», а не «размах обычный»;
* **показывать надо `lift`, а не квантили.** Абсолютные квантили наполовину
  объясняются часом суток и недавней волатильностью, то есть показывают время
  дня не меньше, чем рынок. Относительная величина от этого свободна;
* содержательно `lift` ближе к «текущая волатильность необычна относительно
  своей суточной нормы», чем к «рынок пойдёт шире обычного».

## 5. Примеры

```bash
BASE=https://crypto-graph.selll.ru
KEY=<ключ>

# проверка связи
curl -sH "X-API-Key: $KEY" "$BASE/api/v1/ping"

# сильные long-кандидаты BTC за сутки
curl -sH "X-API-Key: $KEY" \
  "$BASE/api/v1/candidates?symbol=BTCUSDT&rating=STRONG&direction=long&hours=24"

# что интереснее всего сейчас по всем монетам
curl -sH "X-API-Key: $KEY" \
  "$BASE/api/v1/candidates?symbol=all&order=score&limit=10"

# один кандидат с исходным досье
curl -sH "X-API-Key: $KEY" \
  "$BASE/api/v1/candidates/BTCUSDT/245be5fb0908d59f6e89?include_raw=true"
```

```python
import requests

S = requests.Session()
S.headers["X-API-Key"] = KEY

def fresh_strong(symbol: str, hours: int = 24) -> list[dict]:
    """Свежие STRONG-кандидаты монеты, со всеми страницами."""
    items, offset = [], 0
    while True:
        r = S.get(f"{BASE}/api/v1/candidates", params={
            "symbol": symbol, "rating": "STRONG", "hours": hours,
            "limit": 200, "offset": offset,
        }, timeout=30)
        r.raise_for_status()
        page = r.json()
        items += page["items"]
        offset += page["count"]
        if offset >= page["total"] or not page["count"]:
            return items
```

Опрос по расписанию: берите `hours` с запасом относительно интервала опроса
(например `hours=2` при опросе раз в полчаса) и отбрасывайте уже виденные
пары `(symbol, candidate_id)` — так пропуск одного цикла не теряет данные.

## 6. Ограничения и режим работы

* **Rate-limit в API отсутствует**, но это не приглашение: разумный интервал
  опроса — от минуты. Генератор выпускает кандидатов раз в полчаса, чаще
  опрашивать нечего.
* **`limit` ограничен 200** на страницу.
* **Только чтение.** Ручек, меняющих состояние, в контракте нет.
* **Пагинация не изолирована от новых данных**: между страницами могут
  появиться свежие оценки и сдвинуть выдачу `order=recent`. Для полной
  выгрузки фиксируйте окно через `hours` либо сверяйтесь по
  `(symbol, candidate_id)`.
* **Время везде UTC**, ISO 8601 с таймзоной.
* Ответы не сжимаются принудительно; `Accept-Encoding: gzip` поддерживается
  прокси.

## 7. Версионирование и совместимость

Версия — в пути (`/api/v1`). Внутри мажорной версии гарантируется:

* **новые поля могут появляться** — клиент обязан игнорировать незнакомые;
* существующие поля не удаляются и не меняют тип;
* значения enum (`rating`, `direction`, `regime`, `transition_rarity`,
  `context_status`) могут пополняться — не падайте на незнакомом значении;
* `null` в любом необязательном поле возможен всегда.

Несовместимые изменения выедут как `/api/v2`; версия 1 при этом продолжит
работать до отдельного уведомления.

Не является контрактом и может меняться без смены версии: содержимое
`raw_payload`, тексты в `notes` и `detail`, состав `warning_flags`, набор
монет.
