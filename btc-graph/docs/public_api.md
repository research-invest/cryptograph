# Публичное API чтения (`/api/v1/*`)

Внешний контракт: отдать наружу уже посчитанные оценки кандидатов по ключу.
Код — `src/api/public.py` (ручки) и `src/api/auth.py` (ключ), тесты —
`tests/test_public_api.py`, журнал решений — `docs/development_log.md`, раздел 13.

**Наружу отдаётся не этот файл, а `docs/api_spec_v1.md`** — описание для
сервиса-потребителя (поля, коды, примеры, политика совместимости), написанное
так, чтобы его можно было отдать как есть, в том числе положить в промпт
чужому агенту. Здесь — внутренний взгляд: почему устроено так и как
выкладывается.

## Что это и чем отличается от остального API

До сих пор весь API проекта был внутренним: он живёт на `127.0.0.1:8000`,
аутентификации не имеет, и `use_llm=true` тратит токены Anthropic по
анонимному запросу. Наружу такое не выставляют.

`/api/v1/*` устроено иначе по трём границам сразу:

* **доступ** — весь роутер закрыт ключом из `API_KEYS`;
* **что происходит по запросу** — только `SELECT`. Ни LLM, ни записи, ни
  перезагрузки конфигурации: утёкший ключ стоит трафика, а не денег и не
  данных;
* **совместимость** — префикс `/api/v1` — внешний контракт, состав полей
  меняется только добавлением. `/evaluate/*` и `/stats/*` таким контрактом
  никогда не были.

## Ключ

`API_KEYS` в `btc-graph/.env` — список через запятую, элемент либо голый ключ,
либо `метка:ключ`. Метка нужна только логам: по ней видно, чей интегратор
шумит, не выписывая сам ключ в журнал.

```
API_KEYS=bot:9f3c...,dashboard:71ae...
```

Сгенерировать: `openssl rand -hex 32`. На боевом контуре ключ создаёт
`deploy/02_configure.sh` (`API_KEYS=prod:<hex>`), в том числе на уже
развёрнутой машине — файл не перезаписывается, строка дописывается.
Посмотреть: `grep '^API_KEYS=' ~/crypto-graph/btc-graph/.env`.

Передавать можно двумя способами — второй ради клиентов, которым произвольный
заголовок прописать негде:

```
X-API-Key: <ключ>
Authorization: Bearer <ключ>
```

Коды: `401` — ключа нет или он неизвестен; `503` — `API_KEYS` пуст.
**Пустое значение никогда не означает «пускать всех»** — это самая дорогая из
возможных ошибок конфигурации, поэтому она отдельная и заметная.

Ключи читаются из окружения на каждом запросе, а не на импорте: смена ключа
требует `make reload`, но не пересборки образа. Сравнение —
`hmac.compare_digest`, чтобы время ответа не подсказывало подбирающему длину
общего префикса.

## Ручки

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/api/v1/ping` | Проверка ключа; в базу не ходит |
| `GET` | `/api/v1/symbols` | Монеты с сохранёнными оценками, `has_profile` у каждой |
| `GET` | `/api/v1/candidates` | Кандидаты монеты с оценками |
| `GET` | `/api/v1/candidates/{symbol}/{candidate_id}` | Один кандидат |

### `GET /api/v1/candidates`

| Параметр | По умолчанию | Значение |
|---|---|---|
| `symbol` | — (обязателен) | Тикер либо `all` для смешанной выдачи |
| `rating` | все | `STRONG` / `MODERATE` / `WEAK`, можно через запятую |
| `direction` | оба | `long` / `short` |
| `min_score` | — | Нижняя граница `quality_score` |
| `hours` | вся история | Только оценки за последние N часов |
| `order` | `recent` | `recent` — по времени вниз, `score` — по качеству вниз |
| `limit` / `offset` | `50` / `0` | Страница, `limit` ≤ 200 |

`symbol` обязателен, а смешанная выдача пишется явным `symbol=all`: выдача без
монеты перемешивает рынки, а профильные `quality_score` между монетами не
сравнимы. При `symbol=all` сортировка `order=score` идёт по
`quality_score_baseline` — иначе «топ» означал бы «монета с самой щедрой
калибровкой».

`total` считается тем же фильтром до пагинации: клиенту нужен признак «есть ли
ещё», а не только размер текущей страницы.

### Форма элемента выдачи

Полный список полей с типами и смыслом — **`docs/api_spec_v1.md`, раздел 4**
(он и уходит наружу). Дублировать его здесь
нельзя: два описания одного контракта расходятся молча, и первым это замечает
интегратор.

Три вещи из него, которые касаются не клиента, а нас (первые две едут в каждом
ответе полем `notes` — тот, кто читает только JSON и никогда не откроет
документацию, это обычный случай, а не исключение):

1. **`quality_score` сравним только внутри одной монеты и одной пары
   `(scoring_profile, profile_fingerprint)`.** Перекалибровка профиля делает
   старые сохранённые оценки несравнимыми с новыми, пересчёта записей нет —
   именно поэтому метка едет рядом с числом.
2. **Кандидат — исследовательская идея, а не торговый сигнал.** Это не
   осторожная формулировка: утверждение «после такой конфигурации чаще бывало
   вверх» проверено на отложенной части истории и **не подтвердилось**
   (корневой `CLAUDE.md`, раздел о замере 2026-08-12).
3. **Блок `range` заполнен не всегда, и `null` там — не ошибка.** Полей нет у
   всего, что выпущено до 2026-08-19, у кандидатов из `train` и у монет, чья
   модель размаха не прошла гейт калибровки.

`win_rate` и `favorable_adverse_ratio` колонками не хранятся — они считаются
из `raw_payload` единственными функциями перевода (`win_rate_for`,
`fa_ratio_for`). У строк, записанных схемой прошлых версий, оба поля будут
`null`: разобрать досье не удалось — значит, число не выдумывается.

## Примеры

```bash
KEY=$(grep '^API_KEYS=' .env | cut -d= -f2- | cut -d: -f2)
BASE=http://localhost:8000

curl -H "X-API-Key: $KEY" "$BASE/api/v1/ping"
curl -H "X-API-Key: $KEY" "$BASE/api/v1/symbols"

# сильные long-кандидаты BTC за сутки
curl -H "X-API-Key: $KEY" \
  "$BASE/api/v1/candidates?symbol=BTCUSDT&rating=STRONG&direction=long&hours=24"

# лучшее по всем монетам: сравнение по baseline
curl -H "X-API-Key: $KEY" \
  "$BASE/api/v1/candidates?symbol=all&order=score&limit=10"

# один кандидат вместе с исходным досье генератора
curl -H "X-API-Key: $KEY" \
  "$BASE/api/v1/candidates/BTCUSDT/245be5fb0908d59f6e89?include_raw=true"
```

Интерактивная схема — `http://localhost:8000/docs`, кнопка **Authorize**
(поле `X-API-Key`).

## Описание для чужих сервисов

`docs/api_spec_v1.md` — текст, который отдаётся интегратору или кладётся в
промпт чужому агенту: только `/api/v1`, без внутренней кухни.

**Правишь сигнатуру или модель ответа в `public.py` — проверь его.**
Описание, которое живёт отдельно от кода, расходится с ним молча.

## Выкладка наружу

Порт 8000 закрыт на `127.0.0.1`, и это проверяет `deploy/01_deploy.sh` — снимать
проверку не нужно. Наружу отдаётся **только префикс `/api/v1/`**, через тот же
nginx, что стоит перед админкой btcproc:

**Сделано 2026-09-02**, руками добавлять не нужно: блок лежит в шаблоне
конфига в `deploy/02_configure.sh` (шаг nginx) и применён на боевой машине.
Адрес API — `https://crypto-graph.selll.ru/api/v1/`.

```nginx
location /api/v1/ {
    proxy_pass http://127.0.0.1:8000;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header Connection "";
}
```

Именно `location /api/v1/`, а не `location /`: за `/` поедут `/evaluate/*`
(токены Anthropic по анонимному запросу), `/queue/enqueue` (запись) и
`/config/*`. Ни одна из них ключа не спрашивает. Проверять надо обе стороны
разом — что `/api/v1/ping` отвечает 401 без ключа и 200 с ключом, и что
`/evaluate/json` снаружи на 8000 НЕ попадает (сейчас он уходит в `location /`,
то есть на админку, и та отдаёт 303 на логин).

Чего в API **нет** и о чём стоит знать заранее:

* **rate-limit.** Ключ отличает клиентов, но не ограничивает их. Если ручка
  окажется под нагрузкой, лимит ставится в nginx (`limit_req_zone`), а не в
  приложении;
* **ротации ключей** как процедуры: несколько ключей в `API_KEYS` живут
  одновременно, поэтому смена делается вручную — добавить новый, перевести
  клиента, убрать старый, `make reload`;
* **записи**. Всё, что меняет состояние, осталось внутренним по построению.
