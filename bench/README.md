# Стенд: Go против Python на реальной тяжёлой задаче контура

Вопрос, ради которого стенд собран: **где в этом проекте Go даст выигрыш,
достаточный, чтобы платить за второй язык в контуре.** Не «быстрее ли Go» —
это известно, — а «быстрее ли он там, где у нас на самом деле уходит время».

Задача выбрана не произвольно. Это единственное место конвейера, где Python
крутит цикл по **десяткам миллионов** строк, а не вызывает numpy/sklearn:
сборка баров 15m из тиковых архивов Bybit (`btcproc/ingest/bybit.py`). Монеты с
Bybit — HYPEUSDT и все будущие не-Binance — иначе не получают ни `trades`, ни
`taker_buy_base` (см. шапку `bybit.py`).

## Что меряется

| | Python | Go |
|---|---|---|
| код | `py/ticks2bars.py` — **боевой** `bybit.parse_ticks` + `ticks_to_bars`, без своей копии логики | `go/main.go` — потоковая агрегация, конвенции перенесены из оригинала построчно |
| память | материализация всех сделок в DataFrame | однопроходный проход, память под бары (тысячи), а не под тики (миллионы) |
| выход | CSV баров, 10 знаков | тот же CSV |

Сверка обязательна и делается `compare.py`: **быстрее всего работает
реализация, считающая не то.** Побитового равенства не требуется — pandas
суммирует объёмы в отсортированном порядке, Go в порядке файла, — порог
относительный.

## Результаты (HYPEUSDT, macOS, Apple, 6 ядер)

Один месяц, `2026-06.csv.gz` — 63 МБ gz, 8.3 млн сделок → 2880 баров:

| | время | пик RSS |
|---|---|---|
| Python (боевой код) | 11.5 с | **4171 МБ** |
| Go, 1 поток | 2.8 с | **5.7 МБ** |
| | **×4.1** | **×730** |

Вся история монеты, 13 месячных архивов — 379 МБ gz, **53.0 млн сделок** →
37 020 баров:

| | время | пик RSS |
|---|---|---|
| Python | 66.0 с | **6080 МБ** |
| Go, 1 поток | 18.1 с | 16.0 МБ |
| Go, 6 потоков | **5.3 с** | 27.6 МБ |
| | **×3.6 / ×12.4** | **×380 / ×220** |

Сверка: 37 020 баров, OHLC совпадает **точно** (0.00e+00), суммы объёмов
расходятся на 1.6e-13 — это последние биты мантиссы, разный порядок сложения.
Выход на 1 и на 6 потоках побайтово одинаков (`cmp`): параллелится разбор
архивов, а сшивание идёт строго по порядку — открытие бара берётся из закрытия
предыдущего, и порядок здесь нарушать нельзя.

## Как это читать честно

* **Память — результат крупнее скорости.** 6 ГБ пика на монету с годом истории
  на VPS с 8 ГБ означает, что ingest живёт только за счёт swap; в памяти
  проекта уже записано, что без swap расчёт ловит OOM killer молча — прогон
  виснет в статусе `running` и блокирует следующий cron. У Go пик не зависит от
  длины архива вообще: он от числа баров, а не сделок. Монета с пятью годами
  тиков питоновским кодом просто не пройдёт, го-шным пройдёт на тех же 30 МБ.
* **Python здесь можно ускорить и без Go** — `multiprocessing` по архивам даёт
  примерно тот же множитель, что `--workers` у Go, и это честно упомянуть.
  Чего multiprocessing не чинит — память: шесть процессов по 4 ГБ хуже одного.
* **Пол для любой реализации — 2.5 с** (`gzip -dc` всех 13 архивов, замер
  внизу). Значит из 18.1 с однопоточного Go около 2.5 с — распаковка, причём
  `compress/gzip` в стандартной библиотеке заметно медленнее системного zlib.
  Запас ещё есть, но он в распаковке, а не в разборе.
* **Это НЕ аргумент за переписывание конвейера.** Признаки, кластеризация,
  бустинг — numpy/sklearn, то есть уже C и BLAS; там Go проиграет, а не
  выиграет. Выигрыш здесь ровно потому, что задача — парсинг и агрегация
  потока, единственный класс задач в проекте, где Python считает сам.

## Запуск

```bash
make -C bench build          # собрать go-версию
make -C bench bench          # один месяц: python, go, сверка
make -C bench bench-full     # вся история HYPEUSDT: python, go×1, go×6, сверка
make -C bench floor          # пол распаковки
```

Go 1.22 берётся из `/usr/local/go/bin` (в PATH его нет). Внешних зависимостей
у go-версии нет — только стандартная библиотека.

## Чего стенд не проверяет

Интеграции нет: go-версия ничего не пишет в БД и не вызывается из `btcproc`.
Это замер, а не подмена загрузчика. Прежде чем ставить go-бинарь в ingest,
нужно решить два вопроса, которых в замере нет: как он попадает на VPS
(сборка в `01_deploy.sh` против готового бинаря в репозитории) и что делает
`sync_recent` с REST-хвостом, который остаётся питоновским.
