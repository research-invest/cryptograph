# Как добавить в систему новый источник сигнала

Документ отвечает на вопрос «хочу завести в систему ончейн-метрики / индекс
страха и жадности / данные по фандингу — что делать». Механизм появился по ходу
задачи про Smart Money (`task_smc_integration.md`) и обкатан на ней: SMC
прошёл весь путь целиком и был отвергнут по результатам замера. Отвергнут
именно потому, что механизм работает — он для того и нужен, чтобы гипотезы
проверялись, а не принимались на веру.

Дальше — порядок действий, цена каждого шага и грабли, на которые уже
наступили.

> **Где лежит этот файл.** До 2026-08-11 на него ссылались `README.md`,
> `development_log.md` и комментарий в `features/events.py`, а сам он лежал
> вне репозитория — в `crypto-graph/docs/`. Три ссылки на несуществующий
> документ хуже, чем его отсутствие: читатель считает, что порядок где-то
> описан, и не пишет свой. Перенесён внутрь репозитория вместе с задачей
> 11-101.

## 1. Три канала, выбирается механически

Величины неоднородны. Часть из них — происшествия, часть — состояния, часть —
непрерывные числа. У каждого канала своя цена, и подходящий выбирается по
свойствам самой величины, а не по важности источника.

```
                        ┌────────────────────────────────────────┐
  Происшествие          │ SIGNATURE_ATOMS → event_block_id       │  ДРОБИТ выборку
  (редкое, дискретное)  │ бит в маске                            │  бюджет 1–2 штуки
                        └────────────────────────────────────────┘

                        ┌────────────────────────────────────────┐
  Состояние             │ CONTEXT_ATOMS → bar_events.context_atoms│  выборку не дробит
  (флаг, длится)        │ только для разбора и замера            │  бюджет свободный
                        └────────────────────────────────────────┘

                        ┌────────────────────────────────────────┐
  Непрерывная величина  │ features/builder.py → вектор           │  МЕНЯЕТ состояния
  (число)               │ → кластеризация → group_id             │  нужен train
                        └────────────────────────────────────────┘
```

Правило:

1. Величина непрерывная и стационарная? → **признак**.
2. Иначе: булев флаг активен больше ~15% времени? → **контекстный атом**.
3. Иначе (редкое дискретное происшествие) → кандидат в **signature-атом**,
   но только если частота срабатывания ниже 3% баров.

Порог в 3% не выдуман. Каждый signature-атом в худшем случае удваивает число
блоков событий, а запас по исторической выборке всего 2.4-кратный: два лишних
атома делают выборку по полному ключу недостижимой навсегда.

**Порядок работы важнее самой маршрутизации.** Сначала завести всё, что можно,
контекстными атомами — это бесплатно и обратимо, — измерить лифт и только
потом двигать выжившие в signature или в признаки. Обратный порядок означает
платить дроблением выборки и переобучением за гипотезу, которая ещё не
проверена. На SMC это дало ответ, не потратив ни одного переобучения.

## 2. Что писать в коде

### 2.1. Детектор

Отдельный модуль в `btcproc/features/`, по образцу `smc.py`. Требования,
каждое из которых уже нарушалось и стоило времени:

* **Только прошлое.** Величина на баре `t` считается из баров до `t`
  включительно. Проверяется тестом вида «посчитать на префиксе истории и на
  полной, общие бары обязаны совпасть». Заглядывание вперёд не падает и не
  выглядит странно — оно просто делает всю историческую статистику фикцией.
* **Стационарность.** Уровень 2018 и 2025 годов должен быть сравним.
  Абсолютные величины нормируются: цены — на ATR, счётчики — через `log1p`,
  доли остаются долями.
* **Масштабная инвариантность.** Тот же рынок, умноженный на 128, обязан дать
  те же значения. Множитель — степень двойки, чтобы тест не ловил заодно
  разъезд округления. Порог, заданный в деньгах, этот тест валит — ровно на
  нём в августе 2026 попался `round_level_touch` (`close % 1000 < 50`): на SOL
  за $150 атом не срабатывал никогда, то есть signature-бит, за который
  платили дроблением блоков, работал на одной монете из трёх.
* **Ограниченные реестры.** Если детектор ведёт список зон или уровней,
  записи обязаны выбывать по возрасту. Иначе проход по 300 тысячам баров
  становится квадратичным.

### 2.2. Флаг в конфиге

Новый источник заводится за выключателем в `btcproc/config.py`, по образцу
`SMCConfig`. Дефолт — **выключено**, пока лифт не измерен. Это не
осторожность ради осторожности: включённый по умолчанию источник попадает в
продакшен раньше, чем появляется ответ, нужен ли он.

Выключателя обычно **два**, потому что у половин источника разная цена:
атомы бесплатны и обратимы, признаки требуют полного `train` и
перенумеровывают `group_id`. Один флаг на обе половины означал бы, что
включение атомов в бою молча делает следующий `train` сорокачетырёхмерным.

### 2.3. Регистрация источника

`btcproc/features/registry.py` — один `FeatureSource` на источник:

```python
FeatureSource(
    name="onchain",                          # войдёт в метку набора
    features_enabled=lambda: config.onchain.features_on,
    atoms_enabled=lambda: config.onchain.enabled,
    feature_columns=(...),
    atom_columns=(...),
    compute=lambda base: onchain.build_cached(base),
)
```

Флаги — функции, а не значения: конфиг читается в момент вызова, иначе
подмена `config.<источник>` в тестах и в скриптах замера перестанет работать.

После этого `build_features` и `detect_atoms` подхватывают источник сами —
цепочки `if config.<источник>.enabled` в них нет и заводить её не надо.

**Чего реестр НЕ делает: он не владеет порядком атомов.** Порядок ключей
`ATOM_FAMILY` задаёт номера битов маски, то есть идентичность всех
исторических `event_block_id`. Собирать `ATOM_FAMILY` из реестра динамически
нельзя: порядок стал бы зависеть от порядка регистрации источников и от того,
какие включены, — и биты поехали бы при каждом изменении конфигурации, без
единой ошибки. Источник поставляет детекторы, а не позиции. Прибито тестом
`test_atom_bit_order_is_pinned` (хэш от `ATOM_BIT`).

### 2.4. Атомы

Добавляются в `ATOM_FAMILY` (`btcproc/features/events.py`) — **только в конец
словаря**, по причине из 2.3. Первые 20 битов прибиты тестом
`test_signature_bits_are_pinned`.

Контекстные атомы дополнительно перечисляются в `CONTEXT_ATOMS`. Они в маску
не входят, поэтому не дробят блоки и **не требуют переобучения** — их можно
включить на работающей системе и сразу мерить.

Колонки заводятся всегда, даже при выключенном флаге — иначе набор имён
зависел бы от окружения.

### 2.5. Признаки и метка набора

Признаки объявляются в `feature_columns` источника; в вектор их подмешивает
сам `build_features`, обходя реестр.

**Метка набора собирается из СОСТАВА, а не нумеруется вручную:** `"v1"`,
`"v1+smc"`, `"v1+onchain"`, `"v1+onchain+smc"` — сортировкой имён включённых
источников (`registry.compose_version`). Композируется на любое их число,
читается глазами, и база без источников остаётся `"v1"`.

> **Почему это важнее, чем кажется.** До 2026-08-11 схема была двоичной:
> «есть SMC → v2, иначе v1». Второй источник по тому же рецепту дал бы
>
> ```python
> if config.smc.features_on:     return "v2"
> if config.onchain.features_on: return "v3"
> return "v1"
> ```
>
> и набор «база + SMC + ончейн» (56 признаков) получил бы метку `"v2"` — ту
> же, что «база + SMC» (44). Дальше `save_feature_set` перезаписал бы
> `feature_sets.names` по первичному ключу, старые строки `features`
> остались бы массивами на 44 значения, а `load_features` построил бы из них
> DataFrame с 56 именами колонок. Ни ошибки, ни предупреждения — просто с
> какого-то момента признаки читаются не под теми именами. Закрыто реестром;
> регрессия — `test_two_sources_never_share_a_label`.

По той же схеме собирается версия набора АТОМОВ (`events.event_version()`) и
пишется в `bar_events.version` / `event_blocks.version`. Версия в первичный
ключ не входит: при смене состава строка перезаписывается, а не удваивается.

**Признаки требуют полного `train`.** Модель состояний хранит имена и число
признаков; обученная на 32 не сможет разметить вектор из 44. Отсюда
перенумерация `group_id` и — обязательный — сброс накопленного графа Neo4j
(его делает сам `train`, см. 4).

**Признак обязан существовать на ВСЕЙ истории монеты — или источник обязан
сказать, что делать с той частью, где его нет.** Это не стилистика: сборка
вектора завершается общим `dropna()` по всем колонкам, поэтому NaN одного
признака выбрасывает строку целиком. Метрики деривативов у BTC начинаются в
2020-09 при барах с 2017-08 — включение их признаков «просто чтобы
посмотреть» обучило бы модель на трети истории, и никакой ошибки в логе. Дыры
по отдельным колонкам у поставщика хуже: они выедают бары **из середины**
истории, точечно.

С 2026-08-15 молчанием этот вопрос не решается: потеря строк сверх базового
набора ограничена `config.features.max_source_row_loss` (2%, переменная
`FEATURES_MAX_SOURCE_ROW_LOSS`), превышение — `ValueError` с именем виновного
источника и его худшей колонки. Прогрев собственных окон источника (месячные
ранги, суточные z-score) в этот порог укладывается; потеря куска истории —
нет. Варианта ответа два, и выбрать надо ОСОЗНАННО, записав решение в ТЗ
источника:

* **нейтральное значение** на период без данных — годится, если «нет данных»
  и «величина посередине» для этого признака означают близкое (ранг, доля);
* **явная граница обучения** — модель учится с даты, где источник есть.
  Честнее для уровней и изменений, но платит историей, а на монете с коротким
  торговым стажем может не оставить выборки вовсе.

Третий вариант — поднять порог — не ответ, а способ временно отложить
вопрос при разовом эксперименте.

**Отдельно: вырожденные бары.** Если признак — логарифм отношения, проверь,
что делает нулевой знаменатель или числитель. Нулевой диапазон бара
(`high == low`) — это максимальное сжатие, а не отсутствие данных, и такой
бар обязан получить граничное значение шкалы, а не NaN. Отсекать надо
**константой**: минимум по ряду зависит от ещё не наступивших баров, то есть
это заглядывание вперёд.

### 2.6. Формулировки — обязательны, а не «потом»

Каждый новый признак получает строку в `naming.AXES`, каждый новый атом — в
`naming.ATOM_LABELS` (`btcproc/states/naming.py`). Это не косметика и не
отложенная задача.

Признак без формулировки не даёт ни ошибки, ни предупреждения: он просто
выпадает из подписи, и состояние, выделяющееся именно им, называется «рынок
около среднего». То есть подпись не беднеет, а **начинает врать** — отличие
есть, а сказано, что его нет. Атом без подписи уходит в интерфейс сырым
идентификатором: `sweep_low_reclaim` читается ровно так же, как `group_id 42`.

Обе полноты стерегутся тестами в обе стороны — и по всему набору
(`test_every_feature_has_a_phrase`, `test_atom_labels_cover_all_atoms`), и
по реестру источников (`test_every_registered_feature_has_a_phrase`,
`test_every_registered_atom_has_a_russian_label`). Второй комплект важен
именно для новых источников: он падает от того, что источник приехал
наполовину описанным, не требуя правки списков в самих тестах.

Осознанное исключение оформляется через `naming._UNNAMED` с объяснением, а не
молчанием.

## 3. Как мерить: три проверки, все обязательны

### 3.1. Частоты и корреляции — до интеграции

`scripts/smc_frequencies.py` как образец. По каждому детектору:

* частота срабатывания — проходит ли бюджет signature;
* максимальная корреляция с существующими атомами и признаками — **выше 0.9
  означает дубликат под новым именем**, такой не нужен нигде;
* условная вероятность относительно похожих существующих атомов — выше 0.8
  означает, что новый пересказывает старый;
* **зеркальные пары внутри самого набора** (раздел `mirror`) — детекторы с
  |r| ≥ 0.5 друг с другом входят в поправку на множественные сравнения как
  ОДНА гипотеза. `in_discount` и `in_premium` — один эффект, измеренный с
  двух сторон, и считать их двумя подтверждениями нельзя;
* распределение по годам — детектор, чья частота гуляет в разы между эпохами,
  измеряет режим, а не рынок.

### 3.2. Меняется ли структура состояний — только с контролем на шуме

`scripts/compare_state_granularity.py`, калибровка — `scripts/calibrate_split_gain.py`.

Наивная проверка «изменилось ли число состояний после добавления признаков»
**не работает**. Добавление признаков меняет геометрию пространства, и если
порог дробления зависит от размерности, число состояний поменяется от любых
новых признаков — хоть от случайных.

Поэтому обязателен контроль: те же признаки, **перемешанные по строкам**. Та
же размерность, те же распределения, нулевая связь с рынком. Сравнивать надо
с ним, а не с базой.

На SMC контроль показал: двенадцать признаков любой природы обрушивали граф
(43 → 22 состояния у BTC на чистом шуме), а настоящие держали 31. То есть
эффект был вчетверо меньше эффекта размерности.

**С 2026-08-11 источник этой проблемы устранён в самой калибровке.** Порог
дробления выражен в сигмах референса (полная gap statistic, `_split_gain`), а
не абсолютной константой, и от размерности больше не зависит: на однородном
облаке критерий отрицателен, на разделимых положителен одинаково в 32 и в 64
измерениях (`test_split_gain_is_independent_of_dimensionality`). Контроль на
шуме от этого не отменяется — он по-прежнему единственный способ отличить
информацию от геометрии, — но перестаёт быть заведомо провальным.

### 3.3. Лифт — с поправкой, holdout, блочным бутстрапом и по трём монетам

`scripts/measure_atom_lift.py` — по бинарным атомам,
`scripts/measure_feature_gradation.py` — по градации непрерывных признаков.

Атом засчитывается, только если:

* значим после поправки на множественные сравнения (Бонферрони до ~20 тестов,
  дальше Benjamini-Hochberg — при 25 тестах Бонферрони не пропускает ничего);
* значимость считается по **блочному бутстрапу**, а не по наивному z-тесту.
  Наблюдения зависимы: горизонт 24h — это 96 баров, а кандидаты идут в
  среднем каждые ~11 баров, плюс снимки офсетов дают до четырёх кандидатов на
  одну реализацию перехода. Наивный тест анти-консервативен примерно втрое по
  `z` (разбор — шапка `btcproc/analysis/lift.py`);
* знак и порядок величины лифта сохранились на **holdout по времени**
  (случайный сплит здесь врёт: `sample_size` растёт с историей);
* знак совпал на трёх монетах. Это ловит грубую подгонку под один инструмент,
  но **не даёт трёх независимых подтверждений**: BTC, ETH и SOL коррелированы
  на 0.8+, так что «совпало на 3 из 3» нельзя считать как p³.

Метрик две, и разница принципиальная. `long_outcome_share` — ожидание
системы, доля исторических аналогов: она отвечает на вопрос «коррелирует ли
атом с исторически перекошенными конфигурациями». `realized` — фактический
исход бара, свободный от зацикливания на ожиданиях системы. **Выводы делаются
по `realized`**, расхождение метрик само по себе информативно. Независимыми
наблюдениями не является ни одна из двух — блочный бутстрап нужен обеим.

**Бинарный флаг — самая бедная формулировка гипотезы.** Если у величины есть
градация (свежесть, размер, доля заполнения, номер касания), меряйте её
квантильными бинами с тестом на монотонность (Cochran–Armitage), а не одним
порогом: «чем свежее зона, тем выше доля роста» гораздо труднее объяснить
случайностью, чем один удачно попавший порог. Градация мерится **без
включения признаков в модель** — значения считаются на барах кандидатов и
приджойниваются, поэтому замер не зависит ни от переобучения, ни от
калибровки дробления.

### 3.4. Позитивный контроль измерителя — четвёртая обязательная проверка

Добавлено `docs/tz_deriv_ingest_14-08-26.md`, раздел 6, после того как это
уже стоило времени в самой этой задаче: скрипт-проба границ архива дважды
вернул ложные 404 по ETH и SOL, и ошибка вскрылась только потому, что
следующий прогон противоречил предыдущему. Прими скрипт на веру — и в
реестр ушло бы «метрик у ETH нет с 2021», то есть неверный факт, полученный
исправно работающим на вид кодом.

Тот же класс ошибки в фазе 1 выглядит так: измеритель молча возвращает нули,
результат записывается как «детектор не срабатывает», рабочий признак
выбрасывается — и отличить это от настоящего нуля нечем.

> **Каждый измеритель обязан иметь тест, в котором он ОБЯЗАН сработать.**
> Ноль без позитивного контроля неотличим от сломанного скрипта.

Формат не изобретается заново — образцы уже есть:

* `tests/test_control.py` (D1) — «модель находит нелинейную зависимость на
  синтетике, AUC > 0.7; не находит её в шуме»;
* ревизия 34.8 журнала FGI — калибровка и мощность `spearman_block_p` на
  синтетике с тем же числом независимых блоков, что на проде: доля ложных
  срабатываний 8.3% при номинале 5%, мощность 38% / 88% / 100% при
  rho = 0.15 / 0.30 / 0.50. Именно эта таблица позволила сказать «вывод
  гейта R — отсутствие эффекта, а не отсутствие чувствительности». Без неё
  отрицательный результат FGI не стоил бы ничего;
* деривативные метрики (`docs/tz_deriv_ingest_14-08-26.md`) добавили ещё
  три: `tests/test_metrics_convention.py` (карта конвенций `create_time`
  обязана совпасть с фактической сверкой на живых данных — сетевой тест,
  помечен `network`), `tests/test_gradation.py` (обобщённый
  Cochran–Armitage на непрерывной метрике находит известную монотонную связь
  и не находит её в чистом шуме), `tests/test_range_lift.py`
  (`partial_r2_gain` находит известное приращение R² и не находит его у
  предиктора, не несущего информации).

## 4. Что делает `train` сам, и почему на это нельзя не смотреть

Полный `train` перенумеровывает `group_id` с нуля. Ключ узла в Neo4j —
`(symbol, group_id)`, измерения модели в нём нет, поэтому накопленный граф
новой нумерации не соответствует. `train` **сносит граф монеты** сразу после
сохранения новой модели (`graph_sink.reset_graph`), и ошибка очистки роняет
прогон, а не пропускается.

Место выбрано не случайно: штатный недельный `train` идёт с `--no-emit`,
кандидатов не шлёт, но модель подменяет — и ближайший `live` начинает писать в
граф уже новой нумерацией. Привязка очистки к отправке оставила бы этот путь
открытым.

Для фазы эксплуатации правильное решение другое — `model_id` в ключе узла,
чтобы поколения сосуществовали. Пока накопленная статистика рёбер не ценна
сама по себе, очистка проще и не требует протаскивать `model_id` через
контракт между проектами.

## 5. Грабли, на которые уже наступили

| Грабли | Как проявляется | Чем закрыто |
|---|---|---|
| Атом считается, но не сохраняется | Никак. Величина есть в коде, в БД её нет, лифт мерить не по чему | `bar_events.context_atoms`, тест `test_context_atoms_survive_to_the_output` |
| Новый атом вставлен в середину `ATOM_FAMILY` | Все исторические `event_block_id` меняют смысл, молча | `test_signature_bits_are_pinned`, `test_atom_bit_order_is_pinned` |
| Признак-расстояние с потолком | «Ближайшей зоны нет» после robust-нормировки становится выбросом ±5 при типичном разбросе ±1 и тянет кластеризацию сам по себе | Близость `1/(1+d)` вместо расстояния; проверка доли строк на клипе |
| Порог детектора задан в деньгах | На дешёвой монете атом мёртв, на дорогой вырожден — и видно это только помонетным замером частот | `test_round_level_touch_is_scale_invariant`, требование 2.1 |
| Сравнение записей разных моделей | `group_id` и `transition_id` из чужой нумерации выглядят правдоподобно. На базе с несколькими частичными прогонами ломает holdout | `runs.model_run_scope()`; замер печатает номер модели |
| Фильтр по одному `run_id` вместо модели | Страницы админки замирают на моменте последнего обучения, выглядит как «данные пропали» | тот же `model_run_scope()` |
| Версия набора признаков не сменилась | `feature_sets.names` перезаписан, старые строки `features` — массивы прежней длины | `feature_version()` зависит от состава источников |
| Версия собрана из флагов, а не из состава | На ВТОРОМ источнике два разных набора получают одну метку — та же поломка строкой выше, но уже незакрытая | `registry.compose_version`, `test_two_sources_never_share_a_label` |
| Новый признак или атом без формулировки | Подпись состояния молча теряет отличие и говорит «рынок около среднего»; атом показывается сырым идентификатором | `test_every_registered_feature_has_a_phrase`, `test_every_registered_atom_has_a_russian_label` |
| Пороги дробления не перекалиброваны под новую размерность | Число состояний падает в разы, и это выглядит как «источник ухудшил модель», хотя дело в размерности | Порог в сигмах референса (`_split_gain`), `test_split_gain_is_independent_of_dimensionality`, калибровка `calibrate_split_gain.py` |
| Замер считает зависимые наблюдения независимыми | Значимость завышена примерно втрое по `z`; «подтверждённые» атомы не переживают честной проверки | Блочный бутстрап в `lift.py` и `gradation.py`, прореживание как sanity check |
| Накопленный граф Neo4j пережил `train` | Счётчики рёбер растут поверх узлов прежней нумерации; узлы двух поколений неотличимы | `graph_sink.reset_graph` в `train`, ошибка роняет прогон |
| Двойной расчёт за прогон | Величины считаются и в признаках, и в атомах | `build_smc_cached`, кэш на одну запись |
| **Общерыночный ряд, а критерий помонетный** | «Знак совпал на трёх монетах» выглядит подтверждением, хотя предиктор буквально один и тот же для всех — это один замер, показанный трижды | разрез по ЭПОХАМ вместо монет, `scripts/measure_fgi_epochs.py` |
| **Новизна проверена парной корреляцией** | Источник, наполовину пересобранный из уже имеющихся величин, проходит порог «max \|r\| > 0.9» легко: парные r по 0.6–0.7, а множественная R² — 0.85+ | out-of-sample R² на весь вектор, `analysis/novelty.py` |
| **Предиктор меняется реже бара** | Блок бутстрапа берётся по горизонту исхода (96 баров), а зависимость идёт ещё и по предиктору — у дневного ряда она 125 дней. Значимость завышается | `--block-rows` у `measure_atom_lift.py` / `measure_feature_gradation.py`, `autocorr_block_rows` |
| **Внешний ряд с дырами и без зоны** | `shift()` идёт по позициям — «вчера» уезжает через пропуск; tz-naive индекс не совпадает ни с одним баром и даёт сплошной NaN молча | выравнивание на непрерывный `date_range` и приведение к UTC до расчёта (`features/fear_greed.py`) |
| **Измеритель без позитивного контроля** | Молчаливый ноль от сломанного кода неотличим от настоящего отсутствия эффекта; скрипт-проба границ архива метрик дважды соврал по ETH/SOL, и это вскрылось только по противоречию со следующим прогоном | тест «измеритель ОБЯЗАН сработать на синтетике» на каждый измеритель (§3.4) |

```

[ ] русские формулировки: naming.AXES для признаков, naming.ATOM_LABELS для атомов

[ ] measure_atom_lift.py --all --metric realized — лифт по трём монетам
[ ] measure_feature_gradation.py --all — градация, если у величины она есть
[ ] позитивный контроль на КАЖДЫЙ измеритель фазы 1 (§3.4) — ноль без него неотличим от сломанного скрипта
[ ] гипотезы зафиксированы ПИСЬМЕННО до замера; зеркальные пары считаются одной
[ ] пороги дробления проверены calibrate_split_gain.py на устойчивость
[ ] решение по каждой концепции: включена или отвергнута, С ЧИСЛОМ

```

Отрицательный результат — валидный результат, и записывать его надо так же
подробно, как записали бы успех. Система построена ровно для того, чтобы
отличать одно от другого.
