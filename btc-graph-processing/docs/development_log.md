# Журнал разработки btc-graph-processing

Что было сделано, какие решения приняты и почему, какие проблемы вскрылись по
ходу. Описание самой системы — в [README.md](../README.md); здесь то, чего в
README нет: история, обоснования и разбор ошибок.

Дата: 8 августа 2026. Всё описанное проверено на живых данных.

---

## 1. Задача

В репозитории [btc-graph](../../btc-graph/README.md) первый же раздел говорит:

> Внешняя система (в этот репозиторий она **не входит**) строит граф состояний
> рынка BTC… и выдаёт кандидата.

Этой системы не существовало — кандидатов приходилось подавать в btc-graph
руками. Задача: построить её.

Требовалось четыре вещи:

1. пройти историю BTC с 2015 года по разным таймфреймам и заполнить граф;
2. визуальная составляющая;
3. то, что будет посылать запросы в btc-graph;
4. примитивная админка с жёсткой авторизацией из `.env`.

### Решения, принятые на старте

| Вопрос | Выбор | Следствие |
|---|---|---|
| Источник и глубина истории | Binance с 2017-08 | Спота BTCUSDT раньше не существует; 2015–2017 потребовали бы склейки с Bitstamp, а это разрыв в ликвидности и шум признаков на стыке |
| Таймфреймы | 15m база + 1h / 4h / 1d контекст | Согласуется с age-бакетами кандидата (30/60/120 мин) и горизонтом 24h; ~300k баров считаются на ноутбуке |
| Админка | FastAPI + Jinja + HTMX | Один сервис, без сборки фронта; Cytoscape для графа, lightweight-charts для свечей |
| Инфраструктура | Общий стек с btc-graph, запись в БД напрямую | Реализовано как `SINK_MODE=direct` — см. §3.1 |


Конвейер: **бары → признаки → события → исходы → состояния → граф →

Подробная структура — в [README, раздел 2](../README.md#2-структура-проекта).

## 3. Инженерные решения

### 3.1. `direct` вместо HTTP, но не в обход фильтра

Выбор «прямая запись в БД» я реализовал как импорт пакета btc-graph и вызов
его `run_batch_pipeline(save=True)`. HTTP из цепочки убран, запись идёт прямо
в PostgreSQL, Neo4j и Redis — но проходит через его валидатор, скорер, фильтр
по `candidate_family_key` и дедупликацию.

Писать в `public.candidates` мимо этого я сознательно не стал: тогда btc-graph
перестаёт быть фильтром, а в этом весь его смысл. Разрыв 39 990 отправленных →
28 629 оценённых — это его работа, а не потери.

### 3.2. Пакет называется `btcproc`, а не `src`

Пакет btc-graph называется `src` и внутри себя импортируется как `from src…`,
причём лениво — уже внутри `_persist`. Одноимённый пакет у нас означал бы, что
его импорты резолвятся в наш код. Разные имена снимают вопрос целиком.

### 3.3. Адаптивная гранулярность состояний

ТЗ требует, чтобы число состояний не задавалось заранее: неоднородная группа
дробится, почти идентичные сливаются. Реализовано в три шага — грубое
стартовое разбиение, рекурсивное дробление по gap-критерию (силуэт против
силуэта случайного облака той же формы), затем слияние неразличимых пар.

Поправка на референс обязательна: KMeans «находит» два кластера и в однородном
шаре, без неё дробление шло бы до упора.

### 3.4. Три правила честной выборки

Без них вся статистика кандидата была бы самообманом:

1. **только прошлое** — выборка для момента `t` собирается из случаев раньше `t`;
2. **только созревшие исходы** — случай попадает в выборку не раньше, чем
   пройдёт горизонт;
3. **разные возрасты состояния** — снимки берутся в момент перехода и через
   45 / 90 / 180 минут, иначе все исторические кандидаты были бы
   `age_lt_30` + `fresh`, и ось контекста в btc-graph никогда бы не различалась.

Первые два закреплены тестом `test_candidate_sample_uses_only_matured_past`,
третье — `test_snapshots_cover_all_age_buckets`.

## 4. Проблемы, вскрывшиеся по ходу

Разбор в порядке обнаружения. Часть — ошибки проектирования, часть вылезла
только на живых данных или в другом окружении.

### 4.1. Граф вырождался в 3–4 состояния

**Как проявлялось.** Дробление отрабатывало нормально (в трассе — два десятка
групп), но после слияния оставалось 3–4 узла. Граф состояний рынка из четырёх
состояний бесполезен.

**Причина.** Критерий слияния сравнивал расстояние центроидов с суммой средних
радиусов групп. В 32-мерном пространстве радиус растёт как √d, поэтому любые
две группы выглядят «почти одинаковыми», и слияние схлопывало всё подряд.

**Решение.** Мера различимости считается **вдоль оси между центроидами**:
точки обеих групп проецируются на эту ось, расстояние центроидов сравнивается
с суммой стандартных отклонений проекций. Получается d-prime, от размерности
не зависящий.

**Результат.** Та же история, тот же код в остальном: **4 состояния → 43**.

### 4.2. Блоков событий было столько же, сколько баров

**Как проявлялось.** 16 314 уникальных `event_block_id` на 76 637 баров.
Историческая выборка по конкретному блоку не набиралась никогда, генератор
всегда откатывался к выборке только по переходу.

**Причина.** В блок входили все детектируемые атомы, включая фоновые
(`trend_up_align`, `us_session`, `mid_range`), активные почти всегда. Каждый
такой атом удваивает число возможных комбинаций.

**Решение.** Атомы разделены на `SIGNATURE_ATOMS` (пробои, всплески, кроссы,
развороты — то, что происходит) и `CONTEXT_ATOMS` (тренд, сессии,
доминирование тейкеров — то, что длится). В блок входят только первые. Фон не
теряется: он уже учтён в векторе признаков, а значит — в самом `group_id`.

**Результат.** 16 314 → 2 728 блоков на той же выборке; на полной истории —
4 334. Доля кандидатов с выборкой по полному ключу «переход + блок» стала
заметной (`runs.stats.candidates.scopes`).

### 4.3. `live` терял выходные

**Как проявлялось.** Не проявлялось никак — в этом и проблема. Вопрос
владельца проекта: «запущу в понедельник, а последний прогон был в пятницу —
догрузит?»

**Причина.** Бары догружались корректно (точка бралась из `max(ts)` в БД), а
кандидаты выпускались за фиксированное окно `--lookback 240` минут от
последнего бара. Всё, что произошло с вечера пятницы, пропадало молча.

**Решение.** Точка продолжения для кандидатов тоже берётся из данных —
`max(ts)` среди уже выпущенных. Верхняя граница `--max-lookback-days`
страхует от первого запуска на давно заполненной базе.

**Проверка.** На живой базе разрыв в 14.5 ч закрылся сам:
`Кандидаты начиная с 2026-08-07 17:45 — продолжаем с … (пропуск 14.5 ч)`.
Пять тестов в `tests/test_live_cutoff.py`, первый — буквально сценарий
«пятница 20:00 → понедельник 09:00».

### 4.4. Расхождение окружений: `pgvector` и `neo4j`

**Как проявлялось.** Запуск из `.venv`: кандидат считается, `emit` рапортует
`sent: 1`, а в логе посреди прогона — `ModuleNotFoundError: No module named
'pgvector'` и `сохранён частично: {'db': False, 'graph': False, 'redis': True}`.
Оценки никуда не сохранялись.

**Причина.** Эти пакеты импортирует не наш код, а btc-graph, причём лениво —
уже внутри сохранения. Поэтому нехватка не видна на старте.

**Решение.** `missing_direct_dependencies()` проверяет их наличие до отправки;
предупреждение называет конкретный интерпретатор и готовую команду. `status`
печатает путь к интерпретатору, админка помечает приёмник проблемным с
текстом «кандидаты оцениваются, но не сохраняются».

### 4.5. Два бага, видимых только на pandas 3

Окружения разошлись: `.venv` — pandas 3.0.5 / numpy 2.5.1, системный python —
pandas 2.2.2 / numpy 1.26.4. На старых версиях оба бага молчали.

| Баг | Проявление | Решение |
|---|---|---|
| `to_numpy()` вернул read-only массив | `robust_scale_params` падал с `assignment destination is read-only`; прогон разваливался на кластеризации | `to_numpy(dtype=float, copy=True)` |
| `primary_event_family` = `NaN` вместо `None` | Кандидат не проходил pydantic-схему btc-graph (`Optional[str]`) — на бою уронил бы отправку | Приведение NaN → None |

Отсюда правило: тесты гоняются в обоих окружениях.

### 4.6. Фильтры в админке отвечали 422

**Как проявлялось.**
`GET /candidates?run=12&rating=&direction=&min_quality=&transition=&emitted=`
→ 422, фильтрация не работала совсем.

**Причина.** HTML-форма отправляет незаполненные поля пустыми строками, а
параметры были объявлены типизированно (`float | None`, `int | None`).
FastAPI не может превратить `""` во float и отклоняет весь запрос.

**Решение.** Query-параметры страниц и API принимаются строками и разбираются
помощниками `opt_str` / `opt_int` / `opt_float`: пусто и мусор означают
«фильтр не задан», а не ошибку. Заодно принимается запятая как десятичный
разделитель — русская раскладка не должна ронять фильтр.

Те же грабли были убраны в `/api/graph`, `/api/chart`, `/graph`, `/chart`, где
`run=` мог прийти пустым из селектора «все».

### 4.7. `hsl()` в lightweight-charts

Цвета состояний отдавались как `hsl(32, 62%, 55%)`. Библиотека парсит цвет
сама и падает: `Uncaught Error: Cannot parse color`. Генерация переведена на
hex через `colorsys`.

### 4.8. Мелкие, но существенные

| Проблема | Решение |
|---|---|
| `data.binance.vision` отдаёт 503 при плотной череде запросов — закачка истории падала на середине | Ретраи с экспоненциальной паузой; 403/404 = «файла нет», 429/5xx = «подожди» |
| Имена признаков конфликтовали: базовый `pos_1d` и контекстный `pos_1d` с ТФ 1d | Контекстные получили префикс `tf1d_`, `tf4h_`, `tf1h_` |
| `valid` после `reindex` становился `NaN`, а `bool(NaN)` — это `True`: снимки без разметки попадали в выборку как валидные | Явный `fillna(False).astype(bool)` |
| `train` молча переобучал состояния — `group_id` нового прогона несопоставимы со старыми, граф в Neo4j смешивал две нумерации | Предупреждение при запуске + раздел в README |
| Два тяжёлых прогона могли идти одновременно (админка блокировала, CLI — нет) | Проверка активного прогона в `train` и `live`, снимается `--force` |
| `emit --run 999` возвращал нули — опечатка выглядела как «всё отправлено» | Проверка существования прогона |
| `status` показывал объёмы, но не отвечал на вопрос «мы отстали?» | Добавлены отставание баров, очередь отправки, время последнего кандидата |
| Сообщение «Нет дампов за: 2026-08» пугало, хотя это норма для текущего месяца | Пояснение прямо в сообщении |

## 5. Доработки админки

Первая версия была рабочей, но неудобной: много пустого места, граф из 43
узлов и 631 ребра в окне 640 px нечитаем, цвета никак не объяснены.

**Плотность.** Базовый шрифт 14 → 13 px, отступы урезаны примерно вдвое,
ограничение ширины снято, граф и график заняли высоту экрана
(`calc(100vh − …)`), заголовки таблиц липкие.

**Управляемость графа.** По умолчанию показываются 120 самых частых переходов;
есть фильтр по редкости, минимум случаев, скрытие узлов без связей, пять
раскладок, поиск состояния по номеру. Клик подсвечивает соседство и приглушает
остальное до 8 % непрозрачности.

**Легенда.** Отдельной полосой над графом и чартом: что значит цвет узла,
размер узла, цвет и толщина ребра, цвет свечи, цвет стрелки.

**Светлая тема.** Переключатель в шапке, выбор в `localStorage`, применяется до
первой отрисовки. Палитра целиком в CSS-переменных, включая цвета сущностей
графа: Cytoscape и lightweight-charts читают их оттуда и перекрашиваются по
событию `btcproc:theme`.

**Сводка.** Добавлены блоки «Крупнейшие состояния» и «Самые частые переходы» —
заодно заняли пустое место полезным.

### Полный прогон (run #4), история 2017-08 → 2026-08

| Этап | Результат |
|---|---|
| Загрузка | 314 141 бар 15m + агрегаты 1h / 4h / 1d |
| Признаки | 32 признака × 312 662 строки |
| События | 4 334 уникальных блока |
| Исходы 24h | 309 534 валидные метки |
| Граф состояний | **43 состояния, 631 переход** |
| Кандидаты | **39 990** из 68 793 снимков |
| Принято btc-graph | 28 629 оценок, 0 ошибок отправки |

Расчётная часть — около 8 минут, отправка — 13.5 минут (порядка 600
кандидатов в минуту: каждый проходит скорер и пишется в три хранилища).

### Что легло в btc-graph

| Рейтинг | long | short | ср. quality | максимум |
|---|---|---|---|---|
| STRONG | 205 | 92 | 0.79 | 0.983 |
| MODERATE | 9 266 | 2 067 | 0.62 | 0.749 |
| WEAK | 10 972 | 6 238 | 0.46 | 0.549 |

Neo4j: 43 узла `MarketGroup`, 243 ребра `TRANSITION` со статистикой.

Доля STRONG около 1 % — ожидаемо: максимум статистической оси в btc-graph
требует `sample_size > 1000`.

### Инкрементальные прогоны

`live` отработал многократно (run #5, 6, 8–11): добор баров, разметка
обученной моделью, выпуск кандидатов за пропущенный период, отправка.
Повторный запуск ничего не дублирует — `candidate_id` детерминирован, запись
идёт upsert'ом, `emitted_at` не сбрасывается.

## 7. Тесты

42 теста, проходят в обоих окружениях. Ни БД, ни сеть не требуются —
всё считается на синтетических барах с заранее известной структурой.

| Файл | Что закрывает |
|---|---|
| `test_features.py` | Диапазоны индикаторов, отсутствие NaN, **отсутствие заглядывания вперёд**, устойчивость нормировки к выбросам, стабильность `event_block_id` |
| `test_states.py` | Сглаживание дребезга, возраст и бакеты, разделимые кластеры находятся, однородное облако не дробится, сериализация модели |
| `test_candidates.py` | Исходы совпадают с ценами, дыры в данных дают `valid=False`, снимки покрывают все age-бакеты, **совместимость с pydantic-схемой btc-graph**, выборка только из созревшего прошлого |
| `test_live_cutoff.py` | Точка продолжения live, включая сценарий «пятница → понедельник» |
| `test_sink_deps.py` | Нехватка `pgvector` / `neo4j` определяется до отправки |
| `test_admin_auth.py` | Шаблонные и короткие пароли, срок жизни и подделка куки, блокировка по IP, allowlist |
| `test_admin_params.py` | Пустые и мусорные значения фильтров не дают 422 |

Два теста стоит выделить: `test_features_do_not_look_ahead` (признаки на
полной истории и на её префиксе обязаны совпасть) и
`test_generated_candidates_match_btc_graph_schema` (каждый кандидат обязан
пройти модель `Candidate` из btc-graph без единой правки). Именно они
защищают от ошибок, которые иначе тихо обесценили бы всю статистику.

## 8. Что осталось

Свойства подхода, а не дефекты:

* **Только BTCUSDT и только с 2017-08.** История с 2015 требует склейки бирж.
* **Нормировка признаков глобальная** — медиана и IQR считаются по всей
  истории. Для строгого walk-forward нужно расширяющееся окно.
* **`transition_rarity` и частота блоков — глобальные характеристики графа**,
  а не кумулятивные на момент кандидата.
* **Кандидат ≠ торговый сигнал** — нет entry timing, стопов и размера позиции.

Чего пока нет:

* ончейн- и макро-данных: семейства событий покрывают только то, что видно в
  свечах и объёмах; деривативы (funding, open interest) — очевидное следующее
  расширение;
* walk-forward валидации графа: модель состояний учится на всей истории сразу;
* автоматического расписания: `live` нужно вешать на cron самому.

## 9. Регламент эксплуатации

```bash
source .venv/bin/activate            # зависимости должны быть в этом же python

python3 -m btcproc.cli live          # штатное обновление, раз в 15–60 минут
python3 -m btcproc.cli status        # отставание, очередь, приёмник
python3 -m btcproc.cli emit --run N  # дослать, если btc-graph лежал
python3 -m btcproc.cli train         # переобучение графа, раз в несколько месяцев
```

`train` меняет нумерацию `group_id` — это осознанная операция, не способ
«обновить данные». Для регулярного обновления существует только `live`.
