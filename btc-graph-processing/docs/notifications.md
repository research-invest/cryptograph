# Уведомления: вебхуки о новых кандидатах

Когда появляется кандидат, подходящий под правило, на заданный адрес уходит
`POST` с JSON. Этот документ — контракт для **принимающей стороны**: что
приходит, что означает каждое поле и на что можно опираться, а на что нет.

Настройка правил — страница **Уведомления** в админке. Эксплуатационная часть
(как завести правило, где смотреть журнал доставок) — в конце документа и в
`docs/operator_guide.md`.

---

## 1. Как это выглядит со стороны получателя

```
POST /ваш/адрес HTTP/1.1
Content-Type: application/json
User-Agent: btcproc-notify/1
Idempotency-Key: 3f2a1c9b8e7d6a5c4b30
<ваши заголовки из правила, например Authorization: Bearer ...>

{ …тело, см. ниже… }
```

Что нужно знать сразу:

* **Ответ читается, но ни на что не влияет.** Отправитель не повторяет
  запросы: неудача попадает в журнал доставок и остаётся там. Любой `2xx`
  считается успехом, `4xx` и `5xx` — неудачей, тело ответа не разбирается.
  Считайте, что второй попытки не будет — потому что её и правда не будет.
* **Отвечать надо быстро.** Таймаут по умолчанию 5 секунд (`NOTIFY_TIMEOUT`).
  Если ваша обработка долгая — примите запрос, ответьте `200` и работайте
  дальше у себя.
* **`Idempotency-Key` = `candidate_id`.** Отправитель уже защищён от повторов
  собственным журналом, но защита не абсолютна (журнал чистится по retention,
  а оператор может нажать «проверить» вручную). Дубль по этому ключу нужно
  уметь отбросить.
* **Порядок не гарантирован.** Уведомления уходят несколькими потоками;
  два кандидата, выпущенные подряд, могут прийти в обратном порядке.
  Ориентируйтесь на поле `ts`, а не на порядок получения.

---

## 2. Тело запроса

Два режима, задаются в правиле полем «Формат»:

* **`full`** — сводка + кандидат целиком + оценка целиком. По умолчанию.
* **`compact`** — только сводка. Те же корневые поля, без блоков `candidate`
  и `evaluation`.

Актуальный пример печатается командой (он собирается тем же кодом, что и
боевое тело, поэтому не может протухнуть):

```bash
python3 -m btcproc.cli notify-example            # full
python3 -m btcproc.cli notify-example --mode compact
```

### 2.2. Корень: сводка

Эти поля есть **всегда**, в обоих режимах. Принимающей системе для маршрутизации
и показа хватает только их.

| Поле | Тип | Что это |
|---|---|---|
| `schema` | string | Версия формата. Сейчас `btcproc.candidate.v1`. См. §4. |
| `event` | string | Тип события. Сейчас всегда `candidate`. |
| `sent_at` | ISO-8601 | Момент отправки. **Не** момент кандидата. |
| `rule.id`, `rule.name` | int, string | Какое правило сработало. Полезно, когда на один адрес настроено несколько правил. |
| `candidate_id` | string | Идентификатор кандидата. Детерминированный, годится как ключ дедупликации. |
| `symbol` | string | Тикер Binance: `BTCUSDT`, `ETHUSDT`, `SOLUSDT`. |
| `ts` | ISO-8601, UTC | **Время бара**, к которому относится кандидат. Всегда UTC со смещением `+00:00`. |
| `side` | `long` \| `short` | Направление исторического перекоса. |
| `rating` | `STRONG` \| `MODERATE` \| `WEAK` \| `null` | Оценка btc-graph. `null` — кандидат не оценивался (см. §3.2). |
| `quality_score` | float 0..1 \| null | Оценка качества от btc-graph. |
| `research_score` | float 0..1 | Наша синтетическая оценка силы аналогии. Это **не** вероятность прибыли. |
| `sample_size` | int | Сколько исторических случаев в выборке. |
| `transition_id` | string | Переход между состояниями, вида `42->7`. |
| `event_block_id` | string | Идентификатор блока сопровождающих событий. |
| `primary_event_family` | string \| null | Ведущее семейство событий — «тип события» (список в §5). |
| `horizon` | string | Горизонт оценки исходов, обычно `24h`. |
| `run_id` | int | Прогон, впервые выпустивший кандидата. |
| `warning_flags` | string[] | Предупреждения от btc-graph. Пустой массив, если их нет. |
| `is_trading_signal` | bool | Всегда `false`. См. §6 — это не формальность. |

### 2.3. Блок `candidate` (только `full`)

Кандидат ровно в том виде, в каком он уходит в btc-graph — те же 37 полей его
схемы. Смысл групп полей:

* **Идентичность.** `configuration_hash` — хэш конфигурации (монета + переход +
  блок + возраст + энтропия). `candidate_family_key` — ключ «семьи»: кандидаты
  одной семьи описывают одну и ту же ситуацию, и btc-graph оставляет из них по
  одному.
* **Состояние и траектория.** `previous_group_id` → `current_group_id` — из
  какого состояния рынок перешёл в какое. **Номера состояний осмысленны только
  внутри пары (монета, прогон)**: «состояние 7» у BTC и у ETH — разные рынки, а
  после еженедельного переобучения номера меняются и у одной монеты. Не стройте
  на них долгоживущих правил. `current_group_age_bucket` — сколько рынок в
  состоянии (`age_lt_30`, `age_30_60`, `age_60_120`, `age_gt_120`).
  `trajectory_entropy` (`low`/`medium`/`high`) — насколько рвано рынок ходил по
  состояниям в последнее время. `transition_rarity` (`rare`/`uncommon`/`common`)
  — насколько редок сам переход.
* **События.** `signature_atom_count`, `event_family_count` — сколько
  детекторов сработало и из скольких семейств. `event_intensity_bucket`
  (`sparse`/`moderate`/`dense`), `event_rarity_bucket`
  (`common`/`uncommon`/`rare`), `event_block_total_rows` и
  `event_block_row_share` — насколько такой блок событий вообще част в истории.
* **Историческая выборка.** `sample_size` — всего случаев; `valid_label_count` —
  из них с созревшим исходом; `repeatability_days` / `repeatability_months` — по
  скольким разным дням и месяцам они разбросаны; `monthly_concentration` — доля
  самого «густого» месяца. Высокая концентрация означает, что выборка на самом
  деле про одну рыночную эпоху, а не про рынок вообще.
* **Профиль исхода.** `long_outcome_share` — доля случаев, закончившихся вверх;
  `historical_outcome_skew` = `2 × доля − 1` (диапазон −1..1). `research_side`
  — знак этого перекоса.
* **Favorable / adverse.** `p70_long_favorable_pct` — 70-й перцентиль движения
  «в нашу сторону», `p80_long_adverse_pct` — 80-й перцентиль движения против,
  оба **в процентах и всегда в терминах long**. Отношение —
  `long_favorable_adverse_ratio_p70_p80`.

### 2.4. Блок `evaluation` (только `full`)

Ответ btc-graph. Может быть `null` — см. §3.2. Ключевое:

| Поле | Что это |
|---|---|
| `quality_score`, `rating` | Итоговая оценка и её категория. |
| `quality_score_baseline` | Тот же кандидат по базовому профилю. Нужен для сравнения **между монетами**: обычный `quality_score` считается профилем монеты и между монетами несопоставим. |
| `scoring_profile`, `profile_fingerprint` | Каким профилем посчитано. **Сравнивать `quality_score` корректно только внутри одной метки** — после правки профиля старые оценки несравнимы с новыми. |
| `win_rate`, `favorable_adverse_ratio` | Доля успешных исходов и отношение favorable/adverse. `favorable_adverse_ratio` = `null` для short: p70/p80 описывают движение вверх. |
| `strengths`, `risks`, `summary` | Человеческая формулировка. Числа считает детерминированный скорер, формулирует LLM — на числа она не влияет. |
| `score_statistical`, `score_directional`, `score_context`, `score_rarity` | Разложение оценки по осям. |

## 3. Когда уведомление приходит, а когда нет

### 3.1. Момент отправки

Кандидаты выпускает инкрементальный прогон `live` — по расписанию раз в
полчаса. Уведомление уходит внутри этого прогона, сразу после того как
кандидат записан и (если отправка включена) оценён btc-graph.

Отсюда практическое следствие: **задержка от времени бара до вебхука — до
получаса плюс время прогона.** Поле `ts` может отставать от `sent_at` на
десятки минут, и это норма, а не сбой.

### 3.2. `rating` и `evaluation` бывают пустыми

Кандидат рождается у генератора, а рейтинг ему ставит btc-graph. Между этими
двумя моментами есть штатные развилки, на которых оценки не появляется:

* отправка в btc-graph выключена (`--no-emit`, `SINK_MODE=none`);
* btc-graph принял кандидата, но отсеял своим фильтром качества — тогда
  оценки он не возвращает вовсе.

По умолчанию правило шлёт **только оценённых** (галка «только оценённые
btc-graph»). Если её снять, будут приходить и кандидаты с `rating: null` и
`evaluation: null`. Фильтры по рейтингу и `quality_score` на таких не
срабатывают никогда — «рейтинг неизвестен» это не «рейтинг подходит».

### 3.3. Чего не будет

* **Уведомлений по истории.** Кандидат старше `NOTIFY_MAX_CANDIDATE_AGE_MIN`
  (по умолчанию 180 минут) не отправляется. Это предохранитель: полный прогон
  `train` выпускает сотни тысяч кандидатов начиная с 2017 года, и без окна
  первый же такой прогон разослал бы их все.
* **Повторов одного кандидата по одному правилу.** Пара «правило + кандидат»
  фиксируется в журнале доставок до отправки, поэтому перекрывающиеся окна
  `live` дублей не создают.
* **Ретраев.** Неудачная доставка остаётся неудачной. Повторить можно только
  руками — кнопкой «проверить» в админке или `notify-test`.

## 4. Версионирование формата

Поле `schema` — единственное, на что можно опираться при разборе.

* **Совместимая правка** (новое поле) версию не меняет. Разбирайте JSON так,
  чтобы незнакомые поля игнорировались.
* **Несовместимая правка** (переименование, удаление, смена типа или смысла
  поля) меняет версию: `btcproc.candidate.v2`.

Рекомендация для принимающей стороны: сверять префикс `btcproc.candidate.v1` и
на незнакомой версии писать в свой лог, а не падать.

## 5. Справочники значений

**`rating`**: `STRONG`, `MODERATE`, `WEAK` (пороги `quality_score` задаются
профилем каждой монеты в btc-graph и калибруются, поэтому числа здесь не
приводятся — ориентируйтесь на категорию).

**`side` / `research_side` / `direction`**: `long`, `short`.

**`primary_event_family`** — «тип события», ведущее семейство сработавших
детекторов:

| Значение | Про что |
|---|---|
| `price_action_events` | пробои и провалы уровней, широкие и внутренние бары |
| `volatility_events` | расширение и сжатие волатильности, всплеск ATR |
| `volume_events` | всплеск и пересыхание объёма, доминирование покупателей/продавцов |
| `trend_events` | кроссы EMA, выстроенность трендов |
| `momentum_events` | перекупленность/перепроданность, развороты импульса |
| `session_events` | торговые сессии |
| `structure_events` | слом рыночной структуры (SMC) |
| `imbalance_events` | имбалансы, FVG (SMC) |
| `liquidity_events` | снятие ликвидности, равные максимумы/минимумы (SMC) |
| `zone_events`, `zone_context_events` | ордер-блоки, зоны, premium/discount (SMC) |

Список ведётся в коде (`btcproc/features/events.py`, `ATOM_FAMILY`) и может
пополняться — новое семейство совместимо и версию формата не меняет.

**Бакеты:** `current_group_age_bucket` — `age_lt_30`, `age_30_60`,
`age_60_120`, `age_gt_120`; `context_status` — `fresh`, `stale`;
`trajectory_entropy` — `low`, `medium`, `high`; `transition_rarity` и
`event_rarity_bucket` — `rare`, `uncommon`, `common`;
`event_intensity_bucket` — `sparse`, `moderate`, `dense`;
`historical_bias_context` — `long_skew`, `short_skew`, `neutral`.

## 6. Чем кандидат НЕ является

Это важнее всех предыдущих разделов, и `is_trading_signal: false` стоит в теле
именно поэтому.

Кандидат — **исследовательская идея**: «в такой конфигурации рынка раньше
бывало вот так». В нём нет и не подразумевается:

* цены входа и момента входа,
* стоп-лосса и тейк-профита,
* размера позиции и плеча,
* какого-либо утверждения о будущем.

`research_score` и `quality_score` измеряют **качество исторической аналогии**
(велика ли выборка, устойчива ли во времени, однонаправлена ли), а не
вероятность прибыли. `p70_long_favorable_pct` — свойство прошлых случаев, а не
цель.

Принимающая система вправе строить на этом что угодно, но автоматическое
исполнение ордеров по такому уведомлению — решение, за которое отвечает она, а
не источник.

## 7. Настройка со стороны отправителя

### 7.1. Правило

Админка → **Уведомления** → форма внизу страницы.

| Поле | Смысл |
|---|---|
| Имя, Адрес | Адрес обязан начинаться с `http://` или `https://` — иначе правило не сохранится. |
| Формат | `full` или `compact` (§2). |
| Включено | Выключенное правило не срабатывает, но сохраняется. |
| Монета | Пусто = все монеты. |
| Рейтинг, Сторона, Тип события | Множественный выбор; пусто = не фильтруем. |
| quality ≥, research ≥, Выборка ≥ | Пустое поле = порога нет. Ноль — это заданный порог, а не «нет порога». |
| Переходы | Через запятую, например `42->7, 13->2`. Помните про §2.3: номера состояний живут одну модель. |
| Только оценённые btc-graph | См. §3.2. |
| Заголовки | По строке на заголовок, `Имя: значение`. Сюда кладётся токен авторизации получателя. |

Кнопка **проверить** шлёт на адрес правила последнего реального кандидата
(а если их ещё нет — показательный пример) мимо фильтров, очереди и журнала.
То же из терминала:

```bash
python3 -m btcproc.cli notify-test --rule 3
```

### 7.2. Журнал доставок

Внизу той же страницы. Это **единственное** место, где видно, что стало с
запросом: отправка идёт в фоновом потоке и других следов не оставляет.

| Статус | Значит |
|---|---|
| `sent` | получатель ответил 2xx |
| `failed` | сеть, таймаут или ответ 4xx/5xx; причина в колонке «Ошибка» |
| `queued` | взято в работу, но результат не записан — почти всегда означает, что процесс прогона завершился раньше, чем разобралась очередь |
| `dropped` | очередь была переполнена (`NOTIFY_QUEUE_SIZE`) |

### 7.3. Переменные окружения

Все со значениями по умолчанию; править нужно редко.

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `NOTIFY_ENABLED` | `true` | Общий рубильник. `false` — правила сохраняются, но ничего не отправляется. |
| `NOTIFY_TIMEOUT` | `5.0` | Сколько ждать ответа одного получателя, секунд. |
| `NOTIFY_WORKERS` | `2` | Потоков-отправителей. |
| `NOTIFY_QUEUE_SIZE` | `2000` | Потолок очереди; переполнение = `dropped`. |
| `NOTIFY_FLUSH_SECONDS` | `30` | Сколько прогон ждёт разбора очереди перед выходом. |
| `NOTIFY_MAX_CANDIDATE_AGE_MIN` | `180` | Окно свежести (§3.3). Поднимать осторожно. |
| `NOTIFY_RETENTION_DAYS` | `30` | Хранение журнала доставок. **Ниже суток опускать нельзя**: журнал заодно защищает от повторной отправки. |

## 8. Пример приёмника

Минимальный получатель на FastAPI — как ориентир, а не как готовый сервис:

```python
from fastapi import FastAPI, Header, HTTPException, Request

app = FastAPI()
seen: set[str] = set()          # в бою — Redis или таблица с TTL

@app.post("/hooks/btcproc")
async def hook(request: Request, authorization: str = Header(default="")):
    if authorization != "Bearer МОЙ_ТОКЕН":
        raise HTTPException(status_code=401)

    body = await request.json()

    if not str(body.get("schema", "")).startswith("btcproc.candidate.v1"):
        # Незнакомая версия формата — записать и разобраться, а не падать.
        print("неизвестная схема:", body.get("schema"))

    cid = body["candidate_id"]
    if cid in seen:                      # дубль по Idempotency-Key
        return {"ok": True, "duplicate": True}
    seen.add(cid)

    # Отвечаем сразу: у отправителя таймаут 5 секунд и повторов не будет.
    print(body["symbol"], body["ts"], body["side"], body["rating"],
          body["quality_score"])
    return {"ok": True}
```
