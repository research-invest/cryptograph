Сейчас конвейер считает одну монету — ту, что лежит в `SYMBOL` (`BTCUSDT`).
Нужно научить его вести несколько пар одновременно: качать историю, обучать
графы состояний, выпускать кандидатов и показывать всё это в админке
с разделением по тикеру.

Аналогичная работа идёт в соседнем проекте **btc-graph** (приёмник
кандидатов) — раздел 9 фиксирует, что от него требуется, иначе кандидаты
по альткоинам будут приходить и молча получать warning-флаг.

## 1. Принятые решения — ✅

| Вопрос | Решение | Почему |
|---|---|---|
| Модель состояний | **своя на каждую монету** | Кластеризация ищет режимы конкретного инструмента. У ETH и SOL другая волатильность, другая структура объёма — общий граф размазал бы состояния по «средней монете». Плюс добавление новой пары не требует переобучения остальных |
| Список монет | **реестр-класс в коде** (`btcproc/symbols.py`) | Список монет — это данные о рынке (дата листинга, заметки, переопределения порогов), они должны версионироваться вместе с кодом и ревьюиться в диффе. `.env` остаётся для того, что зависит от окружения; `SYMBOL` в нём становится «монетой по умолчанию» для одиночных команд |
| Сопоставимость `group_id` | **не гарантируется между монетами** | Прямое следствие первого решения. `group_id` осмыслен только в паре `(symbol, run_id)` — это надо закрепить в документации и в UI |

Прямое следствие первого решения: **один прогон = одна монета**. Все таблицы,
привязанные к `run_id` (`state_models`, `market_groups`, `transitions`,
`event_blocks`), автоматически становятся помонетными без добавления колонки
`symbol`. Это экономит миграцию и, главное, делает невозможным состояние
«в одном прогоне смешаны две монеты».

## 2. Что уже готово и трогать не нужно

Приятная часть: `symbol` протянут через сигнатуры почти везде.

* `ingest/binance.py` — все функции принимают `symbol`, кэш дампов лежит
  в `data/binance/<symbol>/<tf>/`, PK `ohlcv` = `(symbol, tf, ts)`.
* `features/builder.py`, `features/events.py`, `candidates/outcomes.py`,
  `states/*` — считают по переданному DataFrame, о символе не знают вовсе.
* Таблицы `ohlcv`, `features`, `bar_events`, `outcomes`, `bar_states`,
  `candidates` уже содержат `symbol` в первичном ключе.
* `candidate_id` = хэш от `(symbol, ts, transition_id, event_block_id, offset)`
  — коллизий между монетами нет по построению
  (`candidates/builder.py:322`).
* Признаки стационарны (относительные величины, не цены), пороги событий
  заданы долями и квантилями — переносятся на другой инструмент без
  пересчёта констант.

Реальная работа — в местах, где символ берётся из `config.data.symbol`
по умолчанию, и в местах, где «последний прогон» ищется без учёта монеты.

## 3. Реестр монет — новый модуль `btcproc/symbols.py` — ✅

```python
"""
Реестр торгуемых пар.

Список живёт в коде, а не в окружении: дата листинга и переопределения
порогов — это знание о рынке, оно должно версионироваться вместе с кодом.
SYMBOL из .env остаётся монетой по умолчанию для одиночных команд.
"""

@dataclass(frozen=True)
class SymbolSpec:
    ticker: str
    # Раньше этой даты дампов на data.binance.vision просто нет.
    # Занижать безопасно (лишние месяцы дадут 404 и попадут в missing_months),
    # но каждый лишний месяц — это лишний HTTP-запрос при каждом ingest.
    history_start: str
    enabled: bool = True
    # Переопределения StatesConfig для короткой истории (см. раздел 7).
    states_overrides: dict[str, Any] = field(default_factory=dict)
    note: str = ""


SYMBOLS: tuple[SymbolSpec, ...] = (
    SymbolSpec("BTCUSDT", "2017-08-01"),
    SymbolSpec("ETHUSDT", "2017-08-17"),
    ...
)


def enabled() -> list[SymbolSpec]      # только активные, в порядке объявления
def get(ticker: str) -> SymbolSpec     # неизвестный тикер → понятная ошибка со списком известных
def default() -> SymbolSpec            # get(config.data.symbol), с внятной ошибкой если его нет в реестре
def tickers() -> list[str]
```

Требования:

1. `get()` на незнакомом тикере кидает не `KeyError`, а сообщение вида
   `«Монета XYZUSDT не заведена в btcproc/symbols.py. Известные: …»` —
   опечатка в CLI не должна выглядеть как «нет данных».
2. `config.data.symbol` обязан присутствовать в реестре; проверка — при
   старте админки, рядом с проверкой плейсхолдеров паролей в `config.py`.
   Иначе дефолт указывает в никуда, а обнаружится это на середине прогона.
3. `history_start` монеты **перекрывает** `HISTORY_START` из `.env`;
   значение из `.env` остаётся дефолтом для монет, у которых поле не задано.
4. Даты листинга проверять по факту, а не по памяти. Дешёвый способ:
   разовый прогон `ingest` с заведомо ранней датой и просмотр
   `missing_months` в ответе — первый месяц, которого нет в списке пропусков,
   и есть настоящее начало истории. Опционально — хелпер
   `binance.resolve_history_start(symbol)`, который ищет его перебором месяцев.

## 4. Изменения схемы БД — ✅

`btcproc/db/schema.sql` идемпотентен и гоняется при каждом `make init-db` —
правки вносятся туда, отдельный механизм миграций не нужен.

```sql
-- Прогон всегда про одну монету. Колонка, а не params->>'symbol':
-- по ней идут выборки «последняя модель монеты» и фильтр списка прогонов.
ALTER TABLE runs ADD COLUMN IF NOT EXISTS symbol TEXT;
UPDATE runs SET symbol = COALESCE(params->>'symbol', 'BTCUSDT') WHERE symbol IS NULL;
CREATE INDEX IF NOT EXISTS runs_symbol_started_idx ON runs (symbol, started_at DESC);

-- last_candidate_ts и страница кандидатов теперь всегда фильтруют по монете.
CREATE INDEX IF NOT EXISTS candidates_symbol_ts_idx ON candidates (symbol, ts DESC);

-- Покрытие истории в status/дашборде считается по (symbol, tf).
CREATE INDEX IF NOT EXISTS ohlcv_symbol_tf_ts_idx ON ohlcv (symbol, tf, ts DESC);
```

`UPDATE` в идемпотентном скрипте безопасен: он проставляет значение только
там, где колонка пустая, — то есть ровно один раз, на существующих прогонах.
Все они были по BTCUSDT.

Колонку `symbol` в `state_models`, `market_groups`, `transitions`,
`event_blocks` **не добавляем** — см. раздел 1: `run_id` уже однозначно
задаёт монету. Если когда-нибудь появится общая модель на несколько монет,
это решение придётся пересмотреть; пометить в `docs/development_log.md`.

## 6. Ловушка, которую нельзя пропустить: `configuration_hash` без монеты — ✅

`candidates/builder.py:326`:

```python
"configuration_hash": _hash(row["transition_id"], row["event_block_id"],
                            row["age_bucket"], row["entropy"], length=16),
```

Символа в хэше нет. Пока монета одна, это неважно. Как только их станет
несколько — btc-graph дедуплицирует по этому полю с TTL 30 минут
(`src/cache/redis_cache.py`, `DEDUP_TTL = 1800`) и **переиспользует оценку
чужого кандидата**: `src/agent/pipeline.py:102` явно достаёт из Redis
готовую оценку по совпавшему хэшу. Одинаковый переход на BTC и ETH в пределах
получаса — и ETH получит оценку BTC. Диагностировать это по данным почти
невозможно: кандидат выглядит нормально оценённым.

То же и с `candidate_family_key` (`builder.py:328`) — btc-graph фильтрует
и группирует по нему, без символа семейства двух монет сольются.

**Правка:** `symbol` первым компонентом в оба поля.

```python
"configuration_hash": _hash(symbol, row["transition_id"], row["event_block_id"],
                            row["age_bucket"], row["entropy"], length=16),
"candidate_family_key": (
    f"{symbol}|{row['current_group_id']:g}|{row['transition_id']}"
    f"|{row['event_block_id']}|{bias}"
),
```

Побочный эффект: хэши и family_key всех ранее выпущенных кандидатов
изменятся. Это допустимо (дедуп живёт 30 минут, семейства пересчитываются),
но `test_generated_candidates_match_btc_graph_schema` и любые зафиксированные
в тестах значения нужно обновить осознанно, а не «подогнать под красное».

## 7. Короткая история и пороги кластеризации — ✅

`STATES_MIN_GROUP_SIZE = 800`, `STATES_SEED_CLUSTERS = 8` и
`STATES_MAX_DEPTH = 4` подобраны под ~300 тыс. баров BTC 15m с 2017 года
(комментарий в `config.py`). Монета с двумя годами истории даёт ~70 тыс. баров:
при том же пороге дробление остановится рано и граф выйдет заметно грубее —
не потому, что рынок однороднее, а потому, что порог абсолютный.

Решение — в два шага, оба нужны:

1. **`min_group_size` считать относительно длины истории:**
   `max(min_group_size, round(min_group_share * len(features)))`, где
   `min_group_share` — новый параметр в `StatesConfig` (ориентир 0.0025,
   что на истории BTC даёт те же ~800). Абсолютный минимум остаётся нижней
   границей: группа меньше сотен баров не даёт статистики кандидату при любой
   длине истории.
2. **`states_overrides` в `SymbolSpec`** — точечное переопределение для монет,
   которым общая формула не подошла. Применяется через
   `dataclasses.replace(config.states, **spec.states_overrides)`;
   `fit_states` уже принимает `cfg`, менять её сигнатуру не нужно
   (`states/clustering.py:202`).

Приёмка по каждой новой монете — числа того же порядка, что у BTC:
40–50 состояний в графе и доля `scope=transition+event_block` в
`runs.stats.candidates.scopes` заметно больше нуля (инвариант 3 из
`CLAUDE.md`). Если у монеты получилось 5 состояний — это не «такой рынок»,
это неподошедшие пороги.

## 8. CLI — ✅

Общий принцип: у команд, работающих с данными, появляется `--symbol`
(можно указать несколько раз) и `--all` (все активные из реестра).
Без флагов поведение прежнее — монета из `.env`, чтобы существующие
скрипты и `make train` не сломались.

```bash
python3 -m btcproc.cli ingest --symbol ETHUSDT --symbol SOLUSDT
python3 -m btcproc.cli train  --symbol ETHUSDT
python3 -m btcproc.cli train  --all           # последовательно, по монете за раз
python3 -m btcproc.cli live   --all
python3 -m btcproc.cli status                 # таблица по всем активным монетам
```

Требования к пакетному режиму (`--all`):

* Монеты обрабатываются **последовательно**, каждая — своим `run_id`.
  Параллелизм здесь не нужен: узкое место — CPU на кластеризации, и два
  одновременных train просто отнимут память друг у друга.
* Падение на одной монете **не останавливает остальные**. Прогон помечается
  `failed` с диагнозом (как сейчас), цикл идёт дальше, в конце — сводка
  «5 из 7 успешно, ETHUSDT: нет баров, XRPUSDT: таймаут Binance».
  Это ровно тот случай, ради которого в проекте оставлен
  `except Exception  # noqa: BLE001`.
* Итоговый ненулевой exit code, если упала хотя бы одна монета — иначе cron
  будет рапортовать об успехе.

`status` перестраивается в таблицу: строка на монету — покрытие базового ТФ,
отставание баров, число кандидатов и очередь отправки, дата последнего
успешного train. Диагностика окружения (интерпретатор, `pgvector`/`neo4j`,
приёмник) остаётся общей, печатается один раз.

## 9. Админка — ✅

Монета становится сквозным измерением интерфейса.

* **Селектор монеты в шапке** (`templates/base.html`), значение хранится
  в query-параметре `?symbol=`, дефолт — `config.data.symbol`.
  Выбранная монета прокидывается во все ссылки страниц.
* `queries.overview()` — принимает `symbol`; сводка и покрытие считаются
  по нему, «последний train» ищется через `latest_completed_run("train", symbol)`.
* `queries.chart_data()` — заменить `config.data.symbol` в `params`
  (`queries.py:111`) на аргумент. `run_id` и `symbol` обязаны быть
  согласованы: график BTC с раскраской по прогону ETH молча отдаст пустую
  раскраску (LEFT JOIN не совпадёт по symbol). Проверять их согласованность
  и отдавать понятную ошибку, а не пустой график.
* `queries.candidates_page()` — фильтр `symbol` в `where`; колонка с тикером
  в таблице.
* Страницы графа и состояний — заголовок обязан называть монету. `group_id 7`
  без указания монеты бессмысленен (раздел 1), и это главный способ
  запутаться в новом интерфейсе.
* **Блокировка одновременных прогонов** (`admin/app.py:269`, `admin/app.py:285`):
  сейчас `active_run()` запрещает любой второй прогон. Заменить на
  `active_run(symbol=…)` — прогоны разных монет независимы и должны
  запускаться параллельно. Но: они идут `BackgroundTasks` в процессе админки,
  и три одновременных train займут три ядра и утроят память. Ограничить
  число одновременных прогонов (2–3, параметр в `AdminConfig`), при
  превышении — 409 с внятным текстом, как сейчас.
* Форма запуска — выбор монеты (или «все активные»).

## 10. Что требуется от btc-graph — ✅

В приёмнике зашит фильтр на одну монету —
`/Volumes/work/btc-graph/src/validator/candidate_validator.py:16`:

```python
if candidate.symbol != "BTCUSDT":
    flags.append("symbol_not_btcusdt")
```

Пока он на месте, **каждый** кандидат по альткоину получает
warning-флаг и режется скорером — то есть вся работа по этой задаче
не даст ни одного принятого кандидата.

Что нужно сделать на стороне btc-graph:

1. Заменить константу на список разрешённых символов (env
   `ALLOWED_SYMBOLS=BTCUSDT,ETHUSDT,…` либо свой реестр — по решению
   того проекта). Флаг переименовать в `symbol_not_allowed`: смысл проверки
   меняется с «не биткоин» на «не в списке поддерживаемых».
2. `src/models/candidate.py:58` — `symbol: str = "BTCUSDT"` как значение
   по умолчанию оставить можно (мы всегда передаём поле явно), но
   осмысленнее сделать поле обязательным: молчаливый дефолт превратит
   потерянное поле в биткоин.
3. `src/db/orm_models.py:23,65,82` — `default="BTCUSDT"` в колонках:
   проверить, что нигде не подставляется вместо реального значения.
   Особенно строка 65, где `symbol` входит в первичный ключ.
4. Убедиться, что Neo4j-граф разделяет узлы по монете — иначе состояния
   разных монет с одинаковыми `group_id` склеятся в один узел. Это зеркало
   нашего решения из раздела 1 и, вероятно, самое дорогое место правки
   на той стороне.

Порядок работ: пункты 1–4 на стороне btc-graph должны быть готовы **до**
первого `train --symbol <альткоин>` с `do_emit=True`. Наш прогон с
`--no-emit` от них не зависит и может идти параллельно.

### Исходный текст критериев

1. `train --all` и `live --all` проходят по всем активным монетам; падение
   одной не мешает остальным; exit code ненулевой при любой неудаче.
2. У каждой монеты — свой граф состояний; `bar_states`, `candidates`,

3. Кандидаты разных монет с одинаковой конфигурацией имеют разные

## 16. Что осознанно не делаем

* **Общую модель состояний на все монеты.** Требует нормализации признаков
  между инструментами и переобучения всех монет при добавлении одной.
  Если понадобится сравнивать состояния монет между собой — отдельная
  задача, и она отменит решение из раздела 4 не добавлять `symbol`
  в таблицы, привязанные к `run_id`.
* **Кросс-монетные признаки** (доминирование BTC, корреляция с ETH).
  Осмысленно и, вероятно, ценно — но это про качество сигнала, а не про
  поддержку нескольких монет. Отдельная задача.
* **Параллельный расчёт монет.** Узкое место — CPU на кластеризации;
  последовательный прогон предсказуем по памяти и проще в диагностике.
* **Управление списком монет из админки.** Реестр в коде — сознательное
  решение (раздел 1). Если потребуется включать/выключать монету без
  деплоя, добавится флаг `enabled` в отдельной таблице поверх реестра,
  а не замена реестра таблицей.

## 17. Оценка объёма данных

Одна монета на 15m с 2017 года — ~300 тыс. баров: около 60 МБ кэша дампов
в `data/binance/<symbol>/` и сопоставимый объём в `ohlcv`, плюс `features`
(32 значения на бар) и `candidates` — самая тяжёлая таблица. Умножается
на число монет линейно; у альткоинов с поздним листингом — меньше
пропорционально длине истории. Перед заведением десятка монет стоит
посмотреть фактический размер схемы `processing` после BTC
(`\dt+` в psql) и умножить.

## 18. Сделано сверх задачи: имена состояний (2026-08-08)

В задаче этого не было; появилось из практики — на графике с тремя десятками
состояний цвета похожи, и «угадай состояние по оттенку» оказалось плохой
механикой.

**Ключевое решение: имя выводится из статистики, а не задаётся руками.**
`train` перенумеровывает состояния при каждом прогоне, поэтому справочник имён
протух бы при первом переобучении — причём молча: номер остался бы на месте,
а рынок под ним стал бы другим. Имя считается в `graph.group_stats` из
`top_features` и хранится в `market_groups.name` рядом с ними, ключ
`(run_id, group_id)`.

Что это даёт на практике: один и тот же `group_id` в прогонах #4 и #12 (обе —
BTCUSDT) получает разные имена, потому что за номером стоят разные кластеры.
При выкладке на другой контур ничего мигрировать не нужно — туда едет только
словарь «признак → формулировка», привязанный к именам признаков, а не к
номерам состояний.

| Что | Где |
|---|---|
| Словарь формулировок, пять смысловых осей | `btcproc/states/naming.py` |
| Хранение | `market_groups.name`, схема идемпотентна |
| Бэкфилл старых прогонов | `scripts/backfill_state_names.py` (считает из уже сохранённых `top_features`, граф пересчитывать не нужно) |
| Легенда графика | `3 (волатильность гаснет · недельный спад…)` |
| Подсказка на графике | одна строка при наведении на свечу: цвет, номер, имя, переход |
| Номера состояний на графике | на первом баре отрезка; порог длины отрезка адаптивный, около 40 подписей на любом масштабе |
| Граф состояний | подсказка узла, панель деталей, переключатель «имена на узлах» |
| Тесты | `tests/test_naming.py`, 12 штук |

Оси нужны, чтобы имя не выходило вида «перекуплен · перекуплен · перекуплен»:
`rsi`, `tf1h_rsi`, `tf4h_rsi` и `tf1d_rsi` — один смысл на разных таймфреймах,
в подпись попадает сильнейший.

## 19. Прочее, сделанное попутно

* **Цикл по монетам вынесен из CLI в `binance.sync_many`.** Он нужен трём
  вызывающим — команде `ingest --all`, форме админки и обкатке новой монеты.
  Возвращает структурную сводку, не печатает; падение одной монеты не рушит
  пакет.
* **`sync_recent` для монеты без единого бара** стартовал от общего
  `HISTORY_START`; теперь от даты листинга из реестра.
* **`emit` печатает прогресс.** У `emit_pending` колбэк был, CLI его не
  передавал — на очереди в 34 тысячи это час полной тишины, неотличимый
  от зависшей команды.
* **Починен `BTC_GRAPH_PATH`.** В `.env` и в дефолте `config.py` был записан
  каталог, которого нет с переезда проектов. Симптомы тихие: `SINK_MODE=direct`
  падал, а `test_generated_candidates_match_btc_graph_schema` **молча скипался**
  — контракт схемы между проектами перестал проверяться незаметно. Дефолт
  теперь вычисляется от расположения `config.py`.
* **Админка переименована в crypto-graph**, знак и favicon — фрагмент графа
  состояний. Пакет остался `btcproc`: его переименование молча ломает
  `SINK_MODE=direct` (инвариант 1 в CLAUDE.md).
* **В таблицу прогонов добавлена колонка «Монета»** — список сводный по всем
  монетам, и без неё «train 38%» не отвечал на вопрос, чей это train.
