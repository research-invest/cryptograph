# ТЗ: страница «ИИ-разбор» — дайджест по всем монетам (17.08.2026)

Статус: **постановка, не реализация.** Решения по развилкам приняты владельцем
17.08.2026: дайджест по всем монетам сразу, вызов модели по кнопке с кэшем,
страница живёт в админке btcproc.

## 1. Зачем

Сейчас, чтобы понять «что вообще происходит», оператор открывает шесть раз
`/graph`, шесть раз `/candidates` и сам держит в голове, что изменилось со
вчера. Данные для ответа в базе есть целиком — не хватает связного текста.

Страница `/analysis` даёт один текст на весь контур: где какая монета сейчас
стоит, чем этот режим отличается от обычного, что бывало после него в истории
и что за сутки выпустил генератор.

## 2. Чего страница НЕ делает

Это не прогноз и не сигнал, и текст обязан читаться именно так.

* Система измерена на отложенной части истории и **утверждение «после такой
  конфигурации чаще бывало вверх» не подтвердилось** (CLAUDE.md, раздел
  «Что установлено замером»; `development_log.md`, разделы 26 и 31). Дайджест
  описывает разметку истории, а не будущее;
* слова «вероятность», «прогноз», «сигнал», «точка входа», «цель», «стоп»
  в тексте недопустимы — ни от модели, ни в подписях страницы;
* дайджест **не участвует в прогоне**: `train`/`live` его не считают и не
  ждут, отсутствие ключа или отказ API на расчёт кандидатов не влияют никак.
  Тот же принцип, что у `fetch-external` и `ingest-metrics`;
* дайджест **никуда не уходит наружу**: ни в `btcproc/notify/`, ни в Telegram
  монитора. Только страница админки.

## 3. Инвариант: числа считает SQL, модель только формулирует

Это тот же жёсткий раздел ролей, что между btcproc и btc-graph и внутри
btc-graph между скорером и LLM. Практически:

* весь вход промта собирается детерминированно, одной функцией
  `btcproc/ai/digest_input.py::collect(symbols)`. Никаких «пусть модель
  посчитает долю» — доли, лифты, счётчики уже в JSON;
* модель не получает сырых рядов и не имеет доступа к базе. Только собранный
  снимок;
* если вызов не удался, страница показывает **сам снимок** таблицей и текст
  ошибки. Пустой страницы быть не должно — данные есть и без модели.

## 4. Что попадает в снимок

На каждую монету из реестра (`btcproc/symbols.py`, сейчас шесть):

| Поле | Откуда |
|---|---|
| `symbol`, `venue`, `base_tf` | реестр монет |
| `last_bar_ts`, `lag_minutes` | `max(ts)` в `ohlcv` |
| `model_run_id`, `trained_at`, `states_total` | `state_models` + `market_groups` |
| `state.group_id`, `state.name`, `state.share`, `state.up_share`, `state.avg_ret_pct` | последняя строка `bar_states` в `model_run_scope()` + `market_groups` |
| `state.top_features` — до 5 штук с **русскими названиями** | `market_groups.top_features` через `naming.feature_labels()` |
| `state.bars_in_state`, `state.entered_at` | длина текущего сегмента `bar_states` |
| `state.context_atoms` — до 5 штук с лифтом | `state_context` (`queries.state_context_atoms`) |
| `last_transition.transition_id`, `.rarity`, `.count`, `.up_share` | `transitions` |
| `candidates_24h`: всего, по рейтингам, по сторонам | `candidates` за сутки в scope модели |
| `candidates_24h.best`: id, рейтинг, `quality_score`, сторона, переход | там же |
| `changed_since_yesterday`: сменилось ли состояние за 24 ч | `bar_states` |

Плюс общая шапка: время сборки, список монет с отставанием данных больше
часа, монеты без свежего `live`-прогона, версия промта.

**Русские названия признаков берутся из `naming.AXES`** — того же словаря, что
подписывает панель узла графа и селектор индикатора (журнал, раздел 45).
Второго словаря для промта не заводить: разъехавшись, текст объяснял бы
состояние не теми словами, которыми оно названо.

## 5. Промт

Версионируется константой `PROMPT_VERSION` и хранится вместе с ответом:
старый отчёт должен читаться с тем промтом, которым он сделан.

Системная часть (черновик):

> Ты аналитик-исследователь рынка криптовалют. Тебе дают снимок разметки
> истории: рынок каждой монеты разбит на состояния по вектору признаков,
> и про каждое состояние известно, чем оно отличается от среднего и что
> бывало в истории после него.
>
> Твоя задача — связно описать текущую картину по всем монетам.
>
> ВАЖНО:
> — это описание разметки истории, а не прогноз. Проверка на отложенной
>   части истории показала, что исторические доли исходов не переносятся на
>   невиданные данные;
> — не употребляй слова «вероятность», «прогноз», «сигнал», «вход», «цель»,
>   «стоп». Говори «в истории после такого состояния», «состояние выделяется
>   тем-то»;
> — не сравнивай quality_score разных монет: он посчитан помонетным профилем;
> — не додумывай чисел, которых нет во входных данных;
> — если данные монеты устарели или прогонов нет, скажи это прямо.

Пользовательская часть — JSON снимка целиком плюс просьба вернуть JSON:

```json
{
  "headline": "одно предложение — что общего по контуру",
  "per_symbol": [{"symbol": "...", "text": "2–4 предложения"}],
  "watch": ["1–3 наблюдения, что стоит посмотреть глазами"],
  "data_caveats": ["проблемы с данными, если есть"]
}
```

Разбор по монете идёт **отдельным полем на монету**, а не сплошным текстом:
страница показывает его в карточке рядом с числами этой монеты, и склеенный
текст пришлось бы резать регулярками.

## 6. Кэш и кнопка

Расчёт запускает только кнопка на странице (админка уже за авторизацией).

* `input_fingerprint` = sha256 канонического JSON снимка. Повторный клик при
  том же отпечатке **не идёт в API**, а отдаёт сохранённый отчёт и показывает
  «данные с прошлого разбора не менялись»;
* новый бар меняет отпечаток, поэтому «свежесть» отчёта видна честно: рядом
  с текстом всегда стоит время бара, по которому он сделан, а не время
  генерации;
* защита от растраты: не чаще одного вызова в `AI_DIGEST_MIN_INTERVAL`
  (по умолчанию 10 минут) и не больше `AI_DIGEST_DAILY_LIMIT` (по умолчанию
  20) вызовов в сутки. Превышение — сообщение на странице, а не молчание.

Таблица (схема `processing`, добавляется в `db/schema.sql`, создаётся
`make init-db`):

```sql
CREATE TABLE IF NOT EXISTS ai_digests (
    id              bigserial PRIMARY KEY,
    created_at      timestamptz NOT NULL DEFAULT now(),
    prompt_version  text        NOT NULL,
    model           text        NOT NULL,
    input_fingerprint text      NOT NULL,
    snapshot        jsonb       NOT NULL,   -- вход, чтобы отчёт читался спустя месяц
    report          jsonb,                  -- ответ модели; NULL, если вызов не удался
    error           text,
    tokens_in       integer,
    tokens_out      integer,
    latency_ms      integer
);
CREATE INDEX IF NOT EXISTS ai_digests_fresh ON ai_digests (created_at DESC);
CREATE INDEX IF NOT EXISTS ai_digests_fp ON ai_digests (input_fingerprint, created_at DESC);
```

Хранится и снимок, и ответ: без снимка отчёт месячной давности нечем
проверить, а перечитать те же числа из базы уже нельзя — `train`
перенумеровывает состояния.

## 7. Конфигурация

Новые переменные в `btcproc/.env` (и в `deploy/02_configure.sh`):

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `ANTHROPIC_API_KEY` | — | ключ. Без него страница показывает снимок и подсказку, что разбор недоступен |
| `AI_DIGEST_MODEL` | `claude-sonnet-5` | дайджест — сжатие готовых чисел в текст, для этого opus не нужен |
| `AI_DIGEST_MIN_INTERVAL` | `600` | секунд между вызовами |
| `AI_DIGEST_DAILY_LIMIT` | `20` | вызовов в сутки |

Зависимость `anthropic` добавляется в `requirements.txt` btcproc. Ключ
btc-graph переиспользовать нельзя: это другой контейнер и другой процесс,
общий у них только `.env`-подход, а не окружение.

## 8. Страница `/analysis`

* селектора монеты нет — дайджест общий; ссылки с каждой карточки ведут
  на `/graph?symbol=…` и `/candidates?symbol=…`;
* шапка: время бара, по которому сделан разбор, модель, версия промта,
  кнопка «пересчитать», расход токенов последнего вызова;
* тело: `headline`, карточка на монету (числа слева, текст модели справа),
  блок «на что посмотреть», блок «претензии к данным»;
* сноска, повторяющая раздел 2: разбор описывает разметку истории;
* отказ API: красная плашка с текстом ошибки, ниже — снимок таблицей.

## 9. Приёмка

Тесты (инфраструктура не нужна, как и во всех тестах btcproc):

1. `collect()` на подготовленных строках базы даёт снимок с ожидаемыми
   полями, признаки в нём подписаны по-русски;
2. отпечаток не меняется от порядка ключей и от порядка монет;
3. второй вызов при неизменном отпечатке не ходит в API (клиент подменён
   заглушкой, счётчик вызовов равен единице);
4. отказ API не роняет ручку: возвращается снимок и `error`;
5. промт содержит дисклеймер и список запрещённых слов;
6. запрещённые слова в ответе модели помечаются в интерфейсе (мягкая
   проверка: показать плашку «модель нарушила формулировку», не прятать
   текст) — тест на саму проверку, а не на модель.

Гейт на выкатку: на боевых данных шести монет снимок собирается меньше чем
за две секунды и укладывается в 8 КБ JSON. Не уложился — резать надо состав
снимка, а не молча увеличивать лимит: длинный вход даёт длинный и общий текст.

## 10. Этапы

1. `btcproc/ai/digest_input.py` + тесты 1–2. Ничего не вызывает наружу,
   проверяется целиком локально;
2. таблица `ai_digests` в `schema.sql`;
3. `btcproc/ai/digest.py`: промт, вызов, разбор ответа, лимиты, кэш; тесты 3–6;
4. роут `/analysis` + шаблон + пункт в меню и в `/help`;
5. запись в `docs/development_log.md`; раздел в `operator_guide.md` —
   что делать, когда кнопка ругается на ключ или на лимит;
6. `deploy/02_configure.sh`: переменные в `.env` боевого контура.

## 11. Что осознанно не делается

* автоматический пересчёт по крону — токены тратились бы и тогда, когда
  страницу никто не открывает; при необходимости добавляется позже, схема
  таблицы это переживёт;
* отправка дайджеста в Telegram — там короткие уведомления оператору о
  ресурсах хоста, смешивать контуры не будем;
* разбор отдельного кандидата на `/candidates/{id}` — это другая задача, и
  для неё в btc-graph уже есть промт и `use_llm`;
* сравнение монет между собой по `quality_score` — числа несравнимы по
  построению, и просить об этом модель нельзя.
