This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Язык проекта — русский: docstrings, комментарии, сообщения CLI и UI пишутся по-русски.
Подробная документация — `README.md` (архитектура и обоснования), `docs/operator_guide.md`

## Команды

Расписание на сервере: `live` каждые полчаса, `train` раз в неделю
(воскресенье 03:20 UTC, `--no-emit`), сводка раз в сутки. `live` и `train`
одной монеты блокируют друг друга, поэтому оба стоят в кроне с
`--skip-if-busy`: занятая монета пропускается без ошибки, точка продолжения
берётся из данных и следующий запуск догоняет.

```bash
make setup                  # .env из .env.example
make install                # зависимости в активный интерпретатор
make init-db                # схема processing в БД btc_graph
make train                  # полный прогон истории (30–60 мин), монета из .env
make train-all              # то же по всем активным монетам, последовательно
make train-fast             # пересчёт по данным из БД, без отправки
make live                   # инкрементальный прогон — штатное обновление
make live-all               # то же по всем активным монетам
make status                 # таблица по монетам: покрытие, отставание, очередь
make admin                  # админка на http://127.0.0.1:8100 (--reload)
make test                   # pytest -q
make fetch-external         # внешние дневные ряды (Fear & Greed) в external_daily
make hostmon                # монитор нагрузки хоста (в проде — systemd btcproc-hostmon)
make hostmon-test-telegram  # проверить канал уведомлений о нагрузке
make ingest-metrics         # деривативные метрики Binance USD-M в deriv_metrics
make ingest-depth           # снимок стакана в depth_snapshots (в кроне раз в минуту)
```

`fetch-external`, `ingest-metrics` и `ingest-depth` стоят особняком: это
команды, ходящие в чужой (для `ingest-metrics` — в другой каталог того же
Binance) API, и в `train`/`live` их нет намеренно — сетевой поход не должен ронять или
замедлять регулярный прогон. Прогоны только читают таблицы. Отсюда
следствие, которое легко проглядеть: если включить `FGI_ENABLED=true` или
`DERIV_ENABLED=true`, не заведя соответствующую команду в крон, ряд
протухнет молча — свежие бары начнут получать `False`/`NaN` без единой
ошибки в логе.

**Отдельно про адреса бирж: архивы и REST блокируются по-разному.** Дампы
(`data.binance.vision`, `public.bybit.com`) отдаются откуда угодно, а
биржевой REST — нет: с боевого VPS `api.binance.com` отвечает **451**,
`api.bybit.com` — **403**, и у второго обхода не нашлось (зеркала
`api.bytick.com` / `api.bybit.nl` блокируются так же — по адресу, а не по
домену). Для Binance обход есть и вынесен в `BINANCE_REST_URL`
(`data-api.binance.vision`), поэтому **любой новый поход в REST обязан брать
адрес оттуда, а не писать хост в модуле**. Цена ошибки — тихая: `ingest-depth`
хардкодил хост и сутки не собирал ничего, а таблица, ради непрерывности
которой всё и заводилось, стояла пустой (раздел 62.7).

Уведомления (вебхуки) настраиваются в админке; из терминала полезны две
команды: `python3 -m btcproc.cli notify-example` — пример тела запроса для
принимающей системы, `notify-test --rule N` — разовая отправка на адрес
правила. Формат — `docs/notifications.md`.

Всё это обёртки над `python3 -m btcproc.cli <команда>`. Интерпретатор задаётся
через `make train PY=.venv/bin/python`.

Мультимонетность: у команд с данными есть `--symbol` (можно несколько раз) и
`--all`. Без флагов — монета из `.env`. Реестр пар — `btcproc/symbols.py`,
сейчас заведены BTCUSDT, ETHUSDT, SOLUSDT, HYPEUSDT, AAVEUSDT, TAOUSDT и
PUMPUSDT (все активны; HYPEUSDT — с Bybit, `venue="bybit_spot"`; у TAOUSDT
единственные в реестре `states_overrides`, журнал 42; PUMPUSDT — самая
короткая история в реестре, около года, журнал 62). Цикл по монетам живёт
в `sources.sync_many`, а не в CLI: он нужен ещё админке и обкатке новой монеты.

Быстрая проверка без ожидания полного прогона:

```bash
python3 -m btcproc.cli ingest --start 2024-06-01
python3 -m btcproc.cli train --no-ingest --no-emit --start 2024-06-01
```

### Тесты

```bash
python3 -m pytest tests/test_states.py                              # один файл
python3 -m pytest tests/test_candidates.py::test_outcomes_match_prices -q   # один тест
python3 -m pytest -k lookahead
```

Тесты не ходят ни в БД, ни в сеть — данные генерирует `make_bars()` из
`tests/conftest.py` (синтетические свечи с чередующимися режимами, чтобы
кластеризации было что находить). Фикстуры `bars` / `context` / `features` —
session-scoped.

Прогонять стоит в обоих окружениях, если их несколько (`python3` и
`.venv/bin/python`): версии pandas/numpy расходятся, и часть багов
(read-only массив из `to_numpy()` на pandas 3, `NaN` вместо `None`)
воспроизводится только на свежих библиотеках.

**И отдельно — с флагами источников, выставленными в окружении:**

```bash
FGI_ENABLED=true SMC_ENABLED=true python3 -m pytest
```

Дефолты полей в `config.py` вычисляются один раз, на импорте, из окружения
процесса — поэтому на боевом VPS (где оба флага `true` в `.env`)
«конфигурация по умолчанию» означает «включён». Тест, сверяющийся с
`SMCConfig()` / `FearGreedConfig()` или подменяющий один источник из двух,
зеленеет локально и падает при выкатке. Так уже ловились два теста
(журнал, 34.10); заводя третий источник, проверь оба режима.

## Внешние зависимости

БД своей нет: PostgreSQL, Redis и Neo4j берутся из соседнего проекта
**btc-graph** (`../btc-graph`, `BTC_GRAPH_PATH`). Его стек должен быть поднят
(`cd ../btc-graph && make up && make migrate`) до любой команды, работающей с БД.
`docker-compose.yml` поднимает только админку и подключается к внешней сети
`btc-graph_default`.

Ловушка окружения: `pgvector` и `neo4j` импортирует не наш код, а btc-graph, и
делает это лениво уже внутри сохранения. При расхождении venv кандидаты
считаются, отправка рапортует об успехе, а записи нет — в логе
`ModuleNotFoundError` посреди прогона. `btcproc.cli status` печатает путь к
интерпретатору и проверяет наличие этих пакетов.

## Архитектура

Конвейер (`btcproc/pipeline/train.py` — стадии в этом порядке, каждая пишет
результат в БД под общим `run_id`):

```
бары → признаки → события → исходы → состояния → граф → кандидаты → btc-graph
```

`btcproc/features/smc.py` — детекторы Smart Money (структура, имбалансы,
ликвидность, зоны), за флагом `SMC_ENABLED`, по умолчанию выключенным.
Включённый флаг делает две разные по цене вещи:

* **16 контекстных атомов** — бесплатно. В маску не входят, `event_block_id`
  не меняют, переобучения не требуют. `live` со старой моделью их просто
  пишет, и по ним можно мерить лифт (`scripts/measure_atom_lift.py`).
* **12 признаков** и метка набора `v1+smc` вместо `v1` — дорого. Требует
  полного `train`, перенумеровывает `group_id` и сносит накопленный граф
  Neo4j. Прежняя причина «не рекомендуется» (двенадцать признаков любой
  природы обрушивали число состояний) **устранена 2026-08-11**: порог
  дробления выражен в сигмах референса и от размерности больше не зависит.
  Перед включением — прогнать `scripts/calibrate_split_gain.py --control`
  и убедиться, что контроль на шуме граф не рушит.

Статус работы — `docs/task_smc_integration.md` в корне crypto-graph,
результаты замеров — `development_log.md`, разделы 13–16 (первый заход) и
**21.10–21.13** (перемер починенным измерителем, 2026-08-11).

Коротко, чтобы не начинать с нуля (перемер 2026-08-11, разделы 21.10–21.13
и **22.5**):

* **зонная половина (ордер-блоки, FVG, брейкеры) — ноль в пяти независимых
  заходах**: маргинальный тест до пересборки и после, градация непрерывных
  признаков, три таймфрейма. Это устойчивый отрицательный результат;
* **устойчиво положительного по SMC нет ни одного.** `structure_bullish`
  проходил 2 монеты из 3 на прежних моделях и 1 из 3 на новых — результаты
  лифта **не переживают пересборку модели**, потому что выборка кандидатов
  порождается моделью, а та чувствительна к полусотне баров (21.17). Через
  пересборку держится только `trend_down_align`, и это существующий трендовый
  атом, а не SMC;
* единственная неразобранная зацепка — `premium_discount`: знак один на трёх
  монетах, эффект растёт с таймфреймом (−0.036 → −0.065 → −0.084 на BTC), но
  предзаявленный критерий не прошёл. Содержательно это возврат к среднему, а
  не подтверждение SMC как рамки.

**Прежде чем ставить новые замеры по SMC, нужно стабилизировать
кластеризацию.** Пока число состояний меняется от полусотни баров, замер
лифта меряет реализацию модели, а не рынок.

**А прежде чем стабилизировать — прочитать раздел 26 журнала (2026-08-12).**
Валидация на отложенной части показала, что перекос, который система
приписывает конфигурации, на невиданных данных не реализуется: шесть замеров
из шести, три монеты × две модели, directional accuracy 0.497–0.516 при
блочных ДИ, накрывающих 0.5, наклон калибровки 0.02–0.07 при идеале 1.0,
неотличимость от «всегда long» на четырёх горизонтах. Замер воспроизводится
`make validate-holdout`. Пока владелец не решил, что делать с этим
результатом, работы по `crypto-graph/docs/plan_priority_2026-08-12.md`
дальше Ш0 не идут: они повышают точность измерения эффекта, которого нет.

**Вопрос закрывать нельзя одним «работает/не работает»:** контекстные атомы
остаются включёнными независимо от исхода — они стоят ~50 секунд на монету и
полезны для разметки. Спор всегда был не о том, интегрировать ли SMC (он
интегрирован: 16 атомов, бэкфилл на всей истории), а о том, давать ли зонам
влиять на `quality_score` и на определение состояний.

`btcproc/features/fear_greed.py` — **второй источник, Fear & Greed Index**,
за флагами `FGI_ENABLED` / `FGI_FEATURES_ENABLED`, обоими выключенными.
Устроен принципиально иначе, чем SMC: величина не считается из баров монеты,
а джойнится из общерыночного дневного ряда (`external_daily`, наполняет
`make fetch-external`). Отсюда два свойства, ломающие привычные рефлексы:

* **ряд один на все монеты**, поэтому «знак совпал на трёх монетах» для него
  не подтверждение, а один замер, показанный трижды. Устойчивость проверяется
  разбиением по эпохам (`scripts/measure_fgi_epochs.py`);
* **разрешение — сутки**: 96 одинаковых значений подряд, автокорреляция
  дневного ряда 125 дней. Блок бутстрапа по горизонту исхода здесь занижен
  втрое с лишним, поэтому у `measure_atom_lift.py` и
  `measure_feature_gradation.py` есть `--block-rows` (для FGI — 12000).

**Результат замера (2026-08-14, журнал раздел 34): источник отвергнут.**
Гейт R (предсказание размаха — та роль, где он считался наиболее
перспективным) не пройден ни на одной из 4 монет, ни на одном из 3
горизонтов, ни в одной из 3 эпох: `|rho(FGI, range_ratio)|` = 0.0003–0.054,
причём тривиальный бенчмарк `rv` предсказывает размах сильнее. Направление и
градация — тоже ноль, обе двумя методами. Признаки не заводятся; четыре
контекстных атома (`fear_extreme`, `greed_extreme`, `sentiment_flip_up`,
`sentiment_flip_down`) посчитаны и провалидированы и остаются как бесплатная
разметка. Постановка и гейты — `docs/task_fear_greed.md`.

`btcproc/features/deriv.py` — **третий источник, деривативные метрики
Binance USD-M** (открытый интерес, long/short ratio, давление тейкеров), за
флагами `DERIV_ENABLED` / `DERIV_FEATURES_ENABLED`. С 2026-08-15 в проде
поднят первый (контекстные атомы-квадранты), второй остаётся выключенным
(признаки не прошли гейт градации). Порядок ввода был соблюдён буквально:
код → крон `ingest-metrics` → наполнение `deriv_metrics` по всем монетам →
и только потом флаг.
Первый источник с ПОМОНЕТНЫМИ внешними данными (в отличие от SMC — считается
из баров — и FGI — один общий ряд): таблица `deriv_metrics` заполняется
отдельной командой `ingest-metrics`, вне `train`/`live`, и уже на сетке
базового ТФ (джойн без сдвига — в отличие от FGI, чей дневной агрегат
сдвигается на сутки; доказательство безопасности — докстринг
`ingest/metrics.py:aggregate`). Заведение источника вскрыло архитектурный
пробел: `build_features`/`detect_atoms` не получали монету явно, потому что
она не требовалась ни SMC, ни FGI — при `train --all` все монеты получили бы
метрики первой из `.env`. Закрыто пробросом `symbol` через всю цепочку
(`FeatureSource.compute(base, symbol)`), регрессия —
`test_compute_uses_passed_symbol_not_global_default`.

**Результат замера (2026-08-15, журнал раздел 36; ПЕРЕСМОТРЕН 2026-08-19,
раздел 47.4): у источника нет ни одного пройденного содержательного гейта.**
`oi_chg_1h` (log-изменение ОИ за час) проходил гейт R сверх бенчмарка `rv`
устойчиво на BTC/ETH/SOL с `ΔR²` 0.002–0.011. Эти числа воспроизводятся, но
бенчмарк был неполон: в скользящей `rv` нет времени суток, а по сессиям
меняются и открытый интерес, и размах. При бенчмарке «HAR-RV + час дня»
(`scripts/measure_range_horizons.py --task deriv`) медиана `ΔR²` падает до
0.0008, **ни одна из 54 ячеек не достаёт до порога практической величины
0.005**, и 63% эффекта съедает сезонность — оба условия отзыва из ТЗ
выполнены вместе, гейт R **отозван**. Гейт G не был пройден никогда.
Остальные пять величин (`oi_chg_1d`, `oi_rank`, `ls_retail_z`, `top_vs_retail`,
`taker_z`) прошли частично и непоследовательно между монетами. Проверка B4
(ожидавшийся дубликат спотового потока тейкеров, `taker_z` против
`taker_buy_dominance`/`taker_bias`) не подтвердилась — |r| ≤ 0.07 везде.
Четыре контекстных атома-квадранта `oi_vs_price` (`oi_up_price_up` и т.д.)
посчитаны и провалидированы, остаются как бесплатная разметка: они на гейт R
не опирались. Признаки не заводятся. Постановка и гейты —
`docs/tz_deriv_ingest_14-08-26.md`, перепроверка —
`docs/tz_range_horizons_19-08-26.md` §3 (обе в каталоге `crypto-graph`, не
`btc-graph-processing`).

`train` и `live` разделены принципиально: `train` переобучает модель состояний
с нуля (номера `group_id` нового прогона несопоставимы со старыми, накопленный в
Neo4j граф после этого смешивает две нумерации), `live` загружает сохранённую
модель последнего успешного train **своей монеты**
(`runs.latest_completed_run("train", symbol)`) и только размечает ей свежие
бары. Регулярное обновление — всегда `live`.

**Отсюда неочевидное: `bar_events` пополняет ТОЛЬКО `train`.** `live` пишет
`bar_states`, `features` и `candidates`, а в таблицу событий не пишет вовсе
(`repo.save_events` вызывается из `pipeline/train.py` и больше ниоткуда).
Поэтому `bar_events` штатно отстаёт от `ohlcv` на срок до недели — до
ближайшего воскресного переобучения, — и это не поломка, а устройство
контура. Практических следствий три, и все три обжигали:

* замер лифта по атомам идёт по данным **до последнего `train`**, а не до
  сегодня, — при `--metric realized` это молча укорачивает выборку;
* новый или изменённый контекстный атом не появляется на свежих барах сам:
  историю закрывает `scripts/backfill_context_atoms.py --force --all`,
  а хвост — ближайший `train`;
* «в `bar_events` данные трёхдневной давности» — не диагноз и не повод
  чинить `live`. Сверять надо с датой последнего `train` монеты.

**`features` в этот список больше не входит — с 2026-08-15.** Раньше входила,
и симптом был виден глазами на каждом графике: нижняя панель признака
обрывалась на дате последнего `train`, а свечи шли до текущего часа. `live`
признаки СЧИТАЛ всегда (без них нечем кормить модель), но не сохранял.
Теперь дописывает хвост — от `max(ts)` уже записанного набора, под **версией
набора модели**, а не под текущей меткой конфигурации: колонки к этому месту
уже приведены к `model.feature_names`, то есть массив позиционно совпадает с
`feature_sets.names` этой версии. Хвостом, а не всей историей: PK здесь
`(symbol, ts, version)`, и повтор был бы upsert'ом тех же чисел на триста
тысяч строк двенадцать раз в сутки.

**Один прогон = одна монета.** Модель состояний обучается на каждую пару
отдельно, поэтому `state_models`, `market_groups`, `transitions`, `event_blocks`
помонетны через `run_id` и колонки `symbol` не имеют. Отсюда же следует, что
`group_id` осмыслен только в паре `(symbol, run_id)`.

Точки продолжения `live` берутся из данных, а не из календаря: бары — от
`max(ts)` в `ohlcv`, кандидаты — от последнего выпущенного
(`pipeline/live.py:resolve_cutoff`). Перекрытие окон безопасно: `candidate_id`
детерминирован, запись идёт upsert'ом, `emitted_at` не сбрасывается.

Доставка в btc-graph в режиме `direct` — импорт его пакета: каталог добавляется
в `sys.path`, `DATABASE_URL` / `REDIS_URL` / `USE_DB` / `USE_REDIS` / `USE_GRAPH`
выставляются **до** импорта (его pipeline читает флаги на уровне модуля), дальше
вызывается `run_batch_pipeline(save=True)`. Кандидаты дублируются в
`processing.candidates` намеренно — btc-graph принимает только прошедших фильтр,
а для разбора нужен полный список.

Хранение: `db/session.py` — psycopg2 напрямую (`connect` выставляет `search_path`,
`bulk_upsert` — `INSERT ... ON CONFLICT` пачками), ORM нет из-за bulk-вставок
сотен тысяч строк. `db/runs.py` работает в autocommit — прогресс и лог прогона
должны быть видны админке до завершения транзакции.

Страница графика показывает не только свечи, раскрашенные состояниями: под
ними гистограмма объёма, панель одного признака **из набора модели прогона**
(`state_models.feature_ver` → `feature_sets.names`, значения читаются из
`features` — пересчитывать индикатор на клиенте нельзя, он разойдётся с
моделью) и строка инспектора с атомами бара. Атомы в инспекторе разделены на
signature и контекстные визуально: первые входят в `event_block_id`, вторые
нет, и одинаковыми в интерфейсе они выглядеть не должны (инвариант 3).
Обоснования — `docs/development_log.md`, раздел 28.

**Раскраска ограничена моделью, маркеры кандидатов — нет** (раздел 52).
`group_id` — нумерация конкретного обучения, поэтому цвет свечи берётся строго
по `model_run_scope`. Кандидат же либо был выпущен на этом баре, либо не был, и
переобучение задним числом этого не меняет; фильтр по модели давал здесь
инверсию — на старых барах показывались кандидаты, посчитанные новой моделью
ретроспективно (без рейтинга, никуда не отправленные), и прятались те, что
система действительно выпустила и оценила. Разделены не по модели, а по
происхождению: `layer=issued` (кандидаты live-прогонов — то, что сказано
тогда) и `layer=all` (плюс кандидаты train-прогонов — ретроспектива модели,
обученной в том числе на будущем этого бара). Второй слой рисуется другой
формой маркера, а непоказанные пересчитываются в строку под графиком.

**Слои различает ФОРМА маркера, а не цвет** (журнал 62.8). Цвет и подпись у
обоих одинаковые — рейтинг и оценка, — потому что серый цвет ретро означал
сразу две разные вещи: «оценки нет» и «оценка есть, но кандидат
ретроспективный». На монете, чей первый прогон шёл с отправкой, это давало
прямое противоречие: MODERATE 0.56 на графике выглядел как WEAK, а его
карточка рейтинг показывала. Серым остаётся ровно неоценённое (`rating IS
NULL` — обычный случай для ретро, недельный `train` идёт с `--no-emit`).
Менять форму обратно на общую нельзя: она единственная отличает «система
сказала это тогда» от «переобученная модель так думает про прошлое».

Админка (`admin/app.py`) запускает прогоны через `BackgroundTasks` в том же
процессе; `queries.py` — только чтение (с потолком `statement_timeout` на
запрос), `db/activity.py` — состояние самой базы (активные запросы для
страницы «Сервер», снятие зависшего бэкенда), `auth.py` — сессии, rate-limit,
allowlist.
Страниц девять: сводка, граф, график, **состояния** (полный список состояний
модели с цветами палитры графика — журнал 54), кандидаты, прогоны, **сервер**
(нагрузка хоста, прогоны и живой срез запросов PostgreSQL — журнал 44),
уведомления и `/help` — шпаргалка для оператора. Она выжимка из
`docs/operator_guide.md` и не заменяет его: процедуры (заведение монеты,
калибровка профиля) остаются в инструкции.

`btcproc/hostmon/` — **монитор ресурсов хоста** (страница `/server`, журнал
раздел 40). Устроен нарочито в стороне от остального: замеры пишет отдельный
процесс (`btcproc.cli hostmon`, в проде systemd-сервис `btcproc-hostmon`) в
SQLite-файл `<repo>/logs/hostmon.sqlite`, а не в Postgres, — монитор обязан
работать, когда docker-стек лежит, потому что именно тогда он и нужен. Файл
лежит вне каталогов подпроектов: `01_deploy.sh` гонит их `rsync --delete`.
Пороговые уведомления идут в Telegram (`hostmon/alerts.py`) и не имеют ничего
общего с `notify/` — там внешний контракт о кандидатах, здесь короткий текст
оператору о машине.

## Инварианты, которые легко сломать

Полное обоснование — README, раздел 3. Кратко, чего нельзя делать вслепую:

1. **Пакет называется `btcproc`, а не `src`.** Пакет btc-graph — `src`, и его
   ленивые импорты `from src.db...` резолвились бы в наш код, тихо ломая режим
   `direct`.
2. **Слияние состояний считается через d-prime** (разброс вдоль оси между
   центроидами), а не через радиус группы: радиус растёт как √d, при 32 признаках
   критерий «центроиды ближе суммы радиусов» схлопывает граф до 3–4 состояний
   вместо 43.
3. **В `event_block_id` входят только `SIGNATURE_ATOMS`** (пробои, всплески,
   кроссы, развороты), а не `CONTEXT_ATOMS` (тренд, сессии, доминирование
   тейкеров). Фон активен почти всегда и даёт комбинаторный взрыв блоков, после
   которого историческая выборка по блоку не набирается никогда. Проверка после
   правок: `runs.stats.candidates.scopes` — доля `transition+event_block` не
   должна быть близка к нулю.
   Фон при этом **сохраняется** — отдельной колонкой `bar_events.context_atoms`,
   а не внутри `atoms`: `atoms`, `atom_count`, `families` и `primary_family`
   обязаны описывать ровно то, что закодировано в маске. До 2026-08-09 контекст
   считался и молча выбрасывался, из-за чего лифт по фоновым атомам нельзя было
   измерить в принципе. Регрессии — `test_context_atoms_survive_to_the_output`,
   `test_context_atoms_do_not_change_block_id`.
   Новые атомы добавляются **только в конец** `ATOM_FAMILY`: вставка в середину
   сдвигает биты и меняет смысл всех исторических `event_block_id` без единой
   ошибки. Первые 20 битов прибиты тестом `test_signature_bits_are_pinned`.
4. **Признаки не заглядывают вперёд.** Старшие ТФ сдвигаются на бар,
   индикаторы считаются только по прошлому, выборка кандидата собирается из
   случаев раньше `t` и только с созревшими исходами. Закреплено тестами
   `test_features_do_not_look_ahead` и
   `test_candidate_sample_uses_only_matured_past`.
5. **Схема кандидата совместима с btc-graph по букве.** Каждый кандидат обязан
   пройти его pydantic-модель `Candidate` без правок —
   `test_generated_candidates_match_btc_graph_schema`.
6. **Символ входит в `configuration_hash` и `candidate_family_key`.** Без него
   btc-graph переиспользует оценку кандидата другой монеты: он дедуплицирует
   по хэшу с TTL 30 минут и явно достаёт готовую оценку из Redis. Одинаковый
   переход на BTC и ETH в пределах получаса — и ETH получит оценку BTC.
   Диагностировать по данным почти невозможно: кандидат выглядит нормально
   оценённым. Регрессия — `test_configuration_hash_includes_symbol`.
7. **Словарь формулировок обязан быть полным, и это проверяется.** Признак
   без строки в `naming.AXES` не ломает ничего заметного — он просто выпадает
   из подписи, и состояние, выделяющееся именно им, называется «рынок около
   среднего», то есть подпись врёт. Атом без строки в `naming.ATOM_LABELS`
   уходит в интерфейс сырым идентификатором. Оба случая закрыты тестами
   (`test_every_feature_has_a_phrase`, `test_atom_labels_cover_all_atoms`), и
   оба проверяют ОБА направления: и что словарь не ссылается на
   несуществующее, и что ничто существующее не осталось без формулировки.
   Осознанное исключение оформляется через `naming._UNNAMED`, а не молчанием.
   Словарь покрывает и SMC (двенадцать признаков, шестнадцать атомов), и
   Fear & Greed (два признака, четыре атома), хотя признаки обоих выключены:
   включение флага не должно требовать правок здесь.

8. **Имена состояний выводятся из статистики, а не задаются руками.**
   `train` перенумеровывает состояния при каждом прогоне, поэтому ручной
   справочник имён протух бы при первом переобучении — причём молча: номер
   остался бы на месте, а смысл под ним поменялся. Имя считается в
   `graph.group_stats` из `top_features` и хранится в `market_groups.name`
   рядом с ними. Словарь формулировок — `btcproc/states/naming.py`; опечатка
   в имени признака делает строку словаря мёртвой, на это есть тест
   `test_vocabulary_covers_only_real_features`.
9. **Порог дробления состояний относительный, а не абсолютный.** Эффективное
   значение — `max(min_group_size, round(min_group_share × число баров))`.
   Доля основной механизм, абсолютное число — пол «в сотни баров». Если поднять
   пол так, что он перекроет долю на всём диапазоне историй (как было с 800),
   относительный порог станет формальностью и монета с короткой историей снова
   получит грубый граф. Регрессия — `test_absolute_floor_does_not_swallow_the_share`.

10. **Gap-критерий дробления усредняет несколько референсов, а его порог задан
    в сигмах.** Абсолютный порог (`STATES_SPLIT_GAIN = 0.02`, до 2026-08-11)
    зависел от размерности: константа с 32 признаков в 44 означала другую
    строгость, и граф обрушивали двенадцать новых признаков ЛЮБОЙ природы,
    включая чистый шум. Один референс вдобавок означал, что решения у границы
    принимает шум конкретного draw. Регрессия —
    `test_split_gain_is_independent_of_dimensionality`.

    **Чего эта починка НЕ даёт: воспроизводимого числа состояний.** Замер
    2026-08-11: отбрасывание пятидесяти баров (0.016% истории BTC) меняет
    число состояний с 40 на 46. Хаос живёт в процедуре, а не в пороге —
    стартовое разбиение MiniBatchKMeans чувствительно к малым изменениям
    данных, а рекурсия усиливает каждый перевёрнутый выбор во всё поддерево.
    Практическое следствие: **число состояний — характеристика прогона, а не
    рынка монеты**; сравнивать графы двух прогонов по числу узлов
    бессмысленно, и «стало больше состояний» не является диагнозом.
    Разбор и направление починки — `development_log.md`, 21.17.

11. **Замер лифта обязан считать блочный бутстрап.** Наблюдения зависимы:
    горизонт 24h — это 96 баров, кандидаты идут каждые ~11 баров, плюс снимки
    офсетов. Наивный z-тест анти-консервативен примерно втрое по `z`.
    Значимость считается по бутстрапному p-value, наивный печатается рядом
    ради сопоставимости. Регрессия —
    `test_block_bootstrap_rejects_the_spurious_effect`.

12. **Метка набора признаков и атомов собирается ИЗ СОСТАВА источников**
    (`"v1"`, `"v1+smc"`, `"v1+onchain+smc"`), а не нумеруется вручную.
    Двоичная схема на втором источнике даёт двум разным наборам одну метку,
    после чего `feature_sets.names` перезаписывается, а старые строки
    `features` читаются под чужими именами — молча. С 2026-08-14 второй
    источник (`fgi`) существует, и метки `v1+fgi` / `v1+smc` / `v1+fgi+smc`
    собираются реально, а не гипотетически. Реестр источников —
    `btcproc/features/registry.py`; при этом он **не владеет порядком
    атомов**: `ATOM_FAMILY` остаётся единственным упорядоченным источником
    правды. Регрессии — `test_two_sources_never_share_a_label`,
    `test_atom_bit_order_is_pinned`.

13а. **Модель размаха отдаёт числа ТОЛЬКО для баров после конца своего
    обучения.** Боевая версия учится на всей истории (иначе платила бы
    качеством за собственный замер), поэтому на исторических барах её
    квантили — запоминание, а не прогноз, и отличить одно от другого по
    числам невозможно. Режет `range_forecast.view` по `train_end`; следствие —
    кандидаты из `train` полей размаха не несут вообще, они появляются только
    в `live`. Тот же класс защиты, что инвариант 4 даёт признакам.

    Рядом — ловушка, на которой легко попасться: обучающая матрица
    (`design_matrix`) выбрасывает строки без цели, а цель считается по
    горизонту ВПЕРЁД, то есть её нет у последних 96 баров. Для предсказания
    существует отдельный вход `input_matrix`, и именно он даёт свежие бары.
    Воспользуйся `live` обучающей матрицей — он молча получил бы пустой
    прогноз на свежем баре и заполненный на баре суточной давности.

    Модель, не прошедшая гейт калибровки, сохраняется (`calibrated=false`,
    причины в `metrics.failures`), но в кандидата не идёт: «модели нет» и
    «модель есть, но не годится» — разные диагнозы. Регрессии —
    `tests/test_range_forecast.py`.

13. **`train` сносит граф монеты в Neo4j.** Ключ узла там `(symbol, group_id)`
    без измерения модели, а `train` перенумеровывает `group_id`: без очистки
    счётчики рёбер растут поверх узлов прежнего поколения, и отличить их
    нельзя. Очистка привязана к сохранению модели, а не к отправке —
    недельный `train --no-emit` тоже подменяет модель. Ошибка очистки роняет
    прогон.

14. **У уведомлений три предохранителя, и снимать их нельзя поодиночке.**
    Механизм — `btcproc/notify/`, формат тела — `docs/notifications.md`
    (внешний контракт, версия лежит в самом теле).

    * **Окно свежести** `NOTIFY_MAX_CANDIDATE_AGE_MIN` (180 мин). `train`
      выпускает сотни тысяч кандидатов с 2017 года; без окна первый же полный
      прогон с отправкой разослал бы их все — не ошибкой, а по написанному.
      Возраст режется в SQL: список id бывает в десятки тысяч.
    * **Захват доставки** — пара `(rule_id, candidate_id)` в
      `notification_deliveries` через `ON CONFLICT DO NOTHING RETURNING`.
      Окна `live` перекрываются намеренно, и это единственное, что стоит
      между перекрытием и дублями у получателя. Он же позволяет держать ДВЕ
      точки рассылки (`emit_pending` после оценки и конец `run_live` для
      неоценённых) без условий, которые бы разъехались.
    * **Фильтр по рейтингу не срабатывает без оценки.** `rating` и
      `quality_score` считает btc-graph; «рейтинг неизвестен» — это не
      «рейтинг подходит». Иначе правило «только STRONG» слало бы всё подряд
      ровно тогда, когда приёмник недоступен. Регрессия —
      `test_rating_filter_does_not_fire_without_evaluation`.

    Плюс `notify.flush()` в конце прогона: потоки-отправители демонические, а
    `make live` — крон-процесс, и без ожидания очередь умирала бы вместе с ним.
    Ретраев нет сознательно (23.4 в журнале): уведомление про рынок протухает
    за минуты, доставленное через час оно вреднее недоставленного.

15. **Состояние определяется ТОЛЬКО как «ближайший центроид».** `fit_states`
    возвращает метки предиктом, а не членством в группах рекурсивного
    дробления, и нумерует группы по убыванию predict-наполнения. Иначе train
    и live размечают историю двумя разными правилами: дробление режет
    пространство последовательными локальными границами, ячейка группы не
    совпадает с ячейкой её центроида, а модель хранит только центроиды — то
    есть воспроизвести членство она не способна в принципе. Замер до правки
    (2026-08-15, боевые модели четырёх монет): расхождение **21–28% баров**,
    у SOL predict находил на 16% больше переходов; `market_groups` и имена
    состояний описывали разбиение, которого боевой предиктор не давал.
    Регрессия — `test_fit_labels_equal_predict`.

16. **Признаки источника не имеют права молча срезать историю.** Финальный
    `dropna()` в `build_features` режет строку целиком, а внешний источник
    существует не на всей истории монеты (метрики деривативов BTC — с
    2020-09 при барах с 2017-08). Потеря строк сверх базового набора
    ограничена `config.features.max_source_row_loss`; превышение — ошибка с
    именем виновного источника, а не предупреждение. Смежное правило: бар,
    у которого признак вырождается (нулевой диапазон, плоское окно RSI),
    получает граничное значение, а не NaN — «сжатие» это не «нет данных», и
    исчезнувший бар сдвигает позиционные офсеты снимков и рвёт непрерывность
    возраста состояния.

17. **Кэши источников пишутся одним присваиванием.** Админка гоняет прогоны в
    разных ПОТОКАХ одного процесса, а пара `_CACHE["key"], _CACHE["value"]`
    под GIL не атомарна: перемежение оставляет ключ одной монеты со значением
    другой, после чего джойн по совпавшим timestamp молча выдаёт монете чужие
    величины. Единственный слот с кортежем — `features/_cache.py`.

18. **Антиспам алертов монитора состоит из трёх частей, и они не
    взаимозаменяемы.** `cooldown` (5 мин) ограничивает частоту напоминаний,
    `hysteresis` (5 п.п.) не даёт метрике у порога слать пары
    «сработало/отпустило», `sustain` (5 замеров для CPU/load) отсекает
    штатные потолки процессора при кластеризации. Уберёшь гистерезис —
    cooldown не поможет: каждое событие формально новое. Уберёшь выдержку —
    уведомление будет приходить на каждый `train`. Состояние правил лежит в
    SQLite, а не в памяти процесса, иначе перезапуск сервиса = повторная
    рассылка про известную проблему. Регрессии — `tests/test_hostmon.py`.

19. **Админка не считает агрегаты на клик — их считает `train`.** Панель узла
    графа показывает фон состояния (лифт контекстных атомов), и до 2026-08-16
    он считался в обработчике: join `bar_states` × `bar_events` по всей
    истории монеты плюс `unnest` массивов, три секунды и 320 тысяч обращений
    к буферам на каждое открытие узла. Пять кликов подряд уложили боевую
    базу (журнал 43). Теперь агрегат пишет `repo.save_state_context` в конце
    `train`, а страница читает `state_context`.

    Правило общее, а не про этот запрос: **величина, неизменная после
    завершения прогона, считается один раз и хранится**. Разметка train не
    меняется — значит всё, что из неё выводится, вычислять на чтение
    незачем. Кэш в памяти процесса эту роль не выполняет: он заполняется
    ПОСЛЕ первого ответа, а одновременные запросы уходят в БД до того.
    Поверх стоят два предохранителя, и они не взаимозаменяемы:
    `admin/single_flight.py` схлопывает одинаковые параллельные запросы
    (первый считает, остальные ждут его результат), а `statement_timeout`
    в `queries.fetch_all/fetch_one` (60 с) не даёт одному сломанному запросу
    держать соединение. Потолок задаёт вызывающий и никогда — пул: в том же
    процессе фоновые потоки гоняют `train` с bulk-вставками на десятки минут.

20. **Память Postgres задаётся аргументами командной строки, и обойти это
    `ALTER SYSTEM`-ом нельзя.** Образ `timescaledb-ha` прогоняет
    `timescaledb-tune` один раз при создании тома и считает, что машина
    принадлежит только базе: на боевом VPS он выставил
    `shared_buffers=1985MB` — постоянные 2 ГБ в `docker stats` при базе 3.2 ГБ
    и попадании в кэш 99.9%, — и оставил `autovacuum_work_mem` наследовать
    `maintenance_work_mem=993MB`, что при десяти воркерах даёт до 9.7 ГБ на
    машине с восемью. Обе величины переопределены в `command` сервиса postgres
    в `btc-graph/docker-compose.yml`; там же грузится `pg_stat_statements`.

    Три способа сломать это молча: поправить настройку через `ALTER SYSTEM`
    (попадёт в `postgresql.auto.conf` и проиграет аргументам командной
    строки — правка просто не подействует); сделать `docker compose restart`
    вместо `up -d` (контейнер поднимется со старой командой); затереть
    `timescaledb` в `shared_preload_libraries` вторым значением — тогда база
    не поднимется вовсе. Разбор — раздел 48 журнала, страница диагностики —
    `/server/postgres`.

## Конвенции

* Окружение читается **только** в `btcproc/config.py` — модули берут настройки
  из готовых dataclass'ов (`config.data`, `config.states`, `config.candidates`,
  `config.sink`, `config.notify`, `config.admin`). Новый параметр добавляется туда же, с
  комментарием о смысле значения по умолчанию.
* Тяжёлые импорты (`pandas`, pipeline, uvicorn, httpx-приёмник) делаются лениво
  внутри команд CLI — старт `--help` и `status` не должен тянуть весь стек.
* Служебные поля кандидата живут в `_meta` и снимаются `strip_meta` перед
  отправкой.
* Цвета состояний для фронтенда генерируются на сервере в hex:
  lightweight-charts падает на `hsl(...)` с «Cannot parse color». По той же
  причине прозрачность заливок считается из hex вручную (`withAlpha` в
  `server.html`) — `color-mix(...)` библиотека тоже не понимает.
* **Ключи словарей, уходящих в шаблоны, не называются именами методов dict**
  (`items`, `keys`, `values`, `get`). Jinja сначала пробует `getattr`, поэтому
  `containers.items` резолвится в метод, а страница падает с «object is not
  iterable» (журнал 40.7).
* `except Exception` в прогонах и в диагностике приёмника — намеренный, чтобы
  прогон завершался с диагнозом, а не трейсбеком; помечается `# noqa: BLE001`.
