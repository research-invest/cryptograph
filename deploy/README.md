# Разворачивание crypto-graph на VPS

Два скрипта. Оба запускаются **с локальной машины** и всё делают по ssh —
на сервере руками ничего вводить не нужно.

```bash
cd deploy
./01_deploy.sh        # код, docker, venv, образы
./02_configure.sh     # .env, стек, миграции, первый прогон, кроны
```

Предусловия: `ssh-copy-id vps@<host>` уже сделан, на сервере есть `sudo`
без пароля, ОС — Ubuntu/Debian.

## Что делает каждый

### `01_deploy.sh` — инфраструктура и код

1. проверяет сервер (ОС, sudo, ssh) — до того, как что-то менять;
2. системные пакеты, Docker, `vps` в группу `docker`;
3. `rsync` обоих проектов в `/opt/crypto-graph`;
4. **проверяет, что 8000 и 5555 закрыты на `127.0.0.1`** (с 2026-08-09 это
   дефолт самого `docker-compose.yml`, шаг лечит только старые чекауты);
5. собирает **один общий venv** на оба проекта;
6. собирает docker-образы;
7. прогоняет тесты обоих проектов на сервере;
8. пересобирает **уже запущенные** контейнеры, накатывает миграции и
   перезапускает админку (на первом деплое стека ещё нет — шаги молча
   пропускаются, всё это делает `02_configure.sh`).

Ничего не запускает и `.env` не создаёт. Повторный запуск безопасен.

**`./01_deploy.sh --code-only` — «выкатить свежий код».** Делает только то,
что относится к коду: rsync, зависимости, тесты, пересборку контейнеров,
миграции и перезапуск админки. Не трогает пакеты, часовой пояс, swap, docker,
раздачу каталога, правку портов в compose, сборку образов с нуля, ufw, `.env`
и кроны. `pip install` в этом режиме запускается, только если менялся любой из
двух `requirements.txt` (отпечаток лежит в `venv/.requirements.md5`) — иначе
каждая выкатка стоила бы полной переустановки зависимостей.

Порядок в конце важен: контейнеры → миграции → админка. `alembic` живёт
внутри контейнера `api` и на старом образе не увидит новых ревизий, а админка
должна стартовать на уже мигрированной схеме. Миграции графа Neo4j сюда не
вынесены — они разовые, привязаны к заведению новой монеты и остаются
в `02_configure.sh`.

### `02_configure.sh` — конфигурация и запуск

1. `.env` обоих проектов (пароль админки и `ADMIN_SECRET_KEY` генерируются здесь);
2. обёртка `/opt/crypto-graph/bin/btcproc` — правильный интерпретатор и cwd;
3. поднимает стек и **ждёт healthcheck**, а не просто «контейнер запущен»;
4. `alembic upgrade head`, миграция графа Neo4j, схема `processing`;
5. ufw: наружу только 22, 80 и 443;
6. админка btcproc как systemd-сервис;
7. **nginx** перед админкой + сертификат Let's Encrypt, после чего админка
   уезжает на `127.0.0.1` и 8100 закрывается;
8. **обучение монет** из `TRAIN_SYMBOLS` под systemd, по одной подряд;
9. и только после успеха всех — кроны (live, train, сводка, уборка) и logrotate.

Флаги: `--force-env` (пересоздать `.env`, пароль админки сменится),
`--skip-train` (не гонять прогоны — кроны встанут сразу),
`--retrain` (переобучить уже обученные монеты),
`--reset-db` (снести тома PostgreSQL/Redis/Neo4j — необратимо),
`--nginx-only` (только шаг 7 — поставить или починить прокси на уже
развёрнутой машине, ничего больше не трогая),
`--drop-symbols` (подтвердить, что обученная монета выводится из расписания
осознанно — см. ниже).

Домен и сертификат задаются переменными: `ADMIN_DOMAIN` (по умолчанию
`crypto-graph.selll.ru`), `TLS_EMAIL`, `ENABLE_TLS=0` — прокси без
сертификата. Пустой `ADMIN_DOMAIN` возвращает старую схему: nginx не
ставится, админка сама смотрит наружу на 8100.

Монеты задаются переменной: `TRAIN_SYMBOLS="BTCUSDT ETHUSDT SOLUSDT"` (по
умолчанию все три). Уже обученная монета пропускается — `train` переобучает
модель состояний с нуля, и `group_id` нового прогона несопоставим со старым:
накопленный в Neo4j граф смешал бы две нумерации. Для осознанного
переобучения есть `--retrain`.

**`TRAIN_SYMBOLS` — полный список монет контура, а не «что доучить».**
Переменная работает на два шага сразу: шаг 8 обучает из неё только
необученные монеты, а шаг 9 собирает из неё **всё** расписание заново.
Поэтому `TRAIN_SYMBOLS="SUIUSDT"` при добавлении монеты означает не «доучи
SUI», а «в кроне остаётся только SUI» — остальные монеты выпадут из `live`
и `train` без единой ошибки, просто перестав обновляться. Шаг 4а сверяет
переменную с обученными монетами в базе и падает с готовой командой, если
кто-то потерялся; осознанный вывод монеты из расписания подтверждается
флагом `--drop-symbols`. Первая монета списка попадает в `.env` как `SYMBOL`
— монета по умолчанию для одиночных команд, поэтому BTCUSDT держим первым.

## Почему именно так

**Один venv на оба проекта.** Не экономия места, а требование `SINK_MODE=direct`:
btcproc импортирует пакет btc-graph как библиотеку, и `pgvector` с `neo4j`
обязаны лежать в том же интерпретаторе, откуда запущен btcproc. Разъезд
интерпретаторов проявляется молча — кандидаты считаются, sink рапортует об
успехе, записей в базе нет.

**Порты заданы в самом `docker-compose.yml`, не через override.** Списки
`ports` при слиянии compose-файлов *склеиваются*, поэтому override добавил бы
второй биндинг рядом со старым, а не заменил его. И ufw тут бесполезен:
docker пишет свои правила в обход его цепочек, опубликованный на `0.0.0.0`
порт остаётся доступен снаружи при любом `ufw deny`.

**API btc-graph не имеет аутентификации вообще** — отсюда `127.0.0.1` для
8000 и 5555. Наружу смотрит только админка btcproc: у неё есть логин, лимит
попыток и блокировка, и стоит она за nginx с сертификатом Let's Encrypt.

**nginx ставится последним из связки, а 8100 закрывается самым последним.**
Шаг устроен так: поднять nginx → убедиться, что прокси реально отвечает →
выпустить сертификат → и только теперь перевести админку на `127.0.0.1` и
снять правило ufw. Обратный порядок означал бы «отрезать работающий вход и
потом выяснить, что новый не работает» — доступ остался бы только по ssh.
По той же причине шаг откладывает сам себя, если в этот момент идёт прогон:
прогоны, запущенные ИЗ админки, живут `BackgroundTasks` в её процессе, и
рестарт ради смены `ADMIN_HOST` убил бы их. Тогда nginx уже работает, 8100
просто остаётся открытым до `./02_configure.sh --nginx-only`.

**`ADMIN_TRUST_PROXY` и `ADMIN_HOST` переключаются только вместе.** Читать
`X-Forwarded-For` можно ровно тогда, когда до админки нельзя достучаться в
обход nginx. Иначе заголовок ставит сам клиент: любой адрес из
`ADMIN_IP_ALLOWLIST` открывает дверь, а новый выдуманный адрес на каждую
попытку обнуляет счётчик неудачных входов, и блокировка не накапливается
никогда. Оба значения выводятся в скрипте из одного `ADMIN_DOMAIN`, чтобы не
могли разъехаться. В самом конфиге nginx по той же причине стоит
`proxy_set_header X-Forwarded-For $remote_addr` — перезапись, а не привычная
склейка `$proxy_add_x_forwarded_for`: админка берёт из заголовка первый
адрес, и при склейке первым оказался бы присланный клиентом.

**Админка запущена на хосте, а не в docker.** У btcproc есть свой
`docker-compose.yml` для неё, но тогда админка и cron работали бы из разных
интерпретаторов — ровно та ловушка, о которой предупреждает `CLAUDE.md`.

**Сначала прогон, потом кроны.** `live` продолжает работу обученной модели
состояний — до `train` ему нечего размечать. Плюс `train` и `live` одной
монеты друг друга блокируют: cron, попавший на идущий первый прогон, просто
отвалился бы с ошибкой. По той же причине скрипт снимает расписание на время
обучения и возвращает его в конце — но главная причина здесь память, см. ниже.

**Часовой пояс выставляется в UTC явно.** Не потому, что Ubuntu ставит его
сам — у части хостеров образ идёт с местной зоной. Binance отдаёт бары в UTC,
и все метки в базе тоже UTC; в локальной зоне «отставание баров» в `status`
и время в логах разошлись бы с реальностью на несколько часов, а cron-строки
означали бы не то время, что в них написано. После смены зоны скрипт
перезапускает `cron` — он читает её при старте и иначе продолжил бы считать
по старой.

**Swap обязателен.** У VPS его обычно нет вовсе, и на 8 ГБ это ловушка: расчёт
признаков держит в pandas всю историю разом, рядом сидят postgres и neo4j, пик
упирается в потолок — и ядро убивает прогон. Проявляется это отвратительно:
в логе btcproc **ничего**, прогон просто обрывается на середине этапа, а запись
в `processing.runs` остаётся в статусе `running`. Диагноз виден только в
`journalctl`: `killed by the OOM killer`. `01_deploy.sh` создаёт swap по объёму
RAM и ставит `vm.swappiness=10` — swap как подушка под пик, а не как
повседневная память.

С 2026-08-09 такой прогон хотя бы перестал блокировать монету навсегда: у
прогонов есть heartbeat (`runs.updated_at`), и молчащий дольше
`RUN_STALE_AFTER_MINUTES` помечается failed при следующей попытке. Причину
это не лечит — swap всё так же обязателен.

**Уборка базы стоит отдельным кроном** (`scripts/maintenance.py`, среда 04:40
UTC). Она чистит разметку старых `live`-прогонов и вакуумит; при идущем
прогоне откладывается сама. Середина недели выбрана намеренно: воскресный
`train` идёт часами, и обслуживание рядом с ним пропускалось бы каждый раз.
Разметку `train` уборка **не трогает** — это осознанно отложенное решение, и
именно она остаётся главным источником роста базы (312 тыс. строк на монету
каждую неделю). Отчёт скрипта в `logs/maintenance.log` печатает размеры
таблиц и свободное место — по нему видно, когда к вопросу придётся вернуться.

**Крон перечисляет монеты явными `--symbol`, а не `--all`.** `--all` берёт весь
реестр `btcproc/symbols.py`, и монета, которую ещё не обучали, роняла бы весь
пакетный прогон ненулевым кодом каждые полчаса.

**Первый прогон идёт под systemd**, а не в ssh-сессии: обрыв связи его не
убивает. Скрипт опрашивает результат короткими соединениями и, если его
прервать, при повторном запуске подхватит уже идущий прогон.

## После разворачивания

Админка: **https://crypto-graph.selll.ru/login** (пароль печатается в конце
`02_configure.sh`, лежит в `/opt/crypto-graph/logs/.admin_creds`).

```bash
ssh vps@<host>
/opt/crypto-graph/bin/btcproc status          # покрытие, отставание, очередь
sudo nginx -t && sudo systemctl status nginx  # прокси
sudo certbot certificates                     # срок сертификата
tail -f /var/log/nginx/crypto-graph.error.log # 502/504 от прокси
tail -f /opt/crypto-graph/logs/live.log       # что делает cron
cat /opt/crypto-graph/logs/maintenance.log   # недельная уборка: размеры и рост
sudo systemctl status btcproc-admin           # админка
cd /opt/crypto-graph/btc-graph && docker compose ps
```

Доступ к закрытым сервисам — туннелем:

```bash
ssh -L 8000:127.0.0.1:8000 -L 5555:127.0.0.1:5555 -L 7474:127.0.0.1:7474 vps@<host>
```

### Осталось руками

* **`ANTHROPIC_API_KEY`** в `/opt/crypto-graph/btc-graph/.env` — сейчас там
  заглушка. Без ключа система работает полностью, кроме текстовых объяснений:
  все числа считает детерминированный скорер, LLM только формулирует.
  После правки: `cd /opt/crypto-graph/btc-graph && docker compose up -d --force-recreate`.
### Как добавить монету

Порядок важен (см. `CLAUDE.md`): `SymbolSpec` в `btcproc/symbols.py` →
**профиль оценки в `btc-graph/config/symbols/<TICKER>.yaml`** → тикер в
`TRAIN_SYMBOLS` **рядом со старыми** → перезапустить `02_configure.sh`.
Скрипт обучит только новую монету, а расписание соберёт по всему списку:

```bash
./01_deploy.sh --code-only
TRAIN_SYMBOLS="BTCUSDT ETHUSDT SOLUSDT SUIUSDT" ./02_configure.sh
```

Полная процедура заведения монеты (реестр, история, приёмка графа, калибровка
профиля, sanity-якорь, локальная проверка) — скилл `.claude/skills/add-symbol/`
и `btc-graph-processing/docs/operator_guide.md`, раздел 11. На сервер монета
выкатывается уже проверенной локально: `02_configure.sh` её не калибрует и
качество графа не смотрит.

Без профиля монета получит флаг `unknown_symbol_profile` и оценку по линейке
биткоина — по данным это не диагностируется, кандидат выглядит нормально
оценённым. Проверить постфактум: в `candidates.scoring_profile` должен стоять
`<TICKER>@N`, а не `_DEFAULT`.

Если у новой монеты состояний в разы меньше, чем у BTC (36), дело не в профиле
оценки, а в `states_overrides` в `btcproc/symbols.py` — пороги кластеризации
живут на стороне генератора.

### Чего скрипты не делают

Резервного копирования, мониторинга/алертов, ограничения доступа к
админке по IP (`ADMIN_IP_ALLOWLIST` пуст — теперь его можно включать: за
прокси адрес клиента наконец достоверен). Пароли PostgreSQL и Neo4j остались
дефолтными из `docker-compose.yml` — это осознанно: оба порта слушают только
`127.0.0.1`, а смена пароля затрагивает compose и оба `.env` сразу.
