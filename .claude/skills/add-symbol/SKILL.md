# Заведение новой монеты

Монета живёт в **двух** проектах: генератор `btc-graph-processing` (btcproc) считает
её граф состояний и выпускает кандидатов, приёмник `btc-graph` их оценивает своей
линейкой. Пропущенная половина не даёт ошибки — она даёт молча неверные данные.

**Порядок фаз обязателен.** Каждая фаза заканчивается гейтом: не сошёлся гейт —
не переходи дальше, чини на месте. Причина в фазе 6 (`emit`): отправленные
кандидаты оценятся тем профилем, который есть на момент отправки, и пересчёта
записей в системе нет.

Деплой (фаза 7) выполняется **только по явной команде пользователя**. Фазы 1–6
локальные и обратимые; фаза 7 трогает боевой контур, ломает расписание при
неверных аргументах и стоит часы прогона.

## Что надо знать до начала

- Пути: `/Volumes/work/crypto-graph/btc-graph-processing` (btcproc),
  `/Volumes/work/crypto-graph/btc-graph` (приёмник и вся инфраструктура).
- **Пороги кластеризации живут в btcproc, пороги оценки — в btc-graph.** Мало
  состояний → `states_overrides` в btcproc. Всё WEAK → профиль в btc-graph.
  Симптомы похожи, лечатся в разных репозиториях.
- **Монета не обязана быть с Binance.** Площадка — поле `venue` в `SymbolSpec`
  (`binance_spot`, `bybit_spot`). Отсутствие пары на Binance не повод
  отказываться от монеты: сначала проверь Bybit (фаза 1).
- **Третий источник — деривативные метрики Binance USD-M** (ОИ, long/short
  ratio, тейкеры) в `deriv_metrics`, `DERIV_ENABLED=true` в проде. Он читает
  фьючерс Binance USD-M **по тикеру, независимо от `venue`** — даже у монеты
  со спотом на Bybit (HYPEUSDT) метрики идут с Binance. Это context-атомы
  (4 квадранта `oi_vs_price`), они не входят в вектор признаков и не влияют
  ни на кластеризацию состояний, ни на `event_block_id` — значит не гейт ни
  для одной фазы, но стоит забэкфиллить, чтобы монета не осталась без них
  молча (фаза 2а).
- `group_id` осмыслен только в паре `(symbol, run_id)`. Не сравнивай номера
  состояний новой монеты с BTC.
- Кандидат — исследовательская идея, а не торговый сигнал. Проговаривать это
  в ответах пользователю.

## Фаза 1. Реестр btcproc

Дату листинга проверяем фактом, а не по памяти — лишние месяцы это лишние
HTTP-запросы при каждом `ingest`, а завышенная дата молча теряет историю:

```bash
cd /Volumes/work/crypto-graph/btc-graph-processing
python3 -c "from btcproc import symbols; print(symbols.resolve_history_start('SUIUSDT'))"
```

### Если на Binance пары нет — ищи на Bybit

`UnknownSymbolError: дампов не найдено` означает ровно одно: **на споте Binance
этой пары нет**. Не бросай задачу и не подставляй похожий тикер — сначала
проверь вторую площадку. Так заведён HYPEUSDT: на споте Binance его нет вовсе
(только бессрочный фьючерс), на Bybit он торгуется с 2025-07.

```bash
# та же проверка, другой источник курса
python3 -c "from btcproc import symbols; print(symbols.resolve_history_start('HYPEUSDT', probe_from='2024-01-01', venue='bybit_spot'))"
```

Осторожно с похожими тикерами: `HYPEUSDT` (Hyperliquid) и `HYPERUSDT`
(Hyperlane) — **разные монеты**, и вторая на споте Binance есть. Молча взять
её вместо первой хуже, чем не завести ничего. Если пары нет ни там, ни там —
скажи пользователю и остановись, а не подбирай замену сам.

Площадка объявляется полем `venue` в `SymbolSpec` (`binance_spot` по умолчанию,
`bybit_spot`). Дальше она нигде не всплывает: диспетчер `btcproc/ingest/sources.py`
выбирает загрузчик, а прогоны видят одинаковые строки в `ohlcv`.

**Чем Bybit отличается на деле:** бары собираются из тиковых архивов, а не
из готовых klines — только в тиках есть сторона агрессора, без которой монета
молча теряет признак `taker_bias` и оба атома доминирования тейкеров. Цена —
объём закачки (~6 МБ на месяц против 0.3 МБ), поэтому `ingest` идёт заметно
дольше. Подробности и обоснования — в шапке `btcproc/ingest/bybit.py`.

Добавь `SymbolSpec` в `btcproc/symbols.py` — в конец кортежа `SYMBOLS`, с `note`
о том, чем монета отличается (площадка, длина истории, ликвидность).
`states_overrides` на этом шаге **не задавай**: относительный порог дробления
сначала должен показать, что он не справился.

`metrics_start` на этом шаге тоже, как правило, не задавай — пустая строка
резолвится в `METRICS_ARCHIVE_START` (`2021-12-01`, граница самого архива
Binance). Переопределяй только если бисекцией нашёл, что архив монеты
начинается раньше (как у BTC, `2020-09-01`) или биржевой листинг перпа не
совпадает с листингом спота другой площадки (как у HYPEUSDT — см. её `note`
про двойное смешение площадок). `_validate_metrics_start` не даст поставить
дату раньше `2020-09-01` — это защита от опечатки, а не запрет как таковой.

Гейт: `python3 -m pytest tests/test_multi_symbol.py tests/test_bybit_ingest.py -q`
(там живут тесты реестра и площадок) и `python3 -m btcproc.cli status` — новая
монета в таблице, история нулевая.

## Фаза 2. История

```bash
python3 -m btcproc.cli ingest --symbol SUIUSDT
```

Десятки минут. Гейт: в ответе `rows` > 0, а `missing_months` пуст или содержит
только месяцы до листинга. Сплошные пропуски с начала — не та дата или тикера
нет на площадке; `451` в ошибке — гео-блокировка REST Binance, смотри
`references/troubleshooting.md`.

Для монеты с Bybit проверь ещё и качество сборки: бары там считаются из тиков
нами, а не берутся у биржи готовыми, поэтому ошибка агрегации выглядела бы как
странный рынок, а не как сбой. Сверка с публичными klines биржи — прямая:

```bash
python3 - <<'PY'
import httpx, pandas as pd
from btcproc.ingest import bars
frame = bars.load_ohlcv("HYPEUSDT", "15m").tail(500)
start = int(frame.index[0].timestamp()*1000)
k = httpx.get("https://api.bybit.com/v5/market/kline", params={"category":"spot",
    "symbol":"HYPEUSDT","interval":"15","start":start,"limit":1000}, timeout=60).json()["result"]["list"]
kdf = pd.DataFrame(k, columns=["ts","o","h","l","c","v","turn"]).astype(float)
kdf.index = pd.to_datetime(kdf.ts, unit="ms", utc=True)
cmp = frame.join(kdf, how="inner")
for a, b in [("high","h"), ("low","l"), ("close","c"), ("volume","v")]:
    print(a, "расхождений:", int(((cmp[a]-cmp[b]).abs() > 1e-8).sum()), "из", len(cmp))
PY
```

Норма — ноль расхождений по `high`, `low`, `close` и объёму. `open` может
разойтись на единичных барах: он наследуется от закрытия предыдущего, и на
самом первом баре истории наследовать нечего. Десятки расхождений по `close`
означают сломанный порядок сделок внутри миллисекунды — разбор в шапке
`btcproc/ingest/bybit.py`, регрессии в `tests/test_bybit_ingest.py`.

## Фаза 2а. Деривативные метрики (не гейт)

```bash

```

Источник — Binance USD-M фьючерс по тикеру; венью спота (фаза 1) не связан.

На проде монету дальше подхватит общий крон `ingest-metrics --all` — отдельно
её туда прописывать не нужно.

## Фаза 3. Граф состояний, без отправки

```bash
python3 -m btcproc.cli train --symbol SUIUSDT --no-emit
```

`--no-emit` обязателен: до профиля оценки кандидаты слать некуда — они получат
линейку биткоина, и это не диагностируется по данным.

Гейт (числа того же порядка, что у BTC):

| Проверка | Норма | Где смотреть |
|---|---|---|
| Число состояний | 25–50, а не 5 и не 200 | `stats.states.groups` в ответе, `market_groups` |
| Доля `scope=transition+event_block` | больше нуля — но см. оговорку ниже | `stats.candidates.scopes` |
| Кандидатов выпущено | тысячи | `stats.candidates.produced` |

**Оговорка про `transition+event_block` на короткой истории.** Норма 19–32%
выведена на монетах с историей в шесть и более лет. Выборка кандидата
набирается из СНИМКОВ конфигураций, а не из баров, и порог `min_sample_size`
(30 аналогов) применяется к паре «переход × блок событий». У монеты с историей
в год снимков на порядок меньше, а число пар почти то же — до тридцати не
добирается ни одна пара, и все кандидаты выходят со `scope=transition`.

Замер на HYPEUSDT (13 месяцев, 38 тыс. баров): 8 415 снимков на 4 458 пар,
доля `transition+event_block` — ровно ноль, при 42 состояниях и 1 785
кандидатах. У BTCUSDT на тех же порогах — 66 813 снимков и 13.5%.

Ноль здесь — свойство длины истории, а не поломка, и **понижать
`CAND_MIN_SAMPLE_SIZE` ради его исправления нельзя**: система и без того не
подтвердилась на отложенной части (журнал btcproc, раздел 26), а меньшая
выборка делает оценки ещё шумнее. Отличать этот случай от настоящей поломки
инварианта 3 просто: при поломке ноль будет и у монеты с длинной историей.

```sql
-- run_id и статистика последнего train монеты
SELECT id, status, stats FROM processing.runs
 WHERE symbol='SUIUSDT' AND kind='train' AND status='done'
 ORDER BY started_at DESC LIMIT 1;
```

(`docker compose exec -T postgres psql -U btc_user -d btc_graph` из каталога btc-graph.)

Глазами — `make admin`, переключатель монеты в шапке: раскраска графика должна
совпадать с видимой сменой режима, граф состояний не должен быть звездой из
одного узла.

**Пять состояний вместо сорока — это не «такой рынок», это пороги.** Лечится
`states_overrides` в `SymbolSpec` (`min_group_size`, `min_group_share`,
`seed_clusters`), после чего фаза 3 повторяется. Число состояний — характеристика
прогона, а не рынка: от полусотни баров оно гуляет на ±15%, поэтому «40 против 46»
диагнозом не является, а «5 против 40» — является.

## Фаза 4. Профиль оценки в btc-graph

Без профиля кандидаты монеты получают флаг `unknown_symbol_profile` и линейку
биткоина. Направление, в которое надо двигать ступени, заранее неизвестно: у ETH
линейка BTC оказалась слишком мягкой, а не строгой.

```bash
cd /Volumes/work/crypto-graph/btc-graph

# 1. Выгрузка. ORDER BY ts обязателен: в схеме кандидата поля времени нет,
#    калибратор доверяет порядку строк, и без сортировки проверка на отложенной
#    части считает «будущим» случайные строки.
docker compose exec -T postgres psql -U btc_user -d btc_graph -tA -c \
  "SELECT payload::text FROM processing.candidates
    WHERE symbol='SUIUSDT' ORDER BY ts;" > dumps/sui_candidates.jsonl

# 2. Отчёт, ничего не записывая.
python3 scripts/calibrate_profile.py --symbol SUIUSDT \
    --input dumps/sui_candidates.jsonl --holdout 0.3 --dry-run

# 3. Запись профиля (пресет весов — по типу монеты, таблица ниже).
python3 scripts/calibrate_profile.py --symbol SUIUSDT \
    --input dumps/sui_candidates.jsonl --weights low-liquidity \
    --out config/symbols/SUIUSDT.yaml
```

| `--weights` | Кому | Логика |
|---|---|---|
| `btc` | эталон | текущая калибровка биткоина |
| `major-alt` | ETH, крупные альты | выборки короче, надёжность важнее перекоса |
| `low-liquidity` | монеты потоньше | перекос на малой выборке чаще артефакт |
| `young` | история меньше года | «редкость» на коротком окне не редкость |

Правило: **чем меньше данных, тем больше веса статистической надёжности и меньше
— направленности и редкости.**

Как читать отчёт:

- **Доли рейтингов** — ориентир селективности BTC: ~1% STRONG, ~38% MODERATE.
  Границы скрипт подбирает сам (`--target-strong`).
- **Разброс осей**: σ < 0.05 — ось вырождена, она всем ставит одинаковый балл.
  Лечится ступенями, а не весом.
- **Отложенная часть** (`--holdout 0.3`): доли разъехались вдвое — профиль
  подогнан под прошлое. Небольшой сдвиг вверх — норма, выборки растут со временем.

Чего не делать: править YAML руками «на глаз» (через месяц никто не объяснит
числа — скрипт оставляет в файле комментарий о происхождении); трогать
`_default.yaml` (это общая мерка и baseline всех монет, её правка обесценивает
все накопленные оценки разом); калибровать монету с меньше чем полусотней
кандидатов.

Гейт: файл `config/symbols/SUIUSDT.yaml` есть, `make profiles-check` зелёный.

## Фаза 5. Sanity-якорь и тесты

Монету нельзя завести без якоря — на это есть падающий тест. Якорь ловит
перекалибровку, которая выглядит правкой одной ступени, а переводит понятный
кандидат через границу рейтинга.

```bash
cd /Volumes/work/crypto-graph/btc-graph
python3 ../.claude/skills/add-symbol/scripts/make_sanity_anchor.py \
    --symbol SUIUSDT --input dumps/sui_candidates.jsonl --dry-run
# устроило — без --dry-run: допишет запись в tests/fixtures/sanity_candidates.json
```

Скрипт берёт кандидата, максимально удалённого от границ рейтинга (у границы
якорь падал бы от любого шевеления), и записывает `expected_rating` вместе с
заметкой о происхождении.

Гейт — оба проекта зелёные:

```bash
cd /Volumes/work/crypto-graph/btc-graph && make test-local
cd ../btc-graph-processing && make test
```

Если правил `symbols.py` или схему кандидата — прогони btcproc-тесты в обоих
интерпретаторах (`make test`, `make test PY=.venv/bin/python`): часть багов
воспроизводится только на свежих pandas/numpy.

## Фаза 6. Отправка кандидатов в btc-graph

Профиль есть — теперь можно слать. Повторный `train` для этого **не нужен** и
вреден: он переобучит модель, перенумерует `group_id` и снесёт накопленный граф
монеты в Neo4j. Досылаем кандидатов уже сделанного прогона:

```bash
cd /Volumes/work/crypto-graph/btc-graph-processing
python3 -m btcproc.cli emit --run <run_id из фазы 3>
```

Отправляются только те, у кого нет отметки об отправке; повторный запуск
безопасен. Историческая очередь разбирается долго — команда печатает прогресс.

Гейт — кандидаты дошли и оценены **своим** профилем:

```sql
SELECT scoring_profile, rating, count(*) FROM candidates
 WHERE symbol='SUIUSDT' GROUP BY 1,2 ORDER BY 1,2;
```

В `scoring_profile` должно стоять `SUIUSDT@1`, а не `_DEFAULT@N`. Ноль STRONG
сразу после первого прогона — **норма, а не поломка**: очередь идёт от самых
старых кандидатов, а профиль откалиброван по нынешнему режиму. STRONG появятся,
когда очередь дойдёт до свежих.

Дальше монета живёт на `live`:

```bash
python3 -m btcproc.cli live --symbol SUIUSDT
```

## Фаза 7. Выкатка на прод — только по явной команде

Не запускай без прямой просьбы пользователя. Перед запуском убедись, что фазы
1–6 пройдены локально и код закоммичен в обоих репозиториях (rsync переносит и
незакоммиченное, но разбираться потом придётся в git).

```bash
cd /Volumes/work/crypto-graph/deploy
./01_deploy.sh --code-only                                  # код, тесты, миграции
TRAIN_SYMBOLS="BTCUSDT ETHUSDT SOLUSDT SUIUSDT" ./02_configure.sh
```

**`TRAIN_SYMBOLS` перечисляет ВСЕ монеты, а не только новую.** Шаг 8 пропустит
уже обученные (проверка по `processing.runs`), а вот шаг 9 переписывает crontab
целиком из этой переменной: с одной новой монетой в списке остальные выпали бы
из расписания без единой ошибки — просто перестав обновляться. Шаг 4а сверяет
переменную с обученными монетами в базе и падает с готовой командой, так что
ошибиться тут теперь трудно; осознанный вывод монеты из расписания
подтверждается флагом `--drop-symbols`. BTCUSDT держи первым — первая монета
списка попадает в `.env` как `SYMBOL`.

Что произойдёт: скрипт снимет расписание, обучит новую монету под systemd
(15–60 минут на монету, обрыв ssh не мешает — можно перезапустить скрипт, он
подхватит идущий прогон), и только после успеха вернёт кроны уже со всеми
монетами. Ошибка прогона → кроны НЕ ставятся, разбираться по
`/opt/crypto-graph/logs/train.log`.

Проверка после выкатки:

```bash
ssh vps@162.248.225.60 '/opt/crypto-graph/bin/btcproc status'
ssh vps@162.248.225.60 'crontab -l | grep btcproc'     # новая монета в live и train
```

И на боевой базе — тот же запрос `scoring_profile`, что в фазе 6: профиль монеты
должен быть свой. Профиль едет на VPS вместе с кодом (`config/symbols/` в rsync),
но контейнер `api` читает профили на старте — если правил профиль без выкатки
кода, нужен `docker compose up -d --force-recreate` или `make reload`.
